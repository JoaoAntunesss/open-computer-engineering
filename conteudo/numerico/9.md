Em métodos numéricos, o código "funciona" quase sempre: dá um número. A pergunta é se o número está certo, e com que erro. Ler código numérico obriga a pensar em precisão, convergência e critérios de paragem.

## Ler e prever: somar números pequenos

```python run
total = 0.0
for _ in range(10):
    total += 0.1
print(total, total == 1.0)

grande = 1e16
print(grande + 1 - grande)
print(sum([1e16, 1.0, -1e16]))

import math
print(math.fsum([1e16, 1.0, -1e16]))
```

Antes de correr: que linhas dão o resultado matematicamente certo, e quais não?

## Encontra o erro: bisseção que nunca para

```python run
def bissecao(f, a, b, tol=1e-12):
    passos = 0
    while b - a > tol and passos < 200:
        m = (a + b) / 2
        if f(a) * f(m) < 0:
            b = m
        else:
            a = m
        passos += 1
    return m, passos

print(bissecao(lambda x: x**2 - 2, 0, 2))
print(bissecao(lambda x: x**2 - 2e12, 0, 2e6))
```

O primeiro termina em poucos passos. O segundo bate no limite de 200 passos. Porquê? Pensa no tamanho de `b - a` comparado com a precisão de um `float` perto de 1,4 milhões.

??? Soluções
**Ler e prever:** a soma de dez 0,1 dá `0.9999999999999999` e a comparação dá `False`. `1e16 + 1 - 1e16` dá `0.0` (o 1 perde-se, porque um `float` tem cerca de 16 algarismos). `sum` dá `1.0` desde o Python 3.12, que passou a somar `float`s com compensação de erros (em versões anteriores dava `0.0`), e `math.fsum` também dá `1.0`. Um ciclo com `+=`, como o primeiro, não tem essa proteção.

**Encontra o erro:** perto de 1,4 × 10⁶, a distância entre dois `float` consecutivos é cerca de 2 × 10⁻¹⁰, maior do que a tolerância absoluta de 10⁻¹². O intervalo nunca consegue ficar tão pequeno, e o ciclo só para pelo limite de passos.

**Escreve tu:** com tolerância relativa, ambos terminam. Como cada passo divide o intervalo por 2, são precisos cerca de log₂(10¹²) ≈ 40 passos.
