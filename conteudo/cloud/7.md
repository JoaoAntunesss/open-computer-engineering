**SRE** (Site Reliability Engineering, criada na Google) trata a fiabilidade como um problema de engenharia, com números. A ideia central: 100% de disponibilidade não é o objetivo (é impossível e caríssimo); o objetivo é ser **tão fiável quanto os utilizadores precisam**, e usar a margem que sobra para lançar coisas novas.

## SLI, SLO, SLA

- **SLI** (indicador): o que se mede. Ex.: fração de pedidos com resposta 2xx em menos de 300 ms.
- **SLO** (objetivo): a meta interna. Ex.: 99,9% num período de 30 dias.
- **SLA** (acordo): o contrato com clientes, com penalizações; mais folgado do que o SLO.

## Orçamento de erros

Se o SLO é 99,9%, podes falhar 0,1%: esse é o **orçamento de erros**. Enquanto houver orçamento, a equipa lança à vontade; se se gastar, congela lançamentos e investe em fiabilidade.

```python run
def orcamento(slo, dias=30):
    return (1 - slo) * dias * 24 * 60

for slo in [0.99, 0.999, 0.9999]:
    print(f"SLO {slo:.2%}: {orcamento(slo):7.1f} minutos de falha por mês")

pedidos, maus = 4_200_000, 3_150
slo = 0.999
permitidos = pedidos * (1 - slo)
print(f"usado {maus / permitidos:.0%} do orçamento")
```

Cada «9» extra divide o orçamento por dez, e custa muito mais.

## Gestão de incidentes

Quando algo falha: (1) **mitigar primeiro** (reverter, desviar tráfego), investigar depois; (2) papéis claros: quem comanda, quem comunica, quem investiga; (3) no fim, um **postmortem sem culpas**: o que aconteceu, cronologia, causa, o que vamos mudar para não se repetir. A pergunta não é «quem errou?», é «porque é que o sistema deixou este erro chegar a produção?».
