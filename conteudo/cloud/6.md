Num sistema com dezenas de serviços, a pergunta «porque está lento?» só tem resposta se o sistema for **observável**. Os três pilares:

- **Logs**: eventos discretos com contexto («pedido 123 falhou: timeout na BD»). De preferência estruturados (JSON), para se poderem pesquisar.
- **Métricas**: números ao longo do tempo (pedidos/s, latência, uso de CPU). Baratas de guardar, boas para alertas e gráficos (Prometheus, Grafana).
- **Traces**: o caminho de um pedido por vários serviços, com o tempo gasto em cada um (OpenTelemetry, Jaeger).

## Os quatro sinais dourados

Para qualquer serviço: **latência**, **tráfego**, **erros** e **saturação**. A latência mede-se em **percentis**, não em médias: a média esconde os utilizadores que esperam muito.

```python run
import random, statistics

random.seed(7)
lat = [random.gauss(80, 15) for _ in range(980)] + [random.uniform(900, 2000) for _ in range(20)]
lat.sort()
def p(q):
    return lat[int(q / 100 * len(lat)) - 1]

print(f"média  {statistics.mean(lat):6.0f} ms")
print(f"p50    {p(50):6.0f} ms")
print(f"p99    {p(99):6.0f} ms")
print(f"p99.9  {p(99.9):6.0f} ms")
```

2% dos pedidos são muito lentos. A mediana não os vê; a média sobe um pouco e parece aceitável; o p99 mostra o problema.

## Alertas

Um bom alerta é **acionável** e sobre **sintomas que o utilizador sente** (taxa de erros, latência alta), não sobre causas que podem não importar (CPU a 90% sem impacto). Alertas a mais criam fadiga: as pessoas passam a ignorá-los.

```python
# log estruturado
import json, time
print(json.dumps({"ts": time.time(), "nivel": "erro", "pedido": "a81f", "rota": "/pagar", "ms": 3012, "msg": "timeout BD"}))
```
