Desde cerca de 2005, a frequência dos processadores quase deixou de subir: mais frequência significa mais calor do que se consegue dissipar. Os ganhos passaram a vir do **paralelismo**: vários **núcleos** a correr em simultâneo e instruções **SIMD** que fazem a mesma operação sobre vários dados de uma vez. O hardware está lá; para o aproveitar, o software tem de ser escrito a pensar nele.

## Os níveis de paralelismo

1. **Ao nível da instrução** (ILP): pipeline, execução fora de ordem, várias instruções por ciclo (superescalar). Automático, feito pelo hardware.
2. **Ao nível dos dados** (SIMD): uma instrução opera sobre um vetor de valores (4, 8, 16 de uma vez).
3. **Ao nível das threads**: vários núcleos, cada um com o seu programa ou thread.
4. **Ao nível do pedido**: muitos servidores a atender pedidos diferentes (em Sistemas Distribuídos).

## SIMD

Com AVX2 (x86), um registo de 256 bits guarda 8 `float`. Uma instrução soma 8 pares de uma vez:

```c
// soma de vetores: o compilador vetoriza este ciclo com -O3
void soma(float *a, float *b, float *c, int n) {
    for (int i = 0; i < n; i++) c[i] = a[i] + b[i];
}
```

Com `-O3 -march=native`, o GCC gera `vaddps` (8 somas por instrução). Na ARM chama-se NEON; no RISC-V, extensão V. É o que torna rápidos o processamento de imagem, o áudio, a criptografia e o `numpy`.

Para o compilador vetorizar, o ciclo tem de ser simples: sem dependências entre iterações (`c[i] = c[i-1] + a[i]` não vetoriza diretamente) e sem saltos imprevisíveis.

## Multicore

Cada núcleo tem a sua L1 e L2; a L3 e a RAM são partilhadas. Problemas novos:

- **Coerência de caches:** se o núcleo 1 altera `x` na sua cache, o núcleo 2 não pode continuar a ler o valor antigo. Protocolos como o **MESI** marcam cada linha (Modificada, Exclusiva, Partilhada, Inválida) e invalidam as cópias dos outros núcleos quando alguém escreve.
- **Falsa partilha** (*false sharing*): duas threads escrevem em variáveis **diferentes** que estão na **mesma linha de cache**. A linha salta entre núcleos a cada escrita e o programa fica muito mais lento, sem nenhum erro visível.
- **Consistência de memória:** a ordem pela qual um núcleo vê as escritas de outro não é garantida sem instruções de sincronização (*fences*, operações atómicas). Por isso a programação concorrente usa trincos e atómicos, e não variáveis normais.

## Lei de Amdahl

Se uma fração p do programa pode ser paralelizada, o ganho máximo com n núcleos é:

ganho = 1 / ((1 − p) + p/n)

Prevê o ganho com 4, 16 e 64 núcleos para p = 0,9 e p = 0,99:

```python run
def amdahl(p, n):
    return 1 / ((1 - p) + p / n)

for p in (0.5, 0.9, 0.99):
    print(f"p = {p}:", [round(amdahl(p, n), 1) for n in (4, 16, 64, 1024)])
```

Com 10% de código sequencial, nunca se passa de 10 vezes mais rápido, nem com mil núcleos.

## GPUs

Uma GPU leva o paralelismo ao extremo: milhares de núcleos simples que executam a **mesma instrução** sobre dados diferentes (SIMT). Ótimas para gráficos, multiplicação de matrizes e treino de redes neuronais; más para código com muitos `if` diferentes de thread para thread. Programam-se com CUDA, OpenCL ou, indiretamente, com bibliotecas como o PyTorch.

## Medir: vetorizado contra ciclo

O `numpy` usa SIMD e código compilado; um ciclo em Python não. Prevê a diferença:

```python run
import time
import numpy as np

n = 1_000_000
a = np.random.rand(n).astype(np.float32)
b = np.random.rand(n).astype(np.float32)

t = time.perf_counter()
c = [a[i] + b[i] for i in range(n)]
t_ciclo = time.perf_counter() - t

t = time.perf_counter()
c2 = a + b
t_vetor = time.perf_counter() - t

print(f"ciclo: {t_ciclo * 1000:.0f} ms   vetorizado: {t_vetor * 1000:.2f} ms")
print("mais rápido:", round(t_ciclo / t_vetor), "vezes")
```
