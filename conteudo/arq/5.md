O **pipeline** é a ideia que torna os processadores rápidos: em vez de esperar que uma instrução acabe para começar a seguinte, cada etapa trabalha numa instrução diferente ao mesmo tempo, como numa linha de montagem. Com cinco etapas, há até cinco instruções em curso. O preço são os **conflitos** (*hazards*): situações em que uma instrução não pode avançar porque depende de outra.

## A ideia

Sem pipeline, 3 instruções de 5 etapas demoram 15 ciclos. Com pipeline:

```
ciclo:    1    2    3    4    5    6    7
instr 1:  IF   ID   EX   MEM  WB
instr 2:       IF   ID   EX   MEM  WB
instr 3:            IF   ID   EX   MEM  WB
```

7 ciclos. Com muitas instruções, acaba **quase uma por ciclo**. Cada instrução individual não fica mais rápida (latência igual ou maior); o que aumenta é o **débito** (instruções por segundo). E o ciclo pode ser curto: só tem de caber a etapa mais lenta.

## Conflitos estruturais

Duas instruções precisam do mesmo recurso no mesmo ciclo. Exemplo: uma lê instruções (IF) e outra lê dados (MEM) da mesma memória. Resolve-se com hardware: memórias (caches) separadas para instruções e dados.

## Conflitos de dados

```asm
add  t0, t1, t2      # escreve t0 no WB (ciclo 5)
sub  t3, t0, t4      # lê t0 no ID (ciclo 3): ainda não está lá!
```

Soluções:

1. **Parar** (*stall*): o `sub` espera até `t0` estar escrito. Perdem-se ciclos (bolhas).
2. **Encaminhamento** (*forwarding*): o resultado sai da ALU no fim do EX; liga-se diretamente à entrada da ALU da instrução seguinte, sem esperar pelo WB. Resolve a maioria dos casos sem perder ciclos.
3. O caso que o encaminhamento não resolve totalmente: **load-use**.

```asm
lw   t0, 0(a0)       # o valor só existe no fim do MEM
add  t1, t0, t2      # precisa dele no início do EX: 1 bolha obrigatória
```

O compilador ajuda **reordenando** instruções: põe uma instrução independente entre o `lw` e o uso.

## Conflitos de controlo

Num `beq`, só se sabe se o salto é tomado no EX. Entretanto, já entraram no pipeline as instruções seguintes, que podem estar erradas.

- **Parar** até saber: perde ciclos em cada salto (e ~20% das instruções são saltos).
- **Prever:** assumir um resultado e continuar; se a previsão estiver errada, deitam-se fora as instruções erradas.
- **Previsão dinâmica:** uma tabela lembra o que cada salto fez nas últimas vezes. Os ciclos acertam quase sempre (são tomados em todas as voltas menos na última). Os processadores modernos acertam mais de 95%.

Isto explica um resultado famoso: percorrer um vetor **ordenado** com um `if` lá dentro é muito mais rápido do que o mesmo vetor desordenado, porque o `if` fica previsível.

## Simular o efeito do encaminhamento

Prevê quantos ciclos demora cada sequência, sem encaminhamento e com:

```python run
def ciclos(prog, forwarding):
    # prog: lista de (destino, [fontes], é_load)
    pronto = {}                 # registo -> primeiro ciclo de EX em que pode ser usado
    ex = 0
    for i, (dest, fontes, load) in enumerate(prog):
        ex = max([ex + 1, i + 3] + [pronto.get(f, 0) for f in fontes])
        if forwarding:
            pronto[dest] = ex + (2 if load else 1)   # load: valor no fim do MEM
        else:
            pronto[dest] = ex + 3                    # só depois do WB (escrita na 1.ª metade)
    return ex + 2               # MEM e WB da última

a = [("t0", ["a0"], True), ("t1", ["t0", "t2"], False), ("t3", ["t1"], False)]
b = [("t0", ["a0"], True), ("t3", ["t4"], False), ("t1", ["t0", "t2"], False)]
for nome, p in (("dependente", a), ("reordenado", b)):
    print(nome, "sem:", ciclos(p, False), "com:", ciclos(p, True))
```
