Quase todas as aplicações modernas são um **front-end** (no browser ou no telemóvel) a falar com um **back-end** através de uma **API**. O estilo mais comum é **REST** sobre HTTP, com os dados em **JSON**. Desenhar bem a API poupa trabalho a quem a usa, e evita dores de cabeça quando a aplicação cresce.

## Recursos e métodos

REST organiza a API em **recursos** (substantivos), identificados por URLs, e usa os **métodos HTTP** como verbos:

| Pedido | Significado | Resposta típica |
|---|---|---|
| `GET /api/marcacoes?dia=2026-11-10` | listar (com filtro) | 200 + lista |
| `GET /api/marcacoes/42` | obter uma | 200, ou 404 |
| `POST /api/marcacoes` | criar | 201 + `Location: /api/marcacoes/43` |
| `PATCH /api/marcacoes/42` | alterar parte | 200 |
| `PUT /api/marcacoes/42` | substituir toda | 200 |
| `DELETE /api/marcacoes/42` | apagar | 204 |

Más práticas comuns: verbos nos URLs (`/api/criarMarcacao`), `GET` que altera dados (`/api/marcacoes/42/apagar`), responder sempre 200 com `{"erro": …}` lá dentro.

**Idempotência:** `GET`, `PUT` e `DELETE` podem ser repetidos sem efeitos extra (apagar duas vezes deixa o mesmo estado). `POST` não: repetir cria duas marcações. Por isso, para pagamentos, usa-se uma **chave de idempotência** enviada pelo cliente.

## JSON

```json
{
  "id": 42,
  "cliente": { "nome": "Marta", "telefone": "912345678" },
  "servicos": ["corte", "brushing"],
  "inicio": "2026-11-10T10:00:00+00:00",
  "pago": false,
  "notas": null
}
```

Tipos: objetos, listas, texto, números, `true`/`false`, `null`. Datas não existem: usa-se texto em **ISO 8601** com fuso horário. Dinheiro: cêntimos inteiros (`1500`) ou texto (`"15.00"`), nunca vírgula flutuante.

## Erros

Usa os códigos HTTP (400, 401, 403, 404, 409, 422, 500) e um corpo com detalhe útil, sempre no mesmo formato:

```json
{ "erro": "hora_ocupada", "mensagem": "As 10:00 de 10/11 já estão ocupadas.", "sugestoes": ["10:30", "11:00"] }
```

## Paginação, filtros e versões

- Listas grandes: `GET /api/clientes?limite=50&depois=…` (paginação por cursor) ou `?pagina=2`.
- Filtros e ordenação na *query string*: `?estado=confirmada&ordem=-inicio`.
- Versões: `/api/v1/...`, para poder mudar a API sem partir quem a usa.

## Consumir uma API

```js run
// Uma "API" falsa, para correr aqui sem servidor. No browser real seria fetch("/api/...").
const bd = { marcacoes: [{ id: 1, hora: "10:00", cliente: "Ana" }] };
async function api(metodo, url, corpo) {
  await new Promise(r => setTimeout(r, 10));                    // simula a rede
  if (metodo === "GET" && url === "/api/marcacoes") return { status: 200, json: bd.marcacoes };
  if (metodo === "POST" && url === "/api/marcacoes") {
    if (bd.marcacoes.some(m => m.hora === corpo.hora))
      return { status: 409, json: { erro: "hora_ocupada", mensagem: `${corpo.hora} já está ocupada` } };
    const nova = { id: bd.marcacoes.length + 1, ...corpo };
    bd.marcacoes.push(nova);
    return { status: 201, json: nova };
  }
  return { status: 404, json: { erro: "nao_encontrado" } };
}

(async () => {
  for (const pedido of [["POST", "/api/marcacoes", { hora: "11:00", cliente: "Rui" }],
                        ["POST", "/api/marcacoes", { hora: "10:00", cliente: "Eva" }],
                        ["GET", "/api/marcacoes"],
                        ["DELETE", "/api/clientes/7"]]) {
    const r = await api(...pedido);
    console.log(pedido[0], pedido[1], "→", r.status, JSON.stringify(r.json));
  }
})();
```

Prevê o código de estado de cada pedido. No código real, verifica sempre `r.ok` (status 200–299) antes de usar a resposta: o `fetch` **não** lança exceção num 404 ou 500, só quando a rede falha.

## Alternativas ao REST

- **GraphQL:** o cliente diz exatamente que campos quer, num só pedido. Bom para front-ends com necessidades variadas; mais complexo no servidor.
- **gRPC:** binário, com contratos (Protocol Buffers), rápido. Comum entre microsserviços.
- **WebSockets / Server-Sent Events:** para dados em tempo real (a agenda que se atualiza sozinha). O Firebase faz isto por ti.
