Em Haskell e em OCaml quase nunca se escrevem tipos, e mesmo assim tudo é verificado estaticamente. O compilador **deduz** os tipos mais gerais possíveis, com o algoritmo de **Hindley-Milner** (HM). Perceber como funciona explica as mensagens de erro destas linguagens e a inferência (mais limitada) de Rust, TypeScript, Kotlin e Swift.

## Polimorfismo paramétrico

`length :: [a] -> Int` funciona para listas de qualquer tipo `a`. Em HM, os tipos podem ter **variáveis de tipo**, e uma função pode ter um **esquema** de tipo: ∀a. [a] → Int. Em cada uso, a variável é instanciada com um tipo concreto.

## A ideia: gerar e resolver equações

1. Dá-se a cada expressão desconhecida uma **variável de tipo** nova (t1, t2, …).
2. Cada construção do programa gera **restrições** (equações entre tipos). Em `f x`, se f : t1 e x : t2, então t1 = t2 → t3 (e o resultado tem tipo t3).
3. Resolvem-se as equações com **unificação**: encontrar a substituição mais geral que as torna verdadeiras.
4. As variáveis que sobram ficam **genéricas** (polimorfismo), no `let`.

## Unificação

Unificar dois tipos é torná-los iguais, substituindo variáveis:

- t1 com Int → t1 := Int.
- (t1 → Bool) com (Int → t2) → t1 := Int, t2 := Bool.
- Int com Bool → **erro de tipos**.
- t1 com (t1 → Int) → erro: **verificação de ocorrência** (t1 apareceria dentro de si mesmo, um tipo infinito).

```python run
import itertools
contador = itertools.count(1)
def nova(): return f"t{next(contador)}"

def resolve(t, s):                              # aplica a substituição s ao tipo t
    while isinstance(t, str) and t in s: t = s[t]
    if isinstance(t, tuple): return (t[0],) + tuple(resolve(x, s) for x in t[1:])
    return t

def ocorre(v, t, s):
    t = resolve(t, s)
    return t == v or (isinstance(t, tuple) and any(ocorre(v, x, s) for x in t[1:]))

def unifica(a, b, s):
    a, b = resolve(a, s), resolve(b, s)
    if a == b: return s
    if isinstance(a, str) and a.startswith("t"):
        if ocorre(a, b, s): raise TypeError(f"tipo infinito: {a} = {mostra(b)}")
        return {**s, a: b}
    if isinstance(b, str) and b.startswith("t"): return unifica(b, a, s)
    if isinstance(a, tuple) and isinstance(b, tuple) and a[0] == b[0] and len(a) == len(b):
        for x, y in zip(a[1:], b[1:]): s = unifica(x, y, s)
        return s
    raise TypeError(f"não consigo unificar {mostra(a)} com {mostra(b)}")

def mostra(t):
    if isinstance(t, str): return t
    if t[0] == "→": return f"({mostra(t[1])} → {mostra(t[2])})"
    return f"[{mostra(t[1])}]"

def infere(e, ctx, s):
    k = e[0]
    if k == "num": return "Int", s
    if k == "bool": return "Bool", s
    if k == "var": return ctx[e[1]], s
    if k == "lambda":
        tx = nova()
        tc, s = infere(e[2], {**ctx, e[1]: tx}, s)
        return ("→", tx, tc), s
    if k == "app":
        tf, s = infere(e[1], ctx, s)
        ta, s = infere(e[2], ctx, s)
        tr = nova()
        s = unifica(tf, ("→", ta, tr), s)
        return tr, s

prim = {"soma": ("→", "Int", ("→", "Int", "Int")), "nao": ("→", "Bool", "Bool")}
exemplos = {
    "λx. x": ("lambda", "x", ("var", "x")),
    "λx. soma x 1": ("lambda", "x", ("app", ("app", ("var", "soma"), ("var", "x")), ("num", 1))),
    "λf. λx. f (f x)": ("lambda", "f", ("lambda", "x", ("app", ("var", "f"), ("app", ("var", "f"), ("var", "x"))))),
    "λf. λg. λx. f (g x)": ("lambda", "f", ("lambda", "g", ("lambda", "x",
                             ("app", ("var", "f"), ("app", ("var", "g"), ("var", "x")))))),
    "λx. nao (soma x 1)": ("lambda", "x", ("app", ("var", "nao"), ("app", ("app", ("var", "soma"), ("var", "x")), ("num", 1)))),
    "λx. x x": ("lambda", "x", ("app", ("var", "x"), ("var", "x"))),
}
for nome, e in exemplos.items():
    try:
        t, s = infere(e, prim, {})
        print(f"{nome:22} : {mostra(resolve(t, s))}")
    except TypeError as erro:
        print(f"{nome:22} ✗ {erro}")
```

Prevê os seis resultados. O terceiro e o quarto ficam com variáveis livres no fim: são **polimórficos** (o terceiro é "aplicar duas vezes", o quarto é a **composição** de funções). Os nomes das variáveis (t3, t7…) dependem da ordem em que foram criadas.

## Let-polimorfismo

```haskell
let id = \x -> x in (id 3, id True)
```

Isto é aceite: no `let`, o tipo de `id` é **generalizado** para ∀a. a → a, e cada uso recebe uma instância nova (Int → Int, Bool → Bool). Mas como parâmetro de uma lambda não: `(\id -> (id 3, id True)) (\x -> x)` é recusado, porque o parâmetro tem um único tipo (monomórfico). É o compromisso que torna HM decidível e eficiente. (Polimorfismo de ordem superior, como no System F, exige anotações.)

## Na prática

- Haskell, OCaml, F#, Elm: inferência completa (anotam-se os tipos de topo por clareza).
- Rust, Swift, Kotlin, TypeScript, C++ (`auto`): inferência **local** (dentro das funções); as assinaturas escrevem-se.
- As mensagens de erro de HM podem ser difíceis: o erro aparece onde a unificação falhou, que pode ser longe de onde está o engano. Anotar os tipos ajuda a localizar.
