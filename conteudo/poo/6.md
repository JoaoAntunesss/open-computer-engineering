Os princípios **SOLID** são cinco regras para desenhar classes que se mantêm fáceis de mudar quando o programa cresce. Não são leis: são sinais de alerta. Quando uma mudança pequena obriga a mexer em muitas classes, ou quando é difícil testar uma classe sozinha, normalmente há um destes princípios a ser violado.

## S — Responsabilidade única

Uma classe deve ter **uma única razão para mudar**.

```java
// Mau: três razões para mudar (regras de negócio, formato do PDF, servidor de email)
class Fatura {
    double calcularTotal() { ... }
    byte[] gerarPdf() { ... }
    void enviarPorEmail(String para) { ... }
}

// Melhor
class Fatura { double calcularTotal() { ... } }
class FaturaPdf { byte[] gerar(Fatura f) { ... } }
class EnvioEmail { void enviar(String para, byte[] anexo) { ... } }
```

## O — Aberto/fechado

Aberta a extensão, fechada a modificação: acrescentar comportamento novo não deve obrigar a mudar código que já funciona.

```java
// Mau: cada tipo novo de desconto obriga a mexer aqui
double preco(String tipo, double base) {
    if (tipo.equals("estudante")) return base * 0.8;
    else if (tipo.equals("senior")) return base * 0.7;
    return base;
}

// Melhor: um tipo novo é uma classe nova
interface Desconto { double aplicar(double base); }
class Estudante implements Desconto { public double aplicar(double b) { return b * 0.8; } }
class Senior implements Desconto { public double aplicar(double b) { return b * 0.7; } }
```

## L — Substituição de Liskov

Um objeto de uma subclasse tem de poder ser usado em qualquer sítio onde se espera a superclasse, sem surpresas. Uma subclasse não pode exigir mais (pré-condições mais fortes) nem garantir menos (pós-condições mais fracas).

Sinal de violação: código cheio de `if (x instanceof Subclasse)`, ou subclasses que lançam `UnsupportedOperationException` em métodos herdados.

## I — Segregação de interfaces

Muitas interfaces pequenas e específicas são melhores do que uma grande. Uma classe não deve ser obrigada a implementar métodos de que não precisa.

```java
// Mau: uma impressora simples tem de "implementar" digitalizar e enviar fax
interface Multifuncoes { void imprimir(Doc d); void digitalizar(Doc d); void fax(Doc d); }

// Melhor
interface Impressora { void imprimir(Doc d); }
interface Scanner { void digitalizar(Doc d); }
```

## D — Inversão de dependências

As classes de alto nível (as regras de negócio) não devem depender de detalhes (base de dados, email, ficheiros). Ambas devem depender de **abstrações** (interfaces).

```java
// DependenciasDemo.java
import java.util.*;

public class DependenciasDemo {
    public static void main(String[] args) {
        RepositorioMarcacoes falso = new RepositorioEmMemoria();
        ServicoMarcacoes s = new ServicoMarcacoes(falso);      // injeção pelo construtor
        System.out.println(s.marcar("Ana", 10));
        System.out.println(s.marcar("Rui", 10));
        System.out.println(s.marcar("Rui", 11));
    }
}

interface RepositorioMarcacoes {
    boolean ocupado(int hora);
    void guardar(String cliente, int hora);
}

class RepositorioEmMemoria implements RepositorioMarcacoes {
    private final Map<Integer, String> dados = new HashMap<>();
    public boolean ocupado(int hora) { return dados.containsKey(hora); }
    public void guardar(String cliente, int hora) { dados.put(hora, cliente); }
}

class ServicoMarcacoes {
    private final RepositorioMarcacoes repo;
    ServicoMarcacoes(RepositorioMarcacoes repo) { this.repo = repo; }
    String marcar(String cliente, int hora) {
        if (repo.ocupado(hora)) return "Hora " + hora + " ocupada";
        repo.guardar(cliente, hora);
        return cliente + " marcado às " + hora + "h";
    }
}
```

`ServicoMarcacoes` não sabe se as marcações estão em PostgreSQL, no Firebase ou num `HashMap`. Nos testes, usa-se o repositório em memória; em produção, um que fala com a base de dados. Isto chama-se **injeção de dependências**.

## Ler e prever

Antes de correr `DependenciasDemo`, escreve as três linhas que aparecem.

## Cuidado com o excesso

Aplicar SOLID a tudo dá dezenas de interfaces com uma única implementação, e código difícil de seguir. Começa simples e separa quando aparece uma **segunda** razão para mudar, ou quando precisas de testar algo isoladamente.
