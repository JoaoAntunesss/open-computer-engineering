Um **teste unitário** verifica automaticamente que uma pequena parte do código (normalmente um método) faz o que deve. **Refatorar** é melhorar a estrutura do código sem mudar o que ele faz. Andam juntos: sem testes, refatorar é arriscado; com testes, podes mudar o código com confiança, porque sabes logo se partiste alguma coisa.

## JUnit 5

Com Maven ou Gradle, acrescenta a dependência `org.junit.jupiter:junit-jupiter`. Os testes ficam em `src/test/java`, com a mesma estrutura de pacotes do código.

```java
import org.junit.jupiter.api.*;
import static org.junit.jupiter.api.Assertions.*;

class ContaTest {
    private Conta conta;

    @BeforeEach
    void setUp() {                         // corre antes de cada teste
        conta = new Conta("Ana", 100);
    }

    @Test
    void depositarAumentaOSaldo() {
        conta.depositar(50);
        assertEquals(150, conta.getSaldo(), 0.001);
    }

    @Test
    void naoLevantaMaisDoQueOSaldo() {
        assertFalse(conta.levantar(500));
        assertEquals(100, conta.getSaldo(), 0.001);   // o saldo não mudou
    }

    @Test
    void depositoNegativoLancaExcecao() {
        assertThrows(IllegalArgumentException.class, () -> conta.depositar(-10));
    }

    @ParameterizedTest
    @ValueSource(doubles = {0.01, 1, 99.99, 100})
    void levantamentosValidos(double valor) {
        assertTrue(conta.levantar(valor));
    }
}
```

(Para `@ParameterizedTest`, importa `org.junit.jupiter.params.*` e `org.junit.jupiter.params.provider.ValueSource`.)

Corre com `mvn test`, `gradle test` ou com o botão verde do IntelliJ.

## O que testar

- O caso normal.
- Os **limites**: zero, um, o máximo, a lista vazia, exatamente igual ao saldo.
- Os casos de erro: o método lança a exceção certa?
- Cada teste verifica **uma** coisa e tem um nome que diz o quê. Quando falha, o nome deve dizer o que se partiu.

Estrutura **Arrange–Act–Assert**: preparar os dados, executar a ação, verificar o resultado.

## Cobertura

O JaCoCo (ou o "Run with Coverage" do IntelliJ) mostra que linhas os testes executaram. 80% é um objetivo comum. Mas cobertura alta não garante bons testes: uma linha executada sem nenhum `assert` conta como coberta.

## Testes primeiro (TDD)

1. **Vermelho:** escreve um teste para o comportamento seguinte. Falha.
2. **Verde:** escreve o código mínimo para passar.
3. **Refatorar:** limpa o código, com os testes a garantir que nada se partiu.

## Refatoração

Os "cheiros" mais comuns no código, e o que fazer:

| Cheiro | Refatoração |
|---|---|
| Método longo | **Extrair método** com um nome que explica |
| Código duplicado | Extrair método ou classe partilhada |
| Nomes vagos (`x`, `dados`, `processa`) | **Mudar o nome** (Shift+F6 no IntelliJ) |
| `if/else` ou `switch` por tipo | **Substituir condicional por polimorfismo** |
| Muitos parâmetros | **Introduzir objeto-parâmetro** |
| Números mágicos (`* 0.23`) | Constante com nome (`TAXA_IVA`) |

Exemplo, antes:

```java
double total(List<double[]> linhas, boolean cliente) {
    double t = 0;
    for (double[] l : linhas) t += l[0] * l[1];
    if (cliente) t = t * 0.9;
    return t * 1.23;
}
```

Depois:

```java
private static final double IVA = 0.23;
private static final double DESCONTO_CLIENTE = 0.10;

record Linha(double preco, int quantidade) {
    double subtotal() { return preco * quantidade; }
}

double total(List<Linha> linhas, boolean eCliente) {
    double semIva = linhas.stream().mapToDouble(Linha::subtotal).sum();
    if (eCliente) semIva *= 1 - DESCONTO_CLIENTE;
    return semIva * (1 + IVA);
}
```

O comportamento é o mesmo (os testes confirmam), mas agora lê-se o que faz.
