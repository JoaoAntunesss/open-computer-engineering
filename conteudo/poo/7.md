Um **padrão de desenho** é uma solução conhecida para um problema que aparece muitas vezes no desenho de classes. Os mais famosos vêm do livro *Design Patterns* (1994), do "Gang of Four". Saber os nomes ajuda a comunicar ("aqui usamos um Observer") e a reconhecer a estrutura quando lês código de outras pessoas, nas bibliotecas e nos frameworks.

## Strategy: trocar o algoritmo

Problema: uma parte do comportamento varia (como calcular os portes, como ordenar) e não queres um `if` gigante.

```java
interface CalculoPortes { double calcular(double pesoKg); }

class CTT implements CalculoPortes { public double calcular(double p) { return 3.5 + 1.2 * p; } }
class Gratis implements CalculoPortes { public double calcular(double p) { return 0; } }

class Encomenda {
    private CalculoPortes portes;
    Encomenda(CalculoPortes portes) { this.portes = portes; }
    void setPortes(CalculoPortes portes) { this.portes = portes; }
    double total(double produtos, double peso) { return produtos + portes.calcular(peso); }
}
```

O `Comparator` de Java é uma estratégia de ordenação.

## Observer: avisar interessados

Problema: quando um objeto muda, vários outros precisam de saber, sem o primeiro os conhecer.

```java
// ObserverDemo.java
import java.util.*;
import java.util.function.Consumer;

public class ObserverDemo {
    public static void main(String[] args) {
        Stock s = new Stock();
        s.subscrever(q -> System.out.println("painel: stock = " + q));
        s.subscrever(q -> { if (q < 5) System.out.println("ALERTA: encomendar mais"); });
        s.retirar(3);
        s.retirar(4);
    }
}

class Stock {
    private int quantidade = 10;
    private final List<Consumer<Integer>> observadores = new ArrayList<>();
    void subscrever(Consumer<Integer> o) { observadores.add(o); }
    void retirar(int n) {
        quantidade -= n;
        for (Consumer<Integer> o : observadores) o.accept(quantidade);
    }
}
```

É a base dos eventos em interfaces gráficas (`addActionListener`), do `addEventListener` de JavaScript e de sistemas como o Firebase (`onValue`).

## Factory: decidir que classe criar

Problema: o código que usa um objeto não deve ter de saber que classe concreta instanciar.

```java
class FabricaPagamentos {
    static MetodoPagamento criar(String tipo, String dados) {
        return switch (tipo) {
            case "mbway"  -> new MBWay(dados);
            case "cartao" -> new Cartao(dados);
            default -> throw new IllegalArgumentException("tipo desconhecido: " + tipo);
        };
    }
}
```

Variantes: métodos de fábrica estáticos (`List.of`, `LocalDate.of`), *Abstract Factory*, *Builder* (para objetos com muitos parâmetros opcionais: `new Pedido.Builder().cliente("Ana").urgente().build()`).

## Visitor: operações novas sobre uma estrutura fixa

Problema: tens uma hierarquia estável (os nós de uma árvore de sintaxe) e queres acrescentar operações (avaliar, imprimir, otimizar) sem mexer em cada classe.

```java
interface Expr { <R> R aceitar(Visitante<R> v); }
record Num(int valor) implements Expr { public <R> R aceitar(Visitante<R> v) { return v.num(this); } }
record Soma(Expr a, Expr b) implements Expr { public <R> R aceitar(Visitante<R> v) { return v.soma(this); } }

interface Visitante<R> { R num(Num n); R soma(Soma s); }

class Avaliar implements Visitante<Integer> {
    public Integer num(Num n) { return n.valor(); }
    public Integer soma(Soma s) { return s.a().aceitar(this) + s.b().aceitar(this); }
}
```

É muito usado em compiladores. Em Java moderno, com `sealed interface` e `switch` com padrões, muitas vezes já não é preciso.

## Outros que vais encontrar

- **Singleton:** uma única instância (uma configuração global). Usa com moderação: é estado global e dificulta testes.
- **Adapter:** põe uma classe com a interface errada a funcionar onde se espera outra.
- **Decorator:** acrescenta comportamento envolvendo um objeto (`new BufferedReader(new FileReader(f))`).
- **Template Method:** o esqueleto do algoritmo na superclasse, os passos nas subclasses (o `Relatorio` da lição 3).
