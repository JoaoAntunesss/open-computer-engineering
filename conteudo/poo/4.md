Uma **exceção** é a forma de um método dizer "não consegui fazer o que me pediram" sem devolver um valor especial que alguém se pode esquecer de verificar. Usar bem as exceções separa o caminho normal do tratamento de erros e evita que um problema passe despercebido.

## Lançar e apanhar

```java
// Excecoes.java
import java.util.Scanner;

public class Excecoes {
    static int idadeDe(String texto) {
        int idade = Integer.parseInt(texto.trim());       // pode lançar NumberFormatException
        if (idade < 0 || idade > 150) {
            throw new IllegalArgumentException("idade fora do intervalo: " + idade);
        }
        return idade;
    }

    public static void main(String[] args) {
        for (String t : new String[] {"42", " 7 ", "abc", "-3"}) {
            try {
                System.out.println("ok: " + idadeDe(t));
            } catch (NumberFormatException e) {
                System.out.println("não é um número: " + t);
            } catch (IllegalArgumentException e) {
                System.out.println(e.getMessage());
            } finally {
                System.out.println("  (verificado: '" + t + "')");
            }
        }
    }
}
```

- `throw` lança a exceção; o método termina ali.
- A exceção sobe pela pilha de chamadas até encontrar um `catch` compatível. Se ninguém a apanhar, o programa termina e mostra a pilha (*stack trace*).
- `finally` corre sempre, com ou sem exceção.
- A ordem dos `catch` importa: `NumberFormatException` é subclasse de `IllegalArgumentException`, por isso tem de vir antes.

## Verificadas e não verificadas

- **Verificadas** (*checked*, subclasses de `Exception`): o compilador obriga a apanhá-las ou a declará-las com `throws`. Representam problemas externos que podem acontecer num programa correto: `IOException` (ficheiro não existe), `SQLException`.
- **Não verificadas** (subclasses de `RuntimeException`): indicam normalmente um **erro de programação** ou um argumento inválido: `NullPointerException`, `IndexOutOfBoundsException`, `IllegalArgumentException`.

```java
static String primeiraLinha(String caminho) throws java.io.IOException {
    try (var r = java.nio.file.Files.newBufferedReader(java.nio.file.Path.of(caminho))) {
        return r.readLine();
    }
}
```

## try-with-resources

O `try (recurso)` acima fecha o ficheiro automaticamente, mesmo com exceção. Usa-o sempre com ficheiros, ligações a bases de dados e sockets (tudo o que implementa `AutoCloseable`).

## Criar as tuas exceções

```java
class SaldoInsuficienteException extends Exception {
    private final double emFalta;
    SaldoInsuficienteException(double emFalta) {
        super("faltam " + emFalta + " €");
        this.emFalta = emFalta;
    }
    double getEmFalta() { return emFalta; }
}
```

Uma exceção própria tem nome com significado e pode transportar informação útil a quem a apanha.

## Boas práticas

- **Nunca** engolir exceções: `catch (Exception e) {}` esconde erros e torna-os muito difíceis de encontrar.
- Apanhar só onde se consegue **fazer algo útil** (tentar outra vez, mostrar uma mensagem, usar um valor por omissão). Caso contrário, deixa subir.
- Falhar cedo: validar os argumentos no início do método.
- Mensagens com contexto: "idade fora do intervalo: −3" e não "erro".
- Não usar exceções para o fluxo normal (por exemplo, para sair de um ciclo).
- Ao relançar, manter a causa: `throw new ServicoException("falha ao gravar", e);`.

## Ler e prever

```java
static int f() {
    try {
        throw new RuntimeException("x");
    } catch (RuntimeException e) {
        return 1;
    } finally {
        System.out.println("finally");
    }
}
// System.out.println(f());
```
