Escreves **o que** queres em SQL; a base de dados decide **como** o ir buscar. Esse "como" é o **plano de execução**, escolhido pelo **otimizador**. Para a mesma consulta pode haver milhares de planos, com tempos que vão de milissegundos a horas. Perceber como o otimizador pensa ajuda-te a escrever consultas e índices que ele consegue aproveitar.

## As etapas

1. **Análise:** verifica a sintaxe e se as tabelas e colunas existem.
2. **Reescrita:** expande vistas, simplifica expressões, transforma subconsultas em junções.
3. **Otimização:** gera planos alternativos, estima o custo de cada um e escolhe o mais barato.
4. **Execução:** corre o plano, normalmente como uma árvore de operadores que passam linhas uns aos outros.

## Operadores de acesso

- **Leitura sequencial** (*Seq Scan*): lê a tabela toda. Bom quando se vai buscar uma grande parte.
- **Pesquisa por índice** (*Index Scan*): percorre o índice e vai buscar cada linha.
- **Só pelo índice** (*Index Only Scan*): quando o índice já tem todas as colunas pedidas, nem vai à tabela.

## Algoritmos de junção

| Algoritmo | Como | Bom quando |
|---|---|---|
| **Ciclos encaixados** (*nested loop*) | para cada linha de A, procura em B (de preferência por índice) | A é pequena e B tem índice na coluna de junção |
| **Junção por dispersão** (*hash join*) | constrói uma tabela de dispersão com a mais pequena e percorre a outra | junções de igualdade entre tabelas grandes, sem índices úteis |
| **Junção por fusão** (*merge join*) | ordena as duas pela chave (ou usa índices já ordenados) e percorre em paralelo | as duas já estão ordenadas, ou o resultado tem de vir ordenado |

```python run
import random, time

clientes = [(i, f"cliente{i}") for i in range(20_000)]
marcacoes = [(random.randrange(20_000), random.randrange(100)) for _ in range(20_000)]

def ciclos_encaixados(a, b):
    return [(x, y) for x in a for y in b if x[0] == y[0]]

def juncao_hash(a, b):
    tabela = {}
    for x in a:
        tabela.setdefault(x[0], []).append(x)
    return [(x, y) for y in b for x in tabela.get(y[0], [])]

def juncao_fusao(a, b):
    a, b = sorted(a), sorted(b)
    i = j = 0
    r = []
    while i < len(a) and j < len(b):
        if a[i][0] < b[j][0]: i += 1
        elif a[i][0] > b[j][0]: j += 1
        else:
            k = j
            while k < len(b) and b[k][0] == a[i][0]:
                r.append((a[i], b[k])); k += 1
            i += 1
    return r

for f, a in ((ciclos_encaixados, clientes[:500]), (juncao_hash, clientes), (juncao_fusao, clientes)):
    t = time.perf_counter()
    n = len(f(a, marcacoes))
    print(f"{f.__name__:18} {len(a):>6} clientes: {n:>6} pares em {(time.perf_counter() - t) * 1000:7.1f} ms")
```

Os ciclos encaixados (sem índice) só correm com 500 clientes, para não demorar demasiado: são O(n·m). Prevê quanto tempo demorariam com os 20 000.

## Estimar custos

O otimizador não corre os planos: **estima** o custo, sobretudo em páginas lidas, com base em **estatísticas** das tabelas: número de linhas, número de valores distintos em cada coluna, histogramas.

- `WHERE cidade = 'Porto'` numa tabela de 1 milhão com 50 cidades: estima 20 000 linhas.
- Se as estatísticas estiverem desatualizadas (a tabela cresceu muito desde a última análise), o plano pode ser péssimo. Corre-se `ANALYZE` para as atualizar (o PostgreSQL faz isto automaticamente de tempos a tempos).

**Ordem das junções:** com 5 tabelas, há 120 ordens possíveis (e mais com as formas de as encaixar). Juntar primeiro as que produzem resultados pequenos poupa trabalho em tudo o que vem a seguir. Para muitas tabelas, o otimizador usa programação dinâmica ou heurísticas.

## Regras de reescrita que o otimizador aplica

- **Empurrar seleções para baixo:** filtrar antes de juntar (σ(A ⋈ B) = σ(A) ⋈ B, quando a condição só usa A).
- **Empurrar projeções:** ler só as colunas necessárias.
- Transformar `IN (subconsulta)` e `EXISTS` em junções (*semi-joins*).

## Como ajudar o otimizador

- Ler o plano: `EXPLAIN` (estimado) e `EXPLAIN ANALYZE` (real) no PostgreSQL. Compara as linhas estimadas com as reais: se forem muito diferentes, há um problema de estatísticas.
- Criar os índices certos (lição anterior).
- Evitar funções sobre colunas indexadas no `WHERE`.
- Pedir só as colunas necessárias (`SELECT *` impede *Index Only Scans*).
- O problema **N+1** nas aplicações: buscar 100 clientes e depois fazer 100 consultas, uma por cliente, para as marcações. Uma junção, ou um `WHERE cliente_id IN (...)`, faz o mesmo numa consulta.
