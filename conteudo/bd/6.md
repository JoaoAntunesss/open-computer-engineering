Sem índices, encontrar uma linha numa tabela de dez milhões obriga a ler todas (*full table scan*). Com um **índice**, chega-se lá em três ou quatro leituras de disco. Os índices são a ferramenta número um para tornar uma base de dados rápida, e também a causa de muitos problemas quando são criados a mais ou nas colunas erradas.

## A ideia

Um índice é uma estrutura à parte, ordenada por uma ou mais colunas, com apontadores para as linhas. Como o índice remissivo de um livro: em vez de ler o livro todo à procura de "transação", vais ao índice e ele diz a página.

## Árvores B+

É a estrutura usada por quase todas as bases de dados relacionais.

- É uma árvore **muito larga e baixa**: cada nó ocupa uma página de disco (8 KB no PostgreSQL) e tem centenas de filhos.
- Os nós internos só têm chaves para orientar a pesquisa; os dados (ou os apontadores para as linhas) estão nas **folhas**.
- As folhas estão **ligadas entre si** por ordem, o que torna as consultas por intervalo muito eficientes: encontra-se o início e percorre-se para a direita.
- A árvore mantém-se **equilibrada**: todas as folhas à mesma profundidade, sempre.

Com 500 chaves por nó, uma árvore de altura 3 indexa 500³ = 125 milhões de linhas. Os níveis de cima estão quase sempre em memória, por isso uma pesquisa custa uma ou duas leituras de disco.

Serve para: `=`, `<`, `>`, `BETWEEN`, `ORDER BY`, `LIKE 'abc%'` (prefixo).

## Índices de dispersão (hash)

Uma tabela de dispersão sobre a coluna. O(1) para igualdades, mas não serve para intervalos nem ordenação. Menos usados como índice principal.

## Criar e usar índices

```sql
CREATE INDEX idx_marcacao_cliente ON marcacao (cliente_id);
CREATE INDEX idx_marcacao_dia ON marcacao (dia, servico_id);   -- composto
CREATE UNIQUE INDEX idx_cliente_email ON cliente (email);
```

**Índices compostos** seguem a regra do **prefixo à esquerda**: um índice em `(dia, servico_id)` serve para `WHERE dia = ...` e para `WHERE dia = ... AND servico_id = ...`, mas **não** para `WHERE servico_id = ...` sozinho. É como uma lista telefónica ordenada por apelido e depois nome: não ajuda a procurar só pelo nome.

## Ver o plano

```python run
import sqlite3, time, random
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE marcacao (id INTEGER PRIMARY KEY, cliente_id INTEGER, dia TEXT)")
db.executemany("INSERT INTO marcacao (cliente_id, dia) VALUES (?, ?)",
               [(random.randint(1, 50_000), f"2026-{random.randint(1, 12):02d}-{random.randint(1, 28):02d}")
                for _ in range(300_000)])

def mede(sql):
    plano = db.execute("EXPLAIN QUERY PLAN " + sql).fetchall()
    t = time.perf_counter()
    for _ in range(20):
        db.execute(sql).fetchall()
    return plano[0][-1], (time.perf_counter() - t) / 20 * 1000

consulta = "SELECT * FROM marcacao WHERE cliente_id = 4242"
print("sem índice: %s (%.2f ms)" % mede(consulta))
db.execute("CREATE INDEX idx_cliente ON marcacao (cliente_id)")
print("com índice: %s (%.2f ms)" % mede(consulta))
print("função na coluna: %s (%.2f ms)" % mede("SELECT * FROM marcacao WHERE cliente_id + 0 = 4242"))
```

Prevê, antes de correr: quantas vezes mais rápido fica com o índice? E o que acontece na terceira consulta, em que a coluna aparece dentro de uma expressão?

No PostgreSQL usa-se `EXPLAIN ANALYZE`, que mostra o plano e os tempos reais. "Seq Scan" numa tabela grande, numa consulta frequente, é sinal de que falta um índice.

## Quando um índice não é usado

- A coluna está dentro de uma função ou expressão: `WHERE lower(email) = ...`, `WHERE ano + 1 = 2027`. (Solução: índice sobre a expressão, ou reescrever a condição.)
- `LIKE '%abc'` (começa por um curinga).
- A consulta devolve uma grande parte da tabela: ler tudo seguido é mais rápido do que saltar pelo índice.
- Tipos diferentes: comparar uma coluna de texto com um número.

## O custo dos índices

Cada índice ocupa espaço e **torna as escritas mais lentas**: cada `INSERT`, `UPDATE` ou `DELETE` tem de atualizar todos os índices da tabela. Cria índices para as consultas que realmente existem (em `WHERE`, `JOIN` e `ORDER BY` frequentes), não "em todas as colunas, por precaução". As chaves primárias e as restrições `UNIQUE` já têm índice automático; as chaves estrangeiras, em muitas bases de dados, **não** (e costumam precisar).
