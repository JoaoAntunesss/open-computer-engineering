Antes de criar tabelas, é preciso perceber **o que** se quer guardar. O **modelo entidade-associação** (EA) é uma forma de desenhar os dados de um sistema de forma independente da base de dados: que coisas existem, que características têm e como se relacionam. É o primeiro passo de qualquer projeto de bases de dados, e o diagrama é o que mostras a quem encomendou o sistema para confirmar que percebeste.

## Os três conceitos

- **Entidade:** uma "coisa" sobre a qual se guarda informação: `Cliente`, `Marcação`, `Serviço`. Desenha-se como um retângulo.
- **Atributo:** uma característica da entidade: `nome`, `telefone`, `data`. Desenha-se como uma elipse (ou listado dentro do retângulo, na notação "pé de galinha").
- **Associação** (relacionamento): uma ligação entre entidades: um cliente **faz** marcações. Desenha-se como um losango (ou uma linha com verbo).

Cada entidade tem uma **chave**: um atributo (ou conjunto) que identifica cada ocorrência sem ambiguidade: o NIF, o número de aluno, um código gerado.

## Tipos de atributos

- **Simples** (`idade`) ou **compostos** (`morada` = rua + código postal + localidade).
- **Monovalor** (`data_nascimento`) ou **multivalor** (`telefones`: uma pessoa pode ter vários).
- **Derivados**: calculam-se a partir de outros (`idade` a partir de `data_nascimento`). Normalmente não se guardam.

## Cardinalidade

Quantas ocorrências de cada lado podem participar na associação:

- **1:1** — uma pessoa tem um cartão de cidadão; um cartão pertence a uma pessoa.
- **1:N** — um cliente faz muitas marcações; cada marcação é de um cliente.
- **N:M** — um aluno inscreve-se em muitas cadeiras; uma cadeira tem muitos alunos.

E a **participação**: **obrigatória** (toda a marcação tem de ter cliente) ou **opcional** (um cliente pode ainda não ter marcações).

Na notação "pé de galinha", o lado "muitos" desenha-se com três traços, e a obrigatoriedade com um traço (|) ou um círculo (o) para opcional.

## Um exemplo: um salão com marcações online

Requisitos, em palavras: "O salão tem vários funcionários. Cada serviço (corte, coloração…) tem um preço e uma duração. Os clientes marcam um serviço com um funcionário, para um dia e hora. Um funcionário pode fazer vários serviços."

```
CLIENTE (id, nome, telefone, email)
FUNCIONARIO (id, nome)
SERVICO (id, nome, preco, duracao_min)

CLIENTE 1 ──faz── N MARCACAO
FUNCIONARIO 1 ──atende── N MARCACAO
SERVICO 1 ──é de── N MARCACAO
MARCACAO (id, data_hora, estado)

FUNCIONARIO N ──sabe fazer── M SERVICO
```

Repara que `MARCACAO` é uma entidade própria, e não só uma linha entre cliente e serviço: tem atributos seus (data, estado) e liga três entidades.

## Entidades fracas e especialização

- **Entidade fraca:** não se identifica sozinha. Uma `LinhaFatura` só faz sentido dentro da sua `Fatura` (a chave é número da fatura + número da linha).
- **Especialização / generalização:** `Pessoa` com subtipos `Aluno` e `Docente`, cada um com atributos próprios. Como a herança em POO.

## Erros comuns

- Tratar como atributo o que devia ser entidade: `cliente.servicos_feitos` (texto com uma lista) em vez de uma associação.
- Guardar dados repetidos: o nome do cliente em cada marcação.
- Esquecer que uma associação N:M tem atributos próprios: a nota de um aluno numa cadeira pertence à **inscrição**, não ao aluno nem à cadeira.
- Escolher como chave algo que muda (o email) ou que se repete (o nome).
