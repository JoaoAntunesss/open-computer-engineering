Uma tabela mal desenhada repete informação, e informação repetida acaba por ficar **inconsistente**: o cliente mudou de telefone, mas só se atualizou numa das 30 linhas onde aparece. A **normalização** é um método para dividir tabelas de forma a que cada facto fique guardado num único sítio. Assenta num conceito: a **dependência funcional**.

## O problema

```
marcacao_tudo(id, dia, cliente_nif, cliente_nome, cliente_tel, servico, preco)
1 | 02/11 | 111 | Ana | 912… | Corte     | 15
2 | 09/11 | 111 | Ana | 912… | Coloração | 45
3 | 03/11 | 222 | Eva | 935… | Corte     | 15
```

Anomalias:

- **De atualização:** mudar o telefone da Ana obriga a mudar várias linhas; esquecer uma deixa dados contraditórios.
- **De inserção:** não se consegue registar um serviço novo sem uma marcação.
- **De remoção:** apagar a única marcação da Eva apaga também os dados dela.

## Dependências funcionais

X → Y ("X determina Y") quando duas linhas com o mesmo X têm sempre o mesmo Y.

No exemplo:

- `id → dia, cliente_nif, servico` (a marcação determina tudo)
- `cliente_nif → cliente_nome, cliente_tel`
- `servico → preco`

As dependências vêm do **significado** dos dados (das regras do negócio), não de uma amostra: duas pessoas podem ter o mesmo nome, por isso `nome → nif` não é uma dependência, mesmo que na amostra pareça.

## As formas normais

- **1FN:** todos os valores são atómicos (sem listas dentro de uma célula, sem grupos repetidos `tel1, tel2, tel3`).
- **2FN:** 1FN, e nenhum atributo depende só de **parte** de uma chave composta. (Em `inscricao(aluno, cadeira, nome_aluno, nota)`, `nome_aluno` depende só de `aluno`: viola a 2FN.)
- **3FN:** 2FN, e nenhum atributo não-chave depende de outro atributo não-chave (sem dependências **transitivas**). No exemplo, `id → cliente_nif → cliente_nome`: viola a 3FN.
- **FNBC** (Boyce-Codd): para toda a dependência X → Y não trivial, X é uma superchave. Um pouco mais forte do que a 3FN; quase sempre coincidem.

## Normalizar o exemplo

Divide-se pelas dependências:

```
cliente(nif PK, nome, tel)
servico(nome PK, preco)
marcacao(id PK, dia, cliente_nif FK, servico FK)
```

Cada facto num só sítio. A decomposição deve ser:

- **sem perdas:** a junção das tabelas novas dá exatamente a original (garantido quando o atributo comum é chave de uma delas);
- **com preservação de dependências:** cada dependência pode ser verificada numa só tabela.

## Encontrar chaves: o fecho de atributos

O **fecho** X⁺ é o conjunto de atributos que X determina, aplicando as dependências até não crescer mais. Se X⁺ tem todos os atributos, X é uma superchave.

```python run
def fecho(atributos, dependencias):
    resultado = set(atributos)
    mudou = True
    while mudou:
        mudou = False
        for esquerda, direita in dependencias:
            if set(esquerda) <= resultado and not set(direita) <= resultado:
                resultado |= set(direita)
                mudou = True
    return resultado

todos = {"id", "dia", "nif", "nome", "tel", "servico", "preco"}
dfs = [({"id"}, {"dia", "nif", "servico"}),
       ({"nif"}, {"nome", "tel"}),
       ({"servico"}, {"preco"})]

for x in ({"id"}, {"nif"}, {"nif", "servico"}, {"nif", "dia", "servico"}):
    f = fecho(x, dfs)
    print(sorted(x), "->", sorted(f), "| superchave" if f == todos else "")
```

Prevê qual destes conjuntos é superchave antes de correr.

## Quando não normalizar

Em sistemas de análise (relatórios, *data warehouses*), desnormaliza-se de propósito para evitar junções caras, e os dados quase não mudam. E guardar valores históricos (o preço **cobrado** numa marcação) não é redundância: é outro facto.
