Uma **transação distribuída** altera dados em várias máquinas (ou vários serviços) e tem de ser **atómica**: ou todas as partes confirmam, ou nenhuma. Exemplo: uma marcação que reserva a hora (no serviço de agenda) e cobra o sinal (no serviço de pagamentos). Se uma parte falha, não pode ficar a hora reservada sem pagamento, nem o pagamento sem hora.

## Two-phase commit (2PC)

Um **coordenador** e vários **participantes**:

**Fase 1, preparar:** o coordenador pergunta a todos "consegues confirmar?". Cada participante faz o trabalho, guarda tudo em disco (para conseguir confirmar mesmo depois de uma falha), tranca os dados e responde **sim** ou **não**. Quem diz sim já não pode mudar de ideias.

**Fase 2, decidir:** se **todos** disseram sim, o coordenador grava "confirmar" no seu registo e manda confirmar; se algum disse não (ou não respondeu a tempo), manda anular.

```python run
import random

def two_phase_commit(participantes, falha_coordenador=False, semente=0):
    random.seed(semente)
    registo = []
    votos = {}
    for p, prob_sim in participantes.items():                # fase 1
        votos[p] = random.random() < prob_sim
        registo.append(f"{p} vota {'SIM (preparado, dados trancados)' if votos[p] else 'NÃO'}")
    decisao = "CONFIRMAR" if all(votos.values()) else "ANULAR"
    if falha_coordenador:
        registo.append("coordenador falha antes de enviar a decisão!")
        bloqueados = [p for p, v in votos.items() if v]
        registo.append(f"{', '.join(bloqueados) or 'ninguém'} fica(m) bloqueado(s) à espera, com os dados trancados")
        return registo
    registo.append(f"coordenador decide {decisao}")
    for p in participantes:                                  # fase 2
        registo.append(f"{p}: {decisao.lower()}")
    return registo

for titulo, args in [
    ("tudo corre bem", dict(participantes={"agenda": 1.0, "pagamentos": 1.0})),
    ("pagamento recusado", dict(participantes={"agenda": 1.0, "pagamentos": 0.0})),
    ("coordenador falha", dict(participantes={"agenda": 1.0, "pagamentos": 1.0}, falha_coordenador=True)),
]:
    print(f"--- {titulo}")
    print("\n".join(two_phase_commit(**args)))
```

Prevê o que acontece em cada caso.

## O problema do 2PC: bloqueio

Se o coordenador falha depois de os participantes votarem sim e antes de enviar a decisão, eles ficam **bloqueados**: não podem confirmar (talvez outro tenha votado não) nem anular (talvez o coordenador tenha decidido confirmar). Ficam com os dados trancados até o coordenador voltar. Soluções: replicar o coordenador com consenso (Raft/Paxos), como fazem o Spanner e o CockroachDB, ou o **three-phase commit** (que só funciona sem partições).

O 2PC também é lento (duas idas e voltas, trincos mantidos durante todo o processo) e acopla os serviços: se um está em baixo, nenhum confirma. Por isso é raro **entre** microsserviços.

## Sagas

A alternativa habitual entre serviços: uma sequência de **transações locais**, cada uma confirmada logo, com uma **ação de compensação** para desfazer se um passo seguinte falhar.

```
1. agenda: reservar a hora            (compensação: libertar a hora)
2. pagamentos: cobrar o sinal         (compensação: reembolsar)
3. notificações: enviar confirmação   (compensação: enviar "cancelado")
```

Se o passo 2 falha, executa-se a compensação do 1 (libertar a hora). Não há trincos entre serviços, mas também não há isolamento: durante uns segundos, a hora aparece reservada sem estar paga. A aplicação tem de aceitar esses estados intermédios (por exemplo, com um estado "pendente").

Duas formas de coordenar uma saga:

- **Orquestração:** um serviço (o orquestrador) diz a cada um o que fazer e trata das compensações. Mais fácil de seguir.
- **Coreografia:** cada serviço reage a eventos dos outros ("HoraReservada" → cobrar). Menos acoplado, mais difícil de perceber o fluxo completo.

Cuidados: as compensações têm de ser idempotentes e não podem falhar para sempre (repetem-se até resultar), e algumas ações não se desfazem (um email enviado): põem-se no fim.
