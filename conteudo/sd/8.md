O **teorema CAP** (Brewer, 2000; provado por Gilbert e Lynch, 2002) diz que um sistema distribuído com dados replicados não consegue ter, ao mesmo tempo, as três propriedades: **C**onsistência, **D**isponibilidade (*Availability*) e tolerância a **P**artições. Como as partições de rede acontecem (cabos cortados, routers avariados, centros de dados isolados), a escolha real é: **quando há uma partição, preferes consistência ou disponibilidade?**

## As três letras

- **C (consistência):** linearizável: todas as leituras veem a última escrita confirmada, como se houvesse uma só cópia.
- **A (disponibilidade):** todo o pedido a um nó que está vivo recebe uma resposta (não um erro).
- **P (tolerância a partições):** o sistema continua a funcionar mesmo que a rede entre nós perca mensagens.

## O argumento

Duas réplicas, R1 e R2, deixam de se ver. Um cliente escreve x = 2 em R1. Outro cliente lê x em R2.

- Se R2 responde com o valor que tem (x = 1): é **disponível** mas **não consistente**.
- Se R2 recusa responder até voltar a falar com R1: é **consistente** mas **não disponível**.

Não há uma terceira opção.

```python run
class Replica:
    def __init__(self, nome, modo):
        self.nome, self.modo, self.x, self.ligada_a = nome, modo, 1, None
    def escreve(self, valor):
        if self.modo == "CP" and self.ligada_a is None:
            return f"{self.nome}: ERRO (sem quórum durante a partição)"
        self.x = valor
        if self.ligada_a: self.ligada_a.x = valor        # replica, se houver ligação
        return f"{self.nome}: escrito x = {valor}"
    def le(self):
        if self.modo == "CP" and self.ligada_a is None:
            return f"{self.nome}: ERRO (não sei se o valor é o mais recente)"
        return f"{self.nome}: x = {self.x}"

for modo in ("CP", "AP"):
    r1, r2 = Replica("R1", modo), Replica("R2", modo)
    r1.ligada_a, r2.ligada_a = r2, r1
    print(f"--- sistema {modo}")
    print(r1.escreve(2), "|", r2.le())
    r1.ligada_a = r2.ligada_a = None                      # PARTIÇÃO
    print("(partição)")
    print(r1.escreve(3), "|", r2.le())
    print(r2.escreve(4), "|", r1.le())
```

Prevê as linhas de cada sistema. No sistema AP, depois da partição, R1 e R2 ficaram com valores diferentes de x: quando a rede voltar, é preciso **resolver o conflito** (lição 5). (Num sistema CP real, o lado com a maioria das réplicas continua a funcionar; aqui, com só duas, nenhum lado tem maioria.)

## CP e AP na prática

- **CP:** bases de dados com consenso (etcd, ZooKeeper, Spanner, CockroachDB), uma base de dados relacional com réplicas síncronas. Durante uma partição, o lado minoritário recusa pedidos. Para dinheiro, stock, trincos, configuração.
- **AP:** Cassandra, DynamoDB (por omissão), DNS, CouchDB, as caches. Respondem sempre, com consistência eventual. Para carrinhos de compras, contadores, perfis, catálogos.

Muitos sistemas deixam escolher por operação: o DynamoDB e o MongoDB têm leituras "fortemente consistentes" (mais lentas) e "eventualmente consistentes".

## PACELC: e quando não há partição?

O CAP só fala do momento da partição, que é raro. O **PACELC** (Abadi) completa: se há **P**artição, escolhe entre **A** e **C**; **E**lse (no funcionamento normal), escolhe entre **L**atência e **C**onsistência. Mesmo sem falhas, a consistência forte custa idas e voltas entre réplicas (às vezes entre continentes). O Cassandra é PA/EL; o Spanner é PC/EC.

## Mal-entendidos comuns

- "Escolher 2 de 3": não se pode escolher "CA" num sistema distribuído, porque as partições não se escolhem: acontecem.
- O C do CAP não é o C do ACID (que é cumprir as restrições de integridade).
- Disponibilidade no CAP é uma definição teórica (todos os nós respondem); disponibilidade na prática (99,9% do tempo) é outra coisa.
