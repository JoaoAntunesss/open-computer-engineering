Um **sistema distribuído** é um conjunto de computadores que comunicam por rede e trabalham juntos como se fossem um só: o Gmail, o Firebase, uma loja online com vários servidores, o próprio DNS. Distribuir dá escala e tolerância a falhas, mas traz problemas que não existem num único computador: mensagens que se perdem, relógios que não concordam, máquinas que falham a meio. O primeiro passo é dizer, com precisão, **o que pode correr mal**: o modelo do sistema.

## As falácias da computação distribuída

Pressupostos falsos que quase toda a gente faz no início (Peter Deutsch e outros, Sun, anos 90):

1. A rede é fiável.
2. A latência é zero.
3. A largura de banda é infinita.
4. A rede é segura.
5. A topologia não muda.
6. Há um único administrador.
7. O custo de transporte é zero.
8. A rede é homogénea.

Cada uma já causou falhas reais. Um bom desenho assume o contrário de todas.

## Modelos de tempo

- **Síncrono:** há limites conhecidos para o atraso das mensagens e a velocidade de processamento. Se uma resposta não chega a tempo, a máquina falhou.
- **Assíncrono:** não há limites: uma mensagem pode demorar o tempo que for. **Não se distingue uma máquina lenta de uma que morreu.**
- **Parcialmente síncrono:** quase sempre se comporta como síncrono, mas há períodos de caos. É o modelo realista, e o que os algoritmos práticos (Raft, Paxos) assumem.

## Modelos de falhas

Do mais simples ao mais difícil:

- **Paragem** (*crash-stop*): a máquina para e nunca mais volta.
- **Paragem e recuperação** (*crash-recovery*): para e volta mais tarde, possivelmente sem o que tinha em memória (só com o que guardou em disco).
- **Omissão:** perde algumas mensagens (enviadas ou recebidas).
- **Bizantina:** comporta-se de forma arbitrária: mente, envia mensagens contraditórias (um bug, um ataque, hardware avariado). Tolerá-las exige muito mais réplicas (3f + 1 para f falhas, contra 2f + 1). As blockchains são sistemas tolerantes a falhas bizantinas.

E a rede: mensagens **perdidas**, **atrasadas**, **duplicadas**, **reordenadas**; e **partições** (dois grupos de máquinas que deixam de se ver).

## Simular a incerteza

Um cliente envia um pedido e espera 100 ms pela resposta. Do lado do cliente, prevê o que se consegue distinguir:

```python run
import random
random.seed(4)

def pedido(prob_perda=0.1, prob_crash=0.05, atraso_medio=40):
    if random.random() < prob_perda:
        return "pedido perdido na rede", None
    if random.random() < prob_crash:
        return "servidor falhou antes de processar", None
    atraso = random.expovariate(1 / atraso_medio)          # às vezes muito lento
    processado = True                                       # a operação foi feita!
    if random.random() < prob_perda:
        return "resposta perdida (mas a operação foi feita)", None
    return "ok", atraso

resultados = {}
for _ in range(10_000):
    causa, atraso = pedido()
    visto = "resposta a tempo" if atraso is not None and atraso <= 100 else "timeout"
    if causa == "ok" and atraso > 100:
        causa = "servidor lento (a operação foi feita)"
    resultados.setdefault(visto, {}).setdefault(causa, 0)
    resultados[visto][causa] += 1

for visto, causas in resultados.items():
    print(visto)
    for c, n in sorted(causas.items(), key=lambda x: -x[1]):
        print(f"   {n:5}  {c}")
```

Prevê: quando o cliente vê "timeout", sabe se a operação foi feita? Esta incerteza é a origem de quase todos os problemas da cadeira, e a razão para as operações **idempotentes** (que se podem repetir sem efeito extra) que viste na lição de leitura de código.

## Objetivos e compromissos

- **Escalabilidade:** aguentar mais carga acrescentando máquinas.
- **Disponibilidade:** continuar a responder com falhas.
- **Consistência:** todos veem os mesmos dados.
- **Latência:** responder depressa.

Não se conseguem todos ao mesmo tempo (teorema CAP, lição 8). Cada sistema escolhe.
