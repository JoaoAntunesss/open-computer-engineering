O **consenso** é o problema central dos sistemas distribuídos: pôr várias máquinas a **concordar num valor** (quem é o líder, qual é a próxima operação no registo), mesmo com algumas a falhar e com mensagens atrasadas. Com consenso, constrói-se uma **máquina de estados replicada**: todas as réplicas aplicam as mesmas operações pela mesma ordem, e comportam-se como uma só. É o que está dentro do etcd (Kubernetes), do ZooKeeper, do Consul, do CockroachDB e do Spanner.

## O que se exige

- **Acordo:** todos os processos corretos decidem o mesmo valor.
- **Validade:** o valor decidido foi proposto por alguém.
- **Terminação:** todos os processos corretos acabam por decidir.

**Resultado FLP (1985):** num sistema totalmente assíncrono, com a possibilidade de um único processo falhar, **nenhum** algoritmo garante as três. Na prática, contorna-se assumindo sincronia parcial: os algoritmos são sempre seguros (nunca decidem coisas diferentes) e terminam quando a rede se porta bem durante tempo suficiente.

## Paxos

Lamport (1989). Correto, mas famoso por ser difícil de perceber. Em resumo, um proponente:

1. **Preparar:** escolhe um número de proposta n e pede a uma **maioria** de aceitadores que prometam ignorar propostas com número menor. Eles respondem com o valor que já tenham aceitado (se houver).
2. **Aceitar:** se uma maioria prometeu, propõe um valor (o de número mais alto que recebeu, ou o seu, se não houver) e pede a uma maioria que o aceite.

Como duas maiorias se cruzam sempre em pelo menos um processo, um valor que já foi aceite por uma maioria nunca é contrariado.

## Raft

Desenhado em 2014 para ser **compreensível**, com as mesmas garantias. Três papéis: **líder**, **seguidor**, **candidato**.

1. **Eleição:** o tempo divide-se em **mandatos** (*terms*) numerados. Se um seguidor não ouve o líder durante um tempo aleatório (150–300 ms), passa a candidato, incrementa o mandato e pede votos. Cada servidor vota em no máximo um candidato por mandato. Quem recebe votos de uma **maioria** é líder.
2. **Replicação do registo:** os clientes enviam comandos ao líder, que os acrescenta ao seu registo e os envia aos seguidores. Quando uma **maioria** os guardou, a entrada fica **confirmada** (*committed*) e é aplicada à máquina de estados.
3. **Segurança:** um candidato só ganha se o seu registo estiver pelo menos tão atualizado como o dos que votam nele. Assim, um líder novo tem sempre todas as entradas confirmadas.

```python run
import random

def eleicao(n=5, mortos=(), semente=0):
    random.seed(semente)
    vivos = [i for i in range(n) if i not in mortos]
    timeouts = {i: random.uniform(150, 300) for i in vivos}      # tempo aleatório de espera
    mandato = 1
    for candidato in sorted(vivos, key=timeouts.get):            # o primeiro a esgotar o tempo
        votos = 1                                                 # vota em si próprio
        for outro in vivos:
            if outro != candidato:
                votos += 1                                        # ninguém votou ainda neste mandato
        if votos > n // 2:
            return f"servidor {candidato} é líder no mandato {mandato} com {votos}/{n} votos " \
                   f"(esperou {timeouts[candidato]:.0f} ms)"
        mandato += 1
    return f"sem líder: só {len(vivos)} de {n} vivos, não há maioria"

def confirma(n, guardaram):
    return "confirmada" if guardaram > n // 2 else "à espera (sem maioria)"

print(eleicao())
print(eleicao(mortos=(0, 1)))
print(eleicao(mortos=(0, 1, 2)))
for guardaram in (2, 3, 5):
    print(f"entrada guardada em {guardaram} de 5 servidores: {confirma(5, guardaram)}")
```

Prevê: com 2 de 5 servidores em baixo, ainda há líder? E com 3? O tempo de espera **aleatório** é o que evita que todos se candidatem ao mesmo tempo e dividam os votos.

## Uma partição

Com 5 servidores divididos em {A, B} e {C, D, E}: o lado com 3 elege (ou mantém) um líder e continua a confirmar escritas; o lado com 2 não consegue maioria e fica parado (recusa escritas). Quando a rede volta, o antigo líder isolado vê um mandato maior, passa a seguidor e descarta as entradas que não chegaram a ser confirmadas. Nunca há dois líderes a confirmar escritas contraditórias.

## O custo

Cada escrita precisa de uma ida e volta a uma maioria: com servidores em continentes diferentes, dezenas ou centenas de milissegundos. Por isso o consenso usa-se para o que precisa mesmo de acordo forte (metadados, configuração, trincos, o registo de transações), e não para cada gosto num vídeo.
