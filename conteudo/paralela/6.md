Uma estrutura de dados partilhada por várias threads (uma fila de tarefas, uma tabela de dispersão, um contador) tem de continuar correta quando muitas lhe mexem ao mesmo tempo, e não pode tornar-se o gargalo. A solução simples é um trinco à volta de tudo; as soluções escaláveis usam trincos mais finos ou **operações atómicas**, sem trincos nenhuns (*lock-free*).

## O problema do trinco global

Com um trinco à volta da estrutura inteira, a correção é fácil, mas as threads fazem fila: com 32 núcleos, 31 ficam à espera. Alternativas, da mais simples à mais difícil:

1. **Trincos finos:** um trinco por balde de uma tabela de dispersão, ou por nó de uma lista. Mais paralelismo, mais cuidado com interbloqueios (ordem de aquisição).
2. **Trincos de leitura-escrita:** várias leituras ao mesmo tempo, escritas exclusivas. Bons quando se lê muito mais do que se escreve.
3. **Lock-free:** operações atómicas, sem trincos. Uma thread lenta (ou suspensa) nunca bloqueia as outras.
4. **Evitar a partilha:** dados por thread, juntos no fim (como o `reduction` do OpenMP), ou passagem de mensagens.

## Compare-and-swap

A peça base das estruturas sem trincos é uma instrução atómica do processador:

**CAS(endereço, esperado, novo):** se o valor no endereço é `esperado`, troca por `novo` e devolve sucesso; senão, não faz nada e devolve falha. Tudo numa só operação indivisível.

Incrementar um contador sem trinco:

```c
do {
    antigo = contador;                                // lê
} while (!CAS(&contador, antigo, antigo + 1));        // se alguém mudou entretanto, tenta outra vez
```

Em C11: `atomic_fetch_add`, `atomic_compare_exchange_weak`; em Java: `AtomicInteger`, `ConcurrentHashMap`; em Rust: `std::sync::atomic`.

## Simular o CAS com intercalações

As threads Python não correm em paralelo verdadeiro (por causa do GIL, e no browser nem existem), por isso esta simulação intercala "à mão" os passos de várias threads, numa ordem aleatória, como faria um escalonador:

```python run
import random

def simula(algoritmo, threads=4, incrementos=50, semente=0):
    random.seed(semente)
    memoria = {"contador": 0}
    tentativas_falhadas = 0

    def thread_sem_protecao():
        for _ in range(incrementos):
            valor = memoria["contador"]; yield          # lê ... (pode ser interrompida aqui)
            memoria["contador"] = valor + 1; yield       # ... e escreve

    def thread_cas():
        nonlocal tentativas_falhadas
        for _ in range(incrementos):
            while True:
                antigo = memoria["contador"]; yield
                if memoria["contador"] == antigo:       # CAS: compara e troca numa só operação
                    memoria["contador"] = antigo + 1; yield
                    break
                tentativas_falhadas += 1; yield          # alguém mudou: tenta de novo

    ativas = [(thread_cas if algoritmo == "cas" else thread_sem_protecao)() for _ in range(threads)]
    while ativas:
        t = random.choice(ativas)                        # o escalonador escolhe uma thread ao acaso
        try:
            next(t)
        except StopIteration:
            ativas.remove(t)
    return memoria["contador"], tentativas_falhadas

esperado = 4 * 50
for alg in ("sem proteção", "cas"):
    valor, falhas = simula(alg)
    print(f"{alg:13}: contador = {valor} (esperado {esperado}); tentativas repetidas: {falhas}")
```

Prevê os dois resultados. Sem proteção, perdem-se incrementos (duas threads leem o mesmo valor). Com CAS, a escrita só acontece se ninguém tiver mudado o valor desde a leitura; senão, repete-se.

## O problema ABA

O CAS só verifica se o **valor** é o mesmo, não se **ninguém lhe mexeu**: uma thread lê A; outra muda para B e de volta para A; o CAS da primeira sucede, embora a estrutura tenha mudado (numa pilha sem trincos, um nó pode ter sido retirado, libertado e reutilizado). Soluções: contadores de versão junto ao apontador, *hazard pointers*, recolha de memória por épocas, ou uma linguagem com coletor de lixo.

## Garantias de progresso

- **Com bloqueio** (trincos): uma thread suspensa a segurar o trinco para todas.
- **Lock-free:** em cada momento, **alguma** thread progride (o sistema como um todo avança), mas uma thread pode ter azar repetidamente.
- **Wait-free:** **todas** as threads acabam em número limitado de passos. A garantia mais forte, e a mais difícil.

## Na prática

Escrever estruturas sem trincos corretas é muito difícil (e os erros só aparecem em produção, uma vez por semana). Usa as das bibliotecas: `java.util.concurrent`, `std::atomic` e as bibliotecas de C++ (folly, TBB), `crossbeam` em Rust, `queue.Queue` em Python, os canais de Go. Começa sempre com a solução simples (um trinco), mede, e só complica onde a medição mostrar contenção.
