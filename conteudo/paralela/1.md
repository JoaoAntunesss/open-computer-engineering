Computação paralela é usar vários núcleos, processadores ou máquinas ao mesmo tempo para resolver um problema mais depressa (ou um problema maior no mesmo tempo). Antes de paralelizar, é preciso saber **medir**: quanto se ganha, onde está o tempo, e quais são os limites teóricos. Sem medições, a otimização é um palpite.

## Métricas

- **Ganho** (*speedup*) com p processadores: S(p) = T(1) / T(p).
- **Eficiência:** E(p) = S(p) / p. 100% quer dizer que cada processador foi totalmente aproveitado.
- **Escalabilidade forte:** o mesmo problema, mais processadores; quanto desce o tempo?
- **Escalabilidade fraca:** o problema cresce com os processadores (o dobro dos dados para o dobro dos núcleos); o tempo mantém-se?

## Lei de Amdahl

Se uma fração f do programa é sequencial (não se paraleliza), o ganho máximo é

S(p) = 1 / (f + (1 − f)/p)  →  1/f quando p → ∞

Com 5% sequencial, nunca se passa de 20 vezes mais rápido, nem com um milhão de núcleos.

## Lei de Gustafson

Amdahl assume o problema fixo. Na prática, com mais processadores resolve-se um problema **maior** (mais resolução numa simulação, mais dados), e a parte sequencial pesa cada vez menos:

S(p) = p − f·(p − 1)

As duas leis não se contradizem: respondem a perguntas diferentes (escalabilidade forte e fraca).

```python run
def amdahl(f, p): return 1 / (f + (1 - f) / p)
def gustafson(f, p): return p - f * (p - 1)

print(f"{'p':>5} | {'Amdahl f=5%':>12} {'eficiência':>10} | {'Gustafson f=5%':>14}")
for p in (1, 2, 4, 8, 16, 64, 256, 1024):
    s = amdahl(0.05, p)
    print(f"{p:5} | {s:12.2f} {s / p:10.0%} | {gustafson(0.05, p):14.1f}")

# medições reais de um programa (segundos): onde está a fração sequencial?
medido = {1: 120.0, 2: 63.0, 4: 34.5, 8: 20.4, 16: 13.2}
for p, t in list(medido.items())[1:]:
    s = medido[1] / t
    f = (p / s - 1) / (p - 1)                                 # inverter Amdahl: fração sequencial estimada
    print(f"p = {p:2}: ganho {s:5.2f}, eficiência {s / p:4.0%}, fração sequencial estimada {f:.1%}")
```

Prevê o ganho máximo com f = 5%. Na segunda parte, a fração sequencial **estimada** a partir das medições cresce com p (métrica de Karp-Flatt): é o sinal de custos que aumentam com o número de processadores (comunicação, sincronização, desequilíbrio de carga).

## Medir bem

- **Tempo de relógio** (*wall-clock*), não tempo de CPU: com 8 threads, o tempo de CPU soma o de todas.
- Repetir várias vezes, descartar a primeira (aquecimento: caches, JIT), reportar a mediana e a dispersão.
- Computador "calmo": sem outros programas, frequência fixa, mesma máquina para todas as medições.
- **Perfilar antes de otimizar:** `perf` (Linux), `gprof`, `py-spy`, VTune. A regra 90/10: quase todo o tempo está numa pequena parte do código.
- Verificar o resultado: uma versão paralela rápida e errada não serve (condições de corrida, Sistemas Operativos, lição 4).

## Porque é que o ganho fica abaixo do ideal

- Parte sequencial (Amdahl).
- **Comunicação e sincronização:** trincos, barreiras, troca de mensagens.
- **Desequilíbrio de carga:** um processador fica com mais trabalho e os outros esperam.
- **Memória:** a largura de banda da memória é partilhada; muitos núcleos competem por ela. Falsa partilha nas caches (lição 7).
- Custo de criar e coordenar threads ou processos.

Às vezes há ganho **superlinear** (S(p) > p): ao dividir os dados, cada parte passa a caber na cache.
