As instruções **SIMD** (*Single Instruction, Multiple Data*) fazem a mesma operação sobre vários valores de uma vez: com AVX2, 8 somas de `float` numa só instrução; com AVX-512, 16. Estão em todos os processadores modernos (SSE e AVX no x86, NEON e SVE no ARM, a extensão V no RISC-V). Usá-las bem pode dar 4 a 16 vezes mais velocidade num só núcleo, antes de qualquer thread.

## Três formas de usar SIMD

1. **Vetorização automática:** o compilador transforma ciclos simples em instruções SIMD (`-O3 -march=native` no GCC e no Clang). É a forma preferida.
2. **Intrínsecos:** funções em C que correspondem a instruções (`_mm256_add_ps`). Controlo total, código específico de cada arquitetura.
3. **Bibliotecas que já são vetorizadas:** NumPy, BLAS, Eigen. Em Python, a forma de usar SIMD é **não escrever ciclos**.

## Ajudar o compilador

Um ciclo vetoriza-se automaticamente se:

- as iterações forem **independentes** (sem `a[i] = a[i-1] + …`);
- não houver **aliasing** possível (dois apontadores que podem apontar para a mesma memória): em C, `restrict` promete que não;
- o corpo for simples: sem chamadas a funções desconhecidas, sem saltos imprevisíveis (um `if` simples vira uma seleção sem salto);
- os dados estiverem **contíguos** em memória.

```c
// vetoriza bem
void escala(float *restrict y, const float *restrict x, float a, int n) {
    for (int i = 0; i < n; i++) y[i] = a * x[i] + y[i];
}
```

Para ver o que o compilador fez: `gcc -O3 -march=native -fopt-info-vec-optimized`, ou o Compiler Explorer.

## Estrutura de vetores contra vetor de estruturas

A forma de guardar os dados decide se o SIMD é possível:

```c
struct Particula { float x, y, z, massa; };    // AoS: array of structures
struct Particula ps[N];                         // x, y, z, massa, x, y, z, massa, …

struct Particulas { float x[N], y[N], z[N], massa[N]; };   // SoA: structure of arrays
// x, x, x, …, y, y, y, …  → 8 x seguidos carregam-se numa instrução
```

Para atualizar todas as posições x, a versão SoA lê memória contígua e vetoriza; a AoS salta de 16 em 16 bytes. É uma escolha de desenho de dados que os motores de jogos (ECS) e as bases de dados colunares fazem pelo mesmo motivo.

## Ver o efeito

O NumPy executa as operações em código C vetorizado; um ciclo em Python faz uma operação de cada vez, com o custo do interpretador. Prevê a diferença, e repara no efeito da disposição dos dados:

```python run
import time
import numpy as np

n = 2_000_000
x = np.random.rand(n).astype(np.float32)
y = np.random.rand(n).astype(np.float32)

def mede(f, repeticoes=3):
    melhor = float("inf")
    for _ in range(repeticoes):
        t = time.perf_counter(); f(); melhor = min(melhor, time.perf_counter() - t)
    return melhor * 1000

t_ciclo = mede(lambda: [2.0 * x[i] + y[i] for i in range(200_000)]) * (n / 200_000)   # estimado para n
t_numpy = mede(lambda: 2.0 * x + y)
print(f"ciclo Python (estimado): {t_ciclo:8.1f} ms")
print(f"NumPy vetorizado:        {t_numpy:8.2f} ms   ({t_ciclo / t_numpy:.0f}× mais rápido)")

# AoS contra SoA: somar a coordenada x de todas as partículas
aos = np.random.rand(n, 4).astype(np.float32)          # cada linha: x, y, z, massa (AoS)
soa_x = np.ascontiguousarray(aos[:, 0])                 # só os x, contíguos (SoA)
print(f"soma dos x em AoS (com saltos): {mede(lambda: aos[:, 0].sum()):.2f} ms")
print(f"soma dos x em SoA (contíguos):  {mede(lambda: soa_x.sum()):.2f} ms")
```

## Limites

- **Lei de Amdahl, outra vez:** só as partes vetorizáveis ganham.
- **Largura de banda da memória:** se o ciclo faz pouco cálculo por cada byte lido (como `2x + y`), fica limitado pela memória, e o SIMD ajuda pouco a partir de certo ponto (modelo *roofline*).
- Com instruções muito largas (AVX-512), alguns processadores baixam a frequência.
- Portabilidade: código com intrínsecos de x86 não corre em ARM (os Mac recentes, os telemóveis). Bibliotecas como o Highway (Google) ou o `std::simd` (C++) escondem isto.
