Cada núcleo tem as suas caches. Quando vários núcleos leem e escrevem os mesmos dados, o hardware tem de garantir que ninguém fica a ler uma cópia desatualizada (**coerência**), e define regras sobre a ordem em que as escritas de um núcleo se tornam visíveis aos outros (**modelo de memória**). Estes dois temas explicam erros de concorrência "impossíveis" e quedas de desempenho misteriosas.

## Coerência: o protocolo MESI

Cada linha de cache (64 bytes) está num de quatro estados:

- **M** (modificada): só esta cache a tem, e foi alterada (a memória está desatualizada).
- **E** (exclusiva): só esta cache a tem, igual à memória.
- **S** (partilhada): várias caches têm cópias iguais.
- **I** (inválida).

Para escrever, um núcleo precisa da linha em M: as cópias nos outros núcleos são **invalidadas**. Se outro núcleo voltar a ler, tem de ir buscar a linha (a quem a tem em M). Cada escrita numa linha partilhada custa tráfego entre núcleos.

## Falsa partilha

Duas threads escrevem em variáveis **diferentes** que estão na **mesma linha de cache**. Para o hardware, é a mesma linha: cada escrita invalida a cópia do outro núcleo, e a linha salta de um lado para o outro. O programa está correto, mas pode ficar 10 vezes mais lento.

```python run
LINHA = 64

def invalidacoes(enderecos_por_thread, escritas=1000):
    # cada thread escreve alternadamente no seu endereço; conta quantas vezes a linha muda de dono
    dono = {}
    trocas = 0
    for _ in range(escritas):
        for t, end in enumerate(enderecos_por_thread):
            linha = end // LINHA
            if dono.get(linha, t) != t:
                trocas += 1                         # a linha estava noutro núcleo: invalida e transfere
            dono[linha] = t
    return trocas

contadores_juntos = [0, 8, 16, 24]                  # 4 contadores de 8 bytes seguidos: mesma linha
contadores_afastados = [0, 64, 128, 192]            # um por linha (com "padding")
print("contadores na mesma linha:   ", invalidacoes(contadores_juntos), "transferências de linha")
print("contadores em linhas separadas:", invalidacoes(contadores_afastados), "transferências de linha")
```

Prevê os dois números. A correção é **afastar** os dados escritos por threads diferentes (`alignas(64)` em C++, `@Contended` em Java, ou acrescentar *padding*), ou dar a cada thread a sua cópia e juntar no fim.

## Modelos de memória

Os processadores e os compiladores **reordenam** operações para ir mais depressa (buffers de escrita, execução fora de ordem, otimizações). Numa só thread, nunca se nota. Entre threads, sim:

```c
// inicialmente: dados = 0, pronto = 0
// thread 1                 // thread 2
dados = 42;                 while (pronto == 0) { }
pronto = 1;                 printf("%d", dados);    // pode mostrar 0!
```

Sem sincronização, a thread 2 pode ver `pronto = 1` antes de ver `dados = 42` (o compilador ou o processador trocaram a ordem, ou o `while` foi otimizado para um ciclo infinito porque `pronto` "nunca muda" dentro dele).

- O **x86** é relativamente forte (TSO: só as leituras podem passar à frente de escritas anteriores). O **ARM** e o **RISC-V** são fracos: quase tudo pode ser reordenado. Código que "funciona" no PC pode falhar num Mac M ou num telemóvel.
- As linguagens definem um modelo de memória (C11/C++11, Java, Rust, Go): um programa **sem condições de corrida nos dados** comporta-se como se fosse sequencialmente consistente.
- A correção é usar sincronização: trincos, ou **atómicos** com a ordem certa (`memory_order_release` na escrita de `pronto` e `memory_order_acquire` na leitura): tudo o que foi escrito antes da libertação fica visível depois da aquisição.

## Regras práticas

- Nunca partilhar variáveis entre threads sem sincronização (`volatile` em C **não** chega; em Java, `volatile` sim, por definição).
- Preferir abstrações de alto nível (filas, futuros, canais) que já tratam disto.
- Para desempenho: agrupar os dados de cada thread, evitar escritas frequentes em dados partilhados, cuidado com a falsa partilha.
- Testar em ARM, e com ferramentas como o **ThreadSanitizer** (`-fsanitize=thread`).
