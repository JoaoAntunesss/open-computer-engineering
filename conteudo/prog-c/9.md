Em C, um erro raramente se anuncia com uma mensagem clara. O mais comum é "Segmentation fault (core dumped)", um resultado errado de vez em quando, ou um programa que funciona no teu computador e falha no do professor. Esta lição mostra as três ferramentas que transformam essas falhas em informação precisa: os **sanitizers**, o **gdb** e o **Valgrind**.

## Um programa com erros

```c
// bugs.c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int soma(const int *v, int n) {
    int s = 0;
    for (int i = 0; i <= n; i++) s += v[i];     // erro 1: <= em vez de <
    return s;
}

int main(void) {
    int *v = malloc(5 * sizeof *v);
    for (int i = 0; i < 5; i++) v[i] = i + 1;
    printf("soma = %d\n", soma(v, 5));
    char *nome = malloc(4);
    strcpy(nome, "Ana");
    nome = malloc(10);                            // erro 2: o primeiro bloco perdeu-se (fuga)
    free(v);
    free(nome);
    return 0;
}
```

Compilado normalmente, provavelmente imprime um número e termina "bem". Os erros estão lá, escondidos.

## 1. Sanitizers: o primeiro passo

O compilador pode instrumentar o programa para detetar erros enquanto ele corre:

```bash
gcc -g -O0 -fsanitize=address,undefined -o bugs bugs.c
./bugs
```

O **AddressSanitizer** (ASan) para no primeiro acesso inválido e mostra:

- o tipo de erro (**heap-buffer-overflow**, ao ler 4 bytes logo a seguir a um bloco de 20);
- a pilha de chamadas, com ficheiro e linha (`soma` em `bugs.c:8`, chamada de `main`);
- onde o bloco foi alocado (o `malloc` em `main`).

O ASan para no primeiro erro. Depois de o corrigires e voltares a correr, é o **LeakSanitizer** (incluído no ASan em Linux) que reporta as fugas quando o programa termina: "4 byte(s) leaked in 1 allocation(s)". O `undefined` (UBSan) apanha overflow de inteiros com sinal, deslocamentos inválidos, divisões por zero e mais.

Corrigido o `<=` e acrescentado `free(nome)` antes do segundo `malloc`, o programa corre limpo.

**Usa sempre os sanitizers durante o desenvolvimento.** O custo (o programa fica 2 a 3 vezes mais lento) é pequeno comparado com o tempo que poupam.

## 2. Valgrind

O Valgrind executa o programa numa máquina virtual que vigia cada acesso à memória. Não precisa de recompilar com opções especiais (mas `-g` dá números de linha):

```bash
gcc -g -O0 -o bugs bugs.c
valgrind --leak-check=full --show-leak-kinds=all ./bugs
```

Mostra "Invalid read of size 4" com a linha, e no fim um resumo:

```text
LEAK SUMMARY:
   definitely lost: 4 bytes in 1 blocks
   indirectly lost: 0 bytes in 0 blocks
ERROR SUMMARY: 2 errors from 2 contexts
```

- **definitely lost**: memória sem nenhum apontador para ela — uma fuga certa.
- **indirectly lost**: memória só acessível através de blocos perdidos (por exemplo, os nós de uma lista cuja cabeça se perdeu).
- **still reachable**: ainda apontada no fim; muitas vezes inofensiva, mas convém libertar.

O Valgrind também deteta o uso de valores **não inicializados** ("Conditional jump depends on uninitialised value"), que o ASan não apanha. É mais lento (20 a 50 vezes), e ASan e Valgrind não se usam ao mesmo tempo.

## 3. gdb: parar e inspecionar

O **gdb** deixa-te parar o programa numa linha, executar passo a passo e ver o valor das variáveis.

```bash
gcc -g -O0 -o bugs bugs.c
gdb ./bugs
```

Comandos essenciais:

- `break soma` ou `break bugs.c:8` — põe um ponto de paragem;
- `run` (com argumentos: `run a b c`) — arranca o programa;
- `next` (`n`) — executa a linha atual sem entrar nas funções;
- `step` (`s`) — entra na função chamada;
- `print i`, `print v[i]`, `print *v@5` — mostra valores (o último mostra 5 elementos a partir de `v`);
- `display s` — mostra `s` a cada passo;
- `backtrace` (`bt`) — a pilha de chamadas, essencial depois de um "Segmentation fault";
- `watch s` — para sempre que `s` muda;
- `continue` (`c`), `finish` (até sair da função), `quit`.

Numa falha de segmentação, basta `run` e depois `bt`: vês a função e a linha onde o programa morreu, e com `frame 1` e `print` inspecionas as variáveis de quem a chamou.

O VS Code e o CLion usam o gdb por baixo, com pontos de paragem clicando ao lado do número da linha.

## Um método de depuração

1. **Reproduz** o erro de forma fiável, com o caso mais pequeno possível.
2. **Lê a mensagem** inteira — a linha e a pilha de chamadas.
3. **Forma uma hipótese** ("o ciclo vai um elemento longe demais") e testa-a com o gdb ou com um `printf` bem colocado.
4. **Corrige a causa**, não o sintoma.
5. **Acrescenta um teste** que teria apanhado o erro.

## Erros comuns

- Depurar código compilado com `-O2`: as variáveis "desaparecem" e as linhas saltam. Usa `-O0 -g`.
- Ignorar o primeiro erro do ASan ou do Valgrind e olhar para os seguintes: os outros são muitas vezes consequência do primeiro.
- Encher o código de `printf` sem `\n` ou sem `fflush` e não ver nada antes da falha.
- Achar que "se não deu erro, não tem erros": comportamento indefinido pode não se manifestar em todas as execuções.
