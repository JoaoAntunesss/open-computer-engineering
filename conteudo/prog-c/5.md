Até aqui, todos os vetores tinham um tamanho conhecido ao compilar. Mas e se o utilizador escolher quantos números quer guardar, ou se uma lista crescer sem limite? Para isso pede-se memória ao sistema **durante a execução**, com `malloc`, e devolve-se com `free`. Em C não há recolha de lixo: a responsabilidade é tua.

## Pilha e heap

Um programa em execução tem várias zonas de memória:

- **Pilha** (*stack*): variáveis locais e parâmetros. Criadas ao entrar numa função e destruídas ao sair, automaticamente. É rápida mas pequena (tipicamente 8 MB em Linux).
- **Heap**: memória pedida explicitamente. Existe até ser libertada, e pode ser muito grande.
- **Dados estáticos**: variáveis globais e `static`, que existem durante todo o programa.

## malloc, calloc, realloc e free

```c
// dinamica.c
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    int n = 5;
    int *v = malloc(n * sizeof *v);       // n inteiros, por inicializar
    if (v == NULL) { perror("malloc"); return 1; }
    for (int i = 0; i < n; i++) v[i] = i * i;

    int *maior = realloc(v, 2 * n * sizeof *v);   // aumenta para 10
    if (maior == NULL) { free(v); return 1; }     // se falhar, v continua válido
    v = maior;
    for (int i = n; i < 2 * n; i++) v[i] = -i;

    for (int i = 0; i < 2 * n; i++) printf("%d ", v[i]);
    printf("\n");
    free(v);                               // devolve a memória
    v = NULL;                              // evita usar um apontador "pendurado"
    return 0;
}
```

- `malloc(bytes)` devolve um `void *` para um bloco **não inicializado**, ou `NULL` se falhar.
- `calloc(n, tamanho)` faz o mesmo mas põe tudo a zero (e verifica overflow na multiplicação).
- `realloc(p, bytes)` muda o tamanho de um bloco; pode **mover** os dados para outro sítio e devolve o novo endereço.
- `free(p)` liberta. `free(NULL)` não faz nada.
- Escrever `sizeof *v` em vez de `sizeof(int)` evita erros se mudares o tipo de `v`.

## Um vetor que cresce

É exatamente assim que funcionam as listas do Python e o `std::vector` do C++: quando enchem, **duplicam** a capacidade. Cada inserção custa, em média, tempo constante.

```c
// vetor_dinamico.c
#include <stdio.h>
#include <stdlib.h>

typedef struct { int *dados; size_t n, cap; } Vetor;

int vetor_push(Vetor *v, int x) {
    if (v->n == v->cap) {
        size_t nova = v->cap ? v->cap * 2 : 4;
        int *p = realloc(v->dados, nova * sizeof *p);
        if (!p) return 0;
        v->dados = p;
        v->cap = nova;
    }
    v->dados[v->n++] = x;
    return 1;
}

void vetor_liberta(Vetor *v) { free(v->dados); v->dados = NULL; v->n = v->cap = 0; }

int main(void) {
    Vetor v = {0};
    for (int i = 0; i < 1000; i++) if (!vetor_push(&v, i)) return 1;
    printf("n = %zu, capacidade = %zu, último = %d\n", v.n, v.cap, v.dados[v.n - 1]);   // 1000, 1024, 999
    vetor_liberta(&v);
    return 0;
}
```

## Os quatro erros clássicos

1. **Fuga de memória** (*memory leak*): perder o último apontador para um bloco sem o libertar. Num programa que corre muito tempo (um servidor), a memória usada cresce até o sistema o matar.
2. **Usar depois de libertar** (*use after free*): `free(p); printf("%d", *p);` — o bloco pode já pertencer a outra coisa.
3. **Libertar duas vezes** (*double free*): corrompe as estruturas internas do alocador.
4. **Escrever fora do bloco** (*heap overflow*): `malloc(10)` e escrever 11 bytes.

Os três últimos são **comportamento indefinido**: o programa pode funcionar, falhar logo, ou falhar muito mais tarde, noutro sítio. Estão na origem de uma grande parte das vulnerabilidades de segurança em software escrito em C e C++.

## Encontrar erros de memória

Duas ferramentas indispensáveis (mais detalhes na lição 9):

```bash
gcc -g -fsanitize=address,undefined -o prog prog.c && ./prog     # AddressSanitizer
gcc -g -o prog prog.c && valgrind --leak-check=full ./prog       # Valgrind
```

Ambas dizem a linha exata onde o erro aconteceu e onde o bloco foi alocado.

## Regras de ouro

- Cada `malloc` tem um dono, que é responsável pelo seu `free`. Documenta quem é.
- Verifica sempre se `malloc` e `realloc` devolveram `NULL`.
- Liberta pela ordem inversa de criação, e põe o apontador a `NULL` depois.
- Para estruturas, escreve um par `criar` / `destruir` e usa-o sempre.

## Erros comuns

- `malloc(n)` em vez de `malloc(n * sizeof *v)`: pedes bytes, não elementos.
- `p = realloc(p, ...)`: se falhar, perdes o bloco original (fuga).
- Esquecer de libertar nos caminhos de erro (um `return` a meio da função).
- Achar que o sistema "limpa no fim" e por isso não faz mal: é verdade quando o programa termina, mas é um péssimo hábito e esconde erros reais.
