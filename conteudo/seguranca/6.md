Em C e C++, o programador gere a memória diretamente, e a linguagem não verifica se um acesso está dentro dos limites de um vetor. Escrever para lá do fim de um *buffer* corrompe o que está ao lado na memória: outras variáveis, ou o **endereço de retorno** da função. Estes erros são a origem de cerca de 70% das vulnerabilidades graves em software como o Windows e o Chrome, segundo a Microsoft e a Google. Perceber o mecanismo explica as defesas e a tendência para linguagens com segurança de memória, como o Rust.

## O que está na pilha

Quando uma função é chamada, a pilha guarda (Arquitetura de Computadores, lição 2) as variáveis locais e, mais acima, o endereço para onde voltar:

```c
void pede_nome(void) {
    char nome[16];
    gets(nome);              // NUNCA usar: não sabe o tamanho do buffer
    printf("Olá, %s\n", nome);
}
```

```
endereços altos
┌────────────────────┐
│ endereço de retorno │  ← para onde a função volta
├────────────────────┤
│ registo guardado    │
├────────────────────┤
│ nome[15]           │
│ …                  │
│ nome[0]            │  ← gets escreve a partir daqui, para cima
└────────────────────┘
endereços baixos
```

Se o utilizador escrever 40 caracteres, `gets` continua a escrever por cima do registo guardado e do endereço de retorno. Quando a função faz `ret`, salta para o endereço que lá ficou. Se esse valor foi escolhido por um atacante, o programa passa a executar o que o atacante quiser.

## Simular

Esta simulação não executa nada: modela a pilha como uma lista de bytes e mostra o que acontece a cada "célula" quando se copia uma entrada sem verificar o tamanho, e quando se copia com verificação.

```python run
def chamada(entrada, verificar_tamanho):
    pilha = bytearray(b"\x00" * 16 + b"REGISTO!" + b"RET:main")    # buffer, registo, retorno
    dados = entrada.encode()
    if verificar_tamanho:
        dados = dados[:15]                                            # como fgets/snprintf: corta
    pilha[0:len(dados)] = dados                                       # como strcpy/gets: copia tudo
    buffer, registo, retorno = pilha[0:16], pilha[16:24], pilha[24:32]
    return buffer.rstrip(b"\x00").decode(errors="replace"), registo.decode(errors="replace"), retorno.decode(errors="replace")

for entrada in ["Ana", "A" * 20, "A" * 24 + "XXXXXXXX"]:
    for seguro in (False, True):
        b, reg, ret = chamada(entrada, seguro)
        estado = "ok" if ret == "RET:main" else "ENDEREÇO DE RETORNO CORROMPIDO"
        print(f"{'com' if seguro else 'sem'} verificação, {len(entrada):2} bytes → retorno = {ret!r:12} {estado}")
```

Prevê, antes de correr, a partir de quantos bytes o endereço de retorno é atingido sem verificação. Na realidade, um processo com a pilha corrompida é terminado pelo sistema (no melhor caso) ou desviado (no pior).

## Outras falhas de memória

- **Use-after-free:** usar memória depois de a libertar (outro objeto pode estar lá).
- **Double free:** libertar duas vezes.
- **Overflow de inteiros:** `tamanho * n` dá a volta e aloca-se um buffer minúsculo.
- **Strings de formato:** `printf(texto_do_utilizador)` em vez de `printf("%s", texto)`.
- **Leitura fora dos limites:** o **Heartbleed** (2014) devolvia até 64 KB da memória do servidor, incluindo chaves privadas.

## Defesas

No código:

- Funções com limites: `fgets`, `snprintf`, `strncpy` com cuidado, ou `strlcpy`. Nunca `gets`, `strcpy` ou `sprintf` com dados externos.
- Compilar com avisos (`-Wall -Wextra`) e testar com o **AddressSanitizer** (`-fsanitize=address`) e o **Valgrind**, que detetam acessos fora dos limites durante os testes.
- **Fuzzing** (AFL++, libFuzzer): gerar milhões de entradas aleatórias e mutadas à procura de falhas.

No sistema (mitigações que tornam a exploração muito mais difícil):

- **Canários de pilha:** um valor aleatório entre o buffer e o endereço de retorno; se mudar, o programa aborta (`-fstack-protector-strong`).
- **NX / DEP:** a pilha e a heap não são executáveis.
- **ASLR:** os endereços mudam em cada execução, e o atacante não sabe para onde saltar.
- **Integridade do fluxo de controlo** (CFI, *shadow stacks* em hardware).

E a solução de fundo: **linguagens com segurança de memória** (Rust, Go, Java, C#, Python), que verificam os limites ou impedem estas classes de erros por construção. A Microsoft, a Google, o Linux e o Android estão a escrever código novo em Rust por esta razão, e as agências de cibersegurança dos EUA recomendam-no.
