A maior parte das vulnerabilidades encontra-se a **ler** código, não a atacar sistemas. Um revisor que reconhece os padrões perigosos apanha-os antes de chegarem a produção. Esta lição treina esse olhar com exemplos que podes correr.

## Ler e prever: injeção de SQL

```python run
import sqlite3

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE utilizadores (nome TEXT, password TEXT, admin INTEGER)")
con.executemany("INSERT INTO utilizadores VALUES (?, ?, ?)", [("ana", "x9!kq", 1), ("rui", "pa55", 0)])

def login(nome, password):
    q = f"SELECT nome, admin FROM utilizadores WHERE nome = '{nome}' AND password = '{password}'"
    return con.execute(q).fetchall()

print(login("rui", "errada"))
print(login("ana' --", "qualquer"))
```

Antes de correr: que query é enviada à base de dados no segundo caso? O que fazem o `'` e o `--`?

## Encontra o erro: comparar passwords

```python run
import hashlib

guardado = hashlib.sha256(b"pa55").hexdigest()

def confere(tentativa):
    return hashlib.sha256(tentativa.encode()).hexdigest() == guardado

print(confere("pa55"), confere("errada"))
```

Funciona, mas há pelo menos dois problemas de segurança na forma como a password é guardada. Quais são?

**Ler e prever:** o primeiro dá `[]`. O segundo envia `... WHERE nome = 'ana' --' AND password = 'qualquer'`: a aspa fecha o texto e o `--` transforma o resto em comentário. A password nunca é verificada e entra como `ana`, que é administradora: `[('ana', 1)]`.

**Encontra o erro:** (1) SHA-256 é rápido demais: um atacante com a base de dados testa milhares de milhões de passwords por segundo. Usa-se um algoritmo lento feito para passwords (Argon2, bcrypt, scrypt). (2) Sem *salt*, passwords iguais têm hashes iguais e servem tabelas pré-calculadas. Os algoritmos próprios para passwords tratam do salt sozinhos.

**Escreve tu:**
```python
def login(nome, password):
    return con.execute("SELECT nome, admin FROM utilizadores WHERE nome = ? AND password = ?", (nome, password)).fetchall()
```
Com parâmetros, os dados nunca são interpretados como código SQL: vão separados da query. Filtrar carateres falha sempre em algum caso (outras codificações, outros carateres especiais) e estraga nomes legítimos como O'Neill.
