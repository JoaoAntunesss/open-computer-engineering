Em Ferramentas do Programador aprendeste os comandos do Git. Numa equipa, o problema passa a ser outro: como é que várias pessoas mudam o mesmo código ao mesmo tempo sem se atrapalharem, e como se garante que o que entra no ramo principal tem qualidade. A resposta é um **fluxo de trabalho** combinado e a **revisão de código** (*code review*).

## Fluxos de trabalho com ramos

**GitHub flow** (o mais simples, e o mais usado em projetos web):

1. `main` está sempre pronto a pôr em produção.
2. Para cada alteração, cria-se um ramo a partir de `main` (`git switch -c lembrete-sms`).
3. Commits pequenos, com mensagens claras.
4. Abre-se um **pull request** (PR) para `main`.
5. A CI corre os testes; alguém revê.
6. Depois de aprovado, junta-se a `main` e faz-se deploy.

**Trunk-based development:** ramos que duram horas, não semanas; tudo entra em `main` várias vezes por dia, e o trabalho inacabado fica escondido com *feature flags*. Usado por equipas com muita automação.

**Git flow:** ramos `develop`, `release/*`, `hotfix/*`. Útil para software com versões numeradas e várias versões em manutenção (aplicações de desktop, bibliotecas). Pesado demais para um site.

## Bons pull requests

- **Pequenos:** menos de 400 linhas alteradas. PRs gigantes não são revistos a sério: recebem "LGTM" sem leitura.
- Uma coisa de cada vez: não misturar uma funcionalidade nova com uma refatoração e com a mudança de formatação de 30 ficheiros.
- **Descrição:** o quê, porquê, como testar, capturas de ecrã se mexer na interface.
- Testes incluídos.

## Mensagens de commit

```
Envia lembrete por SMS na véspera da marcação

Os clientes faltavam por esquecimento (3 a 4 faltas por semana).
O lembrete sai às 18h para as marcações confirmadas do dia seguinte
e inclui uma ligação para remarcar.
```

Primeira linha curta (até ~50 caracteres), no imperativo, a dizer o que muda; linha em branco; depois o **porquê**. O "o quê" está no código; o porquê não.

## Conflitos

Acontecem quando dois ramos mudam as mesmas linhas. O Git marca-os:

```
<<<<<<< HEAD
const TAXA_FALTA = 10;
=======
const TAXA_FALTA = 15;
>>>>>>> taxa-nova
```

Resolve-se escolhendo (ou combinando), apagando os marcadores, testando e fazendo commit. Para os evitar: ramos curtos, juntar `main` ao teu ramo com frequência, e não reformatar ficheiros inteiros sem combinar.

## Revisão de código

Objetivos, por ordem: encontrar erros, partilhar conhecimento (pelo menos duas pessoas conhecem cada parte), manter a coerência do código.

**Como rever:**

- Primeiro o **desenho**: a abordagem faz sentido? Depois os pormenores.
- Lê os testes: dizem o que o código promete.
- Procura: casos limite, erros não tratados, segurança (dados do utilizador sem validação), nomes confusos, duplicação.
- Comentários **sobre o código**, não sobre a pessoa; com o porquê; distinguindo o que é obrigatório do que é sugestão ("nit:").
- Deixa a formatação e o estilo para ferramentas automáticas (Prettier, Black, linters na CI).

```python run
# Revê este código como num pull request. Encontra pelo menos 4 problemas antes de correr.
def aplicar_desconto(precos, cupao):
    total = 0
    for i in range(1, len(precos)):
        total += precos[i]
    if cupao == "AMIGO10":
        total = total - total * 10 / 100
    if cupao == "AMIGO10" or "PROMO5":
        total -= 5
    return total

print(aplicar_desconto([15, 45, 20], "AMIGO10"))
print(aplicar_desconto([15, 45, 20], "INVALIDO"))
print(aplicar_desconto([3], ""))
```
