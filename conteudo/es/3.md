Em Programação Orientada a Objetos viste os diagramas de classes e de sequência. Em Engenharia de Software, a UML serve para **comunicar e decidir** antes e durante o desenvolvimento: com o cliente (casos de uso), com a equipa (modelo de domínio, estados, atividades). A regra é desenhar só o que ajuda a perceber ou a decidir, e manter os diagramas no repositório, em texto (PlantUML ou Mermaid), para não ficarem desatualizados.

## Diagrama de casos de uso

Mostra **quem** (atores) faz **o quê** (casos de uso) com o sistema. É o diagrama para conversar com o cliente.

```
@startuml
left to right direction
actor Cliente
actor "Dona do salão" as Dona
actor "Serviço de SMS" as SMS
rectangle "Marcações online" {
  Cliente --> (Marcar serviço)
  Cliente --> (Cancelar marcação)
  Dona --> (Gerir agenda)
  Dona --> (Bloquear férias)
  (Marcar serviço) .> (Enviar confirmação) : <<include>>
  (Enviar confirmação) --> SMS
}
@enduml
```

Cada caso de uso tem uma descrição: ator, pré-condições, fluxo principal, fluxos alternativos (o que acontece se a hora já estiver ocupada?).

## Modelo de domínio

Um diagrama de classes **sem métodos nem pormenores técnicos**, com os conceitos do negócio e as relações. Serve para a equipa e o cliente usarem as mesmas palavras:

```
@startuml
class Cliente { nome; telefone }
class Marcacao { inicio; estado }
class Servico { nome; preco; duracao }
class Funcionario { nome }
Cliente "1" -- "*" Marcacao
Marcacao "*" -- "1" Servico
Marcacao "*" -- "0..1" Funcionario
Funcionario "*" -- "*" Servico : sabe fazer
@enduml
```

## Diagrama de estados

Para objetos com um ciclo de vida: em que estados pode estar uma marcação, e que eventos a fazem mudar.

```
@startuml
[*] --> Pendente : cliente marca
Pendente --> Confirmada : sinal pago
Pendente --> Cancelada : 30 min sem pagar
Confirmada --> Cancelada : cliente cancela (> 24 h)
Confirmada --> Concluida : serviço feito
Confirmada --> Falta : não apareceu
Concluida --> [*]
Cancelada --> [*]
Falta --> [*]
@enduml
```

O diagrama de estados passa diretamente a código, e o código fica a recusar transições que não existem:

```python run
TRANSICOES = {
    ("Pendente", "pagar"): "Confirmada",
    ("Pendente", "expirar"): "Cancelada",
    ("Confirmada", "cancelar"): "Cancelada",
    ("Confirmada", "concluir"): "Concluida",
    ("Confirmada", "faltar"): "Falta",
}

class Marcacao:
    def __init__(self):
        self.estado = "Pendente"
    def evento(self, e):
        novo = TRANSICOES.get((self.estado, e))
        if novo is None:
            raise ValueError(f"'{e}' não é possível no estado {self.estado}")
        self.estado = novo
        return self.estado

m = Marcacao()
for e in ["pagar", "concluir", "cancelar"]:
    try:
        print(e, "→", m.evento(e))
    except ValueError as erro:
        print("recusado:", erro)
```

Prevê as três linhas. Uma marcação concluída não pode ser cancelada: o diagrama e o código dizem o mesmo.

## Diagrama de atividades

Um fluxograma com decisões e atividades em paralelo; bom para processos de negócio ("o que acontece desde que o cliente marca até ao pagamento").

```
@startuml
start
:Cliente escolhe serviço e hora;
if (hora ainda livre?) then (sim)
  :Reservar hora durante 30 min;
  :Pedir pagamento do sinal;
  if (pagou?) then (sim)
    :Confirmar e enviar SMS;
  else (não)
    :Libertar a hora;
  endif
else (não)
  :Sugerir horas próximas;
endif
stop
@enduml
```

## UML a mais e UML a menos

- **A mais:** dezenas de diagramas detalhados antes de escrever uma linha de código, que ninguém volta a abrir.
- **A menos:** decisões importantes (estados, regras, quem fala com quem) que só existem na cabeça de uma pessoa.
- Um bom meio-termo: um modelo de domínio, os diagramas de estados dos objetos com ciclo de vida, e diagramas de sequência dos fluxos mais delicados. Em Mermaid, o GitHub mostra-os diretamente nos ficheiros `.md`.
