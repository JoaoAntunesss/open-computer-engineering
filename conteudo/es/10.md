## Ler e prever: o que acontece quando o requisito muda?

```python run
def preco(tipo_cliente, valor):
    if tipo_cliente == "normal":
        return valor
    elif tipo_cliente == "estudante":
        return valor * 0.8
    elif tipo_cliente == "senior":
        return valor * 0.7
    else:
        raise ValueError(tipo_cliente)

print(preco("estudante", 50), preco("senior", 50))
```

## Encontra o problema: uma função impossível de testar

```python
import datetime, smtplib, sqlite3

def lembrete_diario():
    hoje = datetime.date.today()
    con = sqlite3.connect("/var/app/producao.db")
    for nome, email in con.execute("SELECT nome, email FROM clientes WHERE aniversario = ?", (hoje.isoformat(),)):
        s = smtplib.SMTP("smtp.empresa.pt")
        s.sendmail("app@empresa.pt", email, f"Parabéns, {nome}!")
```

Ler isto e perceber porque é difícil de testar é o objetivo. Para testar "manda um email a cada aniversariante" precisas de que coisas reais?

**Ler e prever:** cada tipo novo obriga a mexer na cadeia de `if` de **todas** as funções que decidem pelo tipo de cliente. É o sinal clássico de que falta polimorfismo ou uma tabela de regras num só sítio (princípio aberto/fechado).

**Encontra o problema:** depende da data real, da base de dados de produção e de um servidor de email verdadeiro. Não dá para testar sem enviar emails a clientes reais. Além disso, abre uma ligação SMTP por cliente e nunca fecha nada.

```python
def lembrete_diario(hoje, clientes, enviar):
    for nome, email, aniversario in clientes:
        if aniversario == hoje:
            enviar(email, f"Parabéns, {nome}!")

def test_so_aniversariantes():
    enviados = []
    clientes = [("Ana", "ana@x.pt", "2027-01-10"), ("Rui", "rui@x.pt", "2027-03-02")]
    lembrete_diario("2027-01-10", clientes, lambda e, m: enviados.append((e, m)))
    assert enviados == [("ana@x.pt", "Parabéns, Ana!")]
```
