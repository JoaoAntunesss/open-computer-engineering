**Integração contínua** (CI) é juntar o trabalho de todos ao ramo principal várias vezes por dia, com testes automáticos a correr a cada alteração. **Entrega contínua** (CD) é ter o código sempre pronto a pôr em produção, com um clique; **implantação contínua** é pô-lo em produção automaticamente, se os testes passarem. Juntas, transformam "o deploy de sexta à noite" num não-acontecimento.

## Porquê

- Os erros são encontrados minutos depois de serem introduzidos, quando ainda se sabe o que se mudou.
- Ninguém fica com um ramo de três semanas impossível de juntar.
- O deploy deixa de depender de uma pessoa e de uma lista de passos manuais (que um dia são esquecidos).
- Entregas pequenas e frequentes são menos arriscadas do que entregas grandes e raras: se algo parte, sabe-se o quê.

## Um pipeline típico

```
push / pull request
   ↓
1. instalar dependências
2. verificar formatação e linter
3. testes unitários
4. construir (compilar, empacotar, imagem Docker)
5. testes de integração / ponta a ponta
6. análise de segurança (dependências vulneráveis, segredos no código)
   ↓ (só em main)
7. deploy para staging → testes de fumo → deploy para produção
```

Se um passo falha, o pipeline para, e quem fez a alteração é avisado.

## GitHub Actions

```yaml
# .github/workflows/ci.yml
name: CI
on:
  push:
    branches: [main]
  pull_request:

jobs:
  testes:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python: ["3.11", "3.12"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python }}
          cache: pip
      - run: pip install -r requirements.txt
      - run: ruff check .
      - run: pytest --cov=app --cov-fail-under=80

  deploy:
    needs: testes
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install -g firebase-tools
      - run: firebase deploy --only hosting --token "${{ secrets.FIREBASE_TOKEN }}"
```

- `on`: quando corre (cada push para `main`, cada pull request).
- `matrix`: os mesmos testes em várias versões.
- `needs`: o deploy só corre se os testes passarem.
- `secrets`: chaves e tokens guardados nas definições do repositório, nunca no código.

## Ler um pipeline e prever

Este pequeno executor simula a lógica de dependências entre trabalhos. Prevê que trabalhos correm em cada caso:

```python run
trabalhos = {
    "lint":     {"precisa": [], "so_main": False},
    "testes":   {"precisa": [], "so_main": False},
    "build":    {"precisa": ["lint", "testes"], "so_main": False},
    "e2e":      {"precisa": ["build"], "so_main": False},
    "deploy":   {"precisa": ["e2e"], "so_main": True},
}

def corre(ramo, falha=None):
    estado = {}
    for nome, t in trabalhos.items():            # já estão por ordem de dependências
        if t["so_main"] and ramo != "main":
            estado[nome] = "ignorado"
        elif any(estado[d] != "ok" for d in t["precisa"]):
            estado[nome] = "não correu"
        else:
            estado[nome] = "falhou" if nome == falha else "ok"
    return estado

print("PR, tudo bem:   ", corre("lembrete-sms"))
print("main, tudo bem: ", corre("main"))
print("main, testes ✗: ", corre("main", falha="testes"))
```

## Boas práticas

- O pipeline deve ser **rápido** (menos de 10 minutos); se demora uma hora, ninguém espera por ele.
- **Testes instáveis** (que falham às vezes) destroem a confiança: corrige-os ou remove-os, não os ignores.
- Usa a CI também para o que é chato: formatação, verificação de tipos, auditoria de dependências (`npm audit`, Dependabot).
- **Ambientes:** staging (igual a produção, com dados de teste) antes de produção.
- Deploys reversíveis: poder voltar à versão anterior num minuto. Para mudanças arriscadas: *feature flags*, *canary releases* (primeiro para 5% dos utilizadores).
- **Nunca** pôr segredos no repositório. Se acontecer, revoga-os imediatamente: apagar o ficheiro não chega, eles ficam no histórico.
