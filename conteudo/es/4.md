A **arquitetura** é a organização de alto nível de um sistema: em que partes se divide, o que cada uma faz e como comunicam. São as decisões difíceis de mudar depois. Uma boa arquitetura permite mudar uma parte sem partir as outras; uma má faz com que cada alteração pequena demore semanas.

## Camadas

A mais comum. Cada camada só usa a de baixo:

```
Apresentação   (páginas, API REST)        ← o que o utilizador vê
Aplicação      (casos de uso: "marcar")   ← orquestra
Domínio        (regras: "não há marcações sobrepostas")
Dados          (repositórios, SQL)        ← onde se guarda
```

- Mudar de base de dados só mexe na camada de dados.
- As regras de negócio ficam num sítio só, e testam-se sem base de dados nem browser.
- Risco: camadas que só passam chamadas umas às outras sem fazer nada ("lasanha").

Variante moderna: **arquitetura hexagonal** (portas e adaptadores) ou **limpa**: o domínio está no centro e não depende de nada; a base de dados, a web e o envio de SMS são "adaptadores" que se ligam por interfaces (a inversão de dependências de SOLID).

## MVC

Para interfaces: **Modelo** (dados e regras), **Vista** (apresentação), **Controlador** (recebe as ações, chama o modelo, escolhe a vista). Laravel, Django, Rails e Spring MVC seguem-no. No front-end, as frameworks (React, Vue) usam variantes: componentes com estado, e o estado partilhado num sítio central.

```python run
# Um MVC mínimo, sem framework
class Modelo:                                   # dados e regras
    def __init__(self):
        self.marcacoes = {}
    def marcar(self, hora, cliente):
        if hora in self.marcacoes:
            raise ValueError(f"{hora} já está ocupada")
        self.marcacoes[hora] = cliente

class Vista:                                    # apresentação
    def agenda(self, marcacoes):
        return "\n".join(f"  {h}  {c}" for h, c in sorted(marcacoes.items())) or "  (vazia)"
    def erro(self, msg):
        return f"  ⚠ {msg}"

class Controlador:                              # liga as ações ao modelo e escolhe a vista
    def __init__(self, modelo, vista):
        self.m, self.v = modelo, vista
    def pedido(self, hora, cliente):
        try:
            self.m.marcar(hora, cliente)
            return self.v.agenda(self.m.marcacoes)
        except ValueError as e:
            return self.v.erro(str(e))

c = Controlador(Modelo(), Vista())
for hora, cliente in [("10:00", "Ana"), ("09:00", "Rui"), ("10:00", "Eva")]:
    print(f"{cliente} pede {hora}:")
    print(c.pedido(hora, cliente))
```

Prevê o que aparece. A regra "não há duas marcações à mesma hora" está no modelo: se amanhã houver uma app móvel, reutiliza-se.

## Monólito e microsserviços

- **Monólito:** uma única aplicação, um único deploy, normalmente uma base de dados. Simples de desenvolver, testar e pôr em produção. É a escolha certa para quase todos os projetos no início, e para a maioria das empresas pequenas e médias.
- **Monólito modular:** um só deploy, mas dividido internamente em módulos com fronteiras claras (marcações, pagamentos, notificações). Bom compromisso.
- **Microsserviços:** cada parte é um serviço independente, com a sua base de dados, comunicando por rede (HTTP, mensagens). Permite equipas independentes e escalar partes diferentes, mas traz os problemas todos de Sistemas Distribuídos: falhas de rede, dados inconsistentes, depuração difícil, muita infraestrutura.

Regra prática: só se divide em microsserviços quando a equipa e a escala o exigem (várias equipas a pisar-se no mesmo código). "Começar com microsserviços" é um erro frequente em projetos pequenos.

## Outros estilos

- **Orientado a eventos:** os componentes publicam eventos ("MarcacaoCriada") e outros reagem (enviar SMS, atualizar estatísticas), sem se conhecerem.
- **Serverless:** funções pequenas que correm a pedido (como as Cloud Functions do Firebase).
- **Cliente-servidor**, **par-a-par**, ***pipeline*** (dados que passam por etapas).

## Documentar decisões

Regista as decisões de arquitetura em **ADRs** (*Architecture Decision Records*): um ficheiro curto por decisão, com o contexto, a decisão, as alternativas consideradas e as consequências. Daqui a um ano, ninguém se lembra porque se escolheu Firebase em vez de PostgreSQL.
