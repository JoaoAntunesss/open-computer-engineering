A maioria dos projetos que correm mal não falha por código mal escrito: falha porque se construiu a coisa errada. Os **requisitos** dizem o que o sistema deve fazer e com que qualidade. As **histórias de utilizador** são a forma ágil de os escrever, em pedaços pequenos e com valor para alguém.

## Requisitos funcionais e não funcionais

- **Funcionais:** o que o sistema faz. "O cliente pode cancelar uma marcação até 24 horas antes."
- **Não funcionais:** como o faz (qualidades). "A página de marcações abre em menos de 2 segundos num telemóvel com 4G." "Os dados pessoais cumprem o RGPD." "Funciona com leitores de ecrã."

Os não funcionais esquecem-se muitas vezes e são os que mais custam a acrescentar no fim (desempenho, segurança, acessibilidade).

## Bons requisitos

Um requisito deve ser:

- **Verificável:** "rápido" não se testa; "responde em menos de 500 ms em 95% dos pedidos" sim.
- **Não ambíguo:** "o administrador pode ver os dados dos clientes" — todos os dados? De todos os clientes?
- **Necessário** (alguém precisa mesmo dele) e **viável**.

## Histórias de utilizador

```
Como cliente do salão,
quero receber um lembrete na véspera da marcação,
para não me esquecer e não pagar a taxa de falta.
```

Quem, o quê, **porquê**. O "porquê" é o mais importante: permite encontrar soluções melhores do que a pedida, e decidir prioridades.

**INVEST**, as qualidades de uma boa história:

- **I**ndependente (pode ser feita sozinha)
- **N**egociável (é o início de uma conversa, não um contrato)
- **V**aliosa para alguém
- **E**stimável
- **S**mall (cabe num sprint)
- **T**estável

## Critérios de aceitação

Cada história tem critérios que dizem quando está feita. O formato **Dado / Quando / Então** (Gherkin) torna-os quase testes automáticos:

```
Cenário: lembrete enviado na véspera
  Dado que a Marta tem uma marcação para 10/11 às 10h
  Quando são 18h de 9/11
  Então a Marta recebe um SMS com a hora e uma ligação para remarcar

Cenário: marcação cancelada não gera lembrete
  Dado que a Marta cancelou a marcação de 10/11
  Quando são 18h de 9/11
  Então a Marta não recebe nenhum lembrete
```

Os critérios podem ser executados com ferramentas como o Cucumber ou o `pytest-bdd`. Mesmo sem ferramentas, escritos assim são fáceis de transformar em testes:

```python run
from datetime import datetime, timedelta

def lembretes_a_enviar(marcacoes, agora):
    """Marcações confirmadas de amanhã, se já passou das 18h e ainda não se avisou."""
    amanha = (agora + timedelta(days=1)).date()
    if agora.hour < 18:
        return []
    return [m for m in marcacoes
            if m["estado"] == "confirmada" and m["inicio"].date() == amanha and not m["avisado"]]

marcacoes = [
    {"cliente": "Marta", "inicio": datetime(2026, 11, 10, 10), "estado": "confirmada", "avisado": False},
    {"cliente": "Rui", "inicio": datetime(2026, 11, 10, 15), "estado": "cancelada", "avisado": False},
    {"cliente": "Eva", "inicio": datetime(2026, 11, 11, 9), "estado": "confirmada", "avisado": False},
    {"cliente": "Tó", "inicio": datetime(2026, 11, 10, 9), "estado": "confirmada", "avisado": True},
]
# Cenário 1 e 2 (Dado / Quando / Então)
r = lembretes_a_enviar(marcacoes, datetime(2026, 11, 9, 18, 0))
print([m["cliente"] for m in r])
print([m["cliente"] for m in lembretes_a_enviar(marcacoes, datetime(2026, 11, 9, 17, 59))])
```

Prevê as duas linhas. Cada caso da lista corresponde a um critério de aceitação.

## Do épico à tarefa

- **Épico:** algo grande ("Marcações online").
- **Histórias:** partes com valor ("marcar um serviço", "cancelar", "lembrete na véspera", "pagar sinal").
- **Tarefas:** o trabalho técnico de cada história ("tabela de lembretes", "envio de SMS", "agendar a tarefa diária").

Divide-se **na vertical** (cada história atravessa interface, lógica e dados e entrega algo utilizável), não na horizontal ("fazer a base de dados toda", depois "fazer a interface toda").

## Erros comuns

- Histórias que são tarefas técnicas disfarçadas: "Como programador, quero uma tabela de clientes".
- Requisitos que descrevem a solução em vez da necessidade: "quero um botão vermelho" em vez de "quero que seja difícil apagar por engano".
- Ninguém falar com os utilizadores reais (ver IPM).
