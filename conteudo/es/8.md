Código que funciona não é o mesmo que código de qualidade. A qualidade interna (legibilidade, simplicidade, testes) decide quanto custa mudar o software amanhã. Quando se escolhe o atalho rápido em vez da solução bem feita, contrai-se **dívida técnica**: poupa-se tempo agora e paga-se "juros" em cada alteração futura.

## Métricas de código

Úteis como **sinais**, nunca como objetivos em si:

- **Complexidade ciclomática:** número de caminhos independentes numa função (1 + número de `if`, `for`, `while`, `and`, `or`, `case`). Acima de 10, a função é difícil de testar e de perceber.
- **Tamanho:** funções com dezenas de linhas, classes com centenas.
- **Duplicação:** o mesmo bloco copiado em vários sítios (uma correção tem de ser feita em todos).
- **Cobertura de testes:** que parte do código os testes executam.
- **Acoplamento** (quantas outras partes cada módulo usa) e **coesão** (se o que está junto pertence junto).

Ferramentas: **SonarQube**/SonarCloud, `radon` (Python), ESLint com regras de complexidade, CodeClimate.

```python run
import ast

codigo = '''
def preco(servico, cliente, dia, cupao):
    p = servico["preco"]
    if cliente["fiel"] and p > 50:
        p *= 0.9
    if dia in ("sábado", "domingo"):
        p += 5
    if cupao:
        if cupao == "AMIGO10":
            p -= 10
        elif cupao == "PROMO5" and p > 20:
            p -= 5
    for extra in servico.get("extras", []):
        if extra["ativo"] or cliente["fiel"]:
            p += extra["preco"]
    return max(p, 0)

def total(itens):
    return sum(i["preco"] for i in itens)
'''

def complexidade(func):
    decisoes = (ast.If, ast.For, ast.While, ast.IfExp, ast.ExceptHandler)
    c = 1
    for n in ast.walk(func):
        if isinstance(n, decisoes):
            c += 1
        elif isinstance(n, ast.BoolOp):
            c += len(n.values) - 1           # cada "and"/"or" é mais um caminho
    return c

for f in ast.parse(codigo).body:
    print(f.name, "complexidade:", complexidade(f), "linhas:", f.end_lineno - f.lineno + 1)
```

Prevê a complexidade de `preco`, contando à mão os `if`, `elif`, `for`, `and` e `or`.

## Dívida técnica

Ward Cunningham comparou-a a uma dívida financeira: às vezes é uma boa decisão (lançar antes de um concorrente, validar uma ideia), desde que seja **consciente** e se **pague** depois.

Tipos (o "quadrante" de Fowler):

| | deliberada | inadvertida |
|---|---|---|
| **prudente** | "lançamos já e refazemos o módulo depois" | "agora percebemos como devíamos ter feito" |
| **imprudente** | "não há tempo para desenho" | "o que é uma camada?" |

**Sinais de dívida acumulada:** cada alteração parte outra coisa; estimativas que falham sempre; partes do código em que "ninguém mexe"; o tempo das funcionalidades novas a crescer mês após mês.

## Gerir a dívida

- **Torná-la visível:** registá-la no backlog como qualquer outro trabalho, com o custo de a deixar ("cada funcionalidade de pagamentos demora o dobro").
- **Regra do escuteiro:** deixa o código um pouco melhor do que o encontraste, em cada alteração.
- Reservar uma parte de cada sprint (10–20%) para pagar dívida.
- **Portões de qualidade** na CI: não deixar entrar código novo com complexidade alta, sem testes ou com duplicação, mesmo que o código antigo ainda tenha.
- Refatorar com testes por trás (lição 9 de POO).
