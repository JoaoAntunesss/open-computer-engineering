Testes automáticos são programas que verificam outros programas. Dão confiança para mudar código sem medo, documentam como o código deve comportar-se e apanham regressões antes dos clientes. Há vários níveis, e uma estratégia equilibrada usa todos, em proporções diferentes.

## A pirâmide de testes

```
        ▲  poucos, lentos, frágeis
       / \     Aceitação / ponta a ponta (E2E)
      /   \    Integração
     /_____\   Unitários
        ▼  muitos, rápidos, estáveis
```

- **Unitários:** uma função ou classe, isolada. Milissegundos. Testam a lógica e os casos limite.
- **Integração:** várias partes juntas a sério: o código e uma base de dados real (num contentor), a API e o serviço de email (falso). Segundos.
- **Ponta a ponta (E2E):** o sistema inteiro, como um utilizador: abrir o browser, marcar, ver a confirmação (Playwright, Cypress). Lentos e mais frágeis, mas apanham o que os outros não apanham.
- **Aceitação:** verificam os critérios de aceitação das histórias (muitas vezes, E2E escritos em Dado/Quando/Então).

## pytest

```python
# marcacoes.py
def preco_total(servicos, cliente_fiel=False):
    total = sum(s["preco"] for s in servicos)
    return round(total * 0.9, 2) if cliente_fiel and total >= 50 else total

# test_marcacoes.py
import pytest
from marcacoes import preco_total

def test_soma_os_servicos():
    assert preco_total([{"preco": 15}, {"preco": 45}]) == 60

def test_desconto_so_acima_de_50():
    assert preco_total([{"preco": 45}], cliente_fiel=True) == 45

@pytest.mark.parametrize("precos, esperado", [([50], 45.0), ([30, 30], 54.0), ([], 0)])
def test_desconto_fiel(precos, esperado):
    assert preco_total([{"preco": p} for p in precos], cliente_fiel=True) == esperado
```

Corre com `pytest`. Os ficheiros e funções começados por `test_` são encontrados automaticamente.

## Duplos de teste

Para testar uma unidade isolada, substitui-se o que ela usa:

- **Stub:** devolve respostas fixas ("a API de pagamentos diz sempre aprovado").
- **Mock:** regista as chamadas para verificares ("enviou exatamente 1 SMS para 912…").
- **Fake:** uma implementação simplificada que funciona (a base de dados em memória).

Usa-os nas fronteiras (rede, tempo, aleatoriedade, serviços pagos), não em tudo: testes cheios de mocks testam a implementação e partem quando se refatora.

## TDD na prática

**Vermelho → verde → refatorar** (POO, lição 9). Um exemplo, com testes à mão para correr aqui:

```python run
# 1. VERMELHO: escreve os testes primeiro
def testes(f):
    casos = [
        (("10:00", 30), "10:30"),
        (("10:45", 30), "11:15"),
        (("23:50", 20), "00:10"),
        (("09:05", 0), "09:05"),
    ]
    falhas = [(args, esperado, f(*args)) for args, esperado in casos if f(*args) != esperado]
    print("OK" if not falhas else f"FALHAM: {falhas}")

# 2. VERDE: primeira versão (ingénua)
def hora_fim_v1(inicio, minutos):
    h, m = map(int, inicio.split(":"))
    return f"{h:02d}:{m + minutos:02d}"

# 3. Corrigir até passar
def hora_fim_v2(inicio, minutos):
    h, m = map(int, inicio.split(":"))
    total = (h * 60 + m + minutos) % (24 * 60)
    return f"{total // 60:02d}:{total % 60:02d}"

testes(hora_fim_v1)
testes(hora_fim_v2)
```

Prevê que casos falham na v1. Os testes escritos antes obrigaram a pensar nos limites (passar a hora, passar a meia-noite).

## O que torna um teste bom

- **Rápido** e **determinista** (sem depender da hora atual, da rede ou da ordem dos testes). Injeta o "agora" como parâmetro.
- **Um comportamento por teste**, com um nome que diz qual.
- Testa o **comportamento** (o que a função devolve) e não a implementação (que métodos internos chama).
- Falha quando o código está errado. Faz a experiência: estraga o código de propósito e vê se algum teste falha (*mutation testing* automatiza isto).
