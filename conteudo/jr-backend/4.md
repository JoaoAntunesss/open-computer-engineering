Autenticação (saber **quem** é o utilizador) é das partes onde um erro tem consequências mais graves. A regra número um: **não inventes**. Usa bibliotecas e serviços testados, e percebe o suficiente para os usar bem.

## Palavras-passe: nunca em texto

As passwords guardam-se como **hash** feito com um algoritmo lento e próprio para isso (Argon2 ou bcrypt), nunca em texto, nunca com MD5 ou SHA-256 simples.

```python
from argon2 import PasswordHasher

ph = PasswordHasher()
guardado = ph.hash("a-password-do-utilizador")   # isto vai para a base de dados

def confere(guardado, tentativa):
    try:
        return ph.verify(guardado, tentativa)
    except Exception:
        return False
```

Se a base de dados for roubada, o atacante não fica com as passwords. O algoritmo ser lento é de propósito: torna muito caro tentar milhões de combinações.

## Sessões e tokens

Depois do login, o servidor tem de reconhecer o utilizador nos pedidos seguintes. Duas formas comuns:

- **Sessão com cookie**: o servidor guarda a sessão e o browser envia um cookie com um identificador. Marca o cookie como `HttpOnly`, `Secure` e `SameSite`.
- **Token (por exemplo JWT)**: o servidor dá um token assinado e o cliente envia-o no cabeçalho `Authorization: Bearer ...`. Comum em APIs e apps móveis. Os tokens devem expirar depressa e não levam dados sensíveis lá dentro (o conteúdo de um JWT é legível por qualquer pessoa).

## Autorização: o que cada um pode fazer

Autenticar é saber quem és; **autorizar** é verificar se podes fazer aquilo. O erro mais comum em APIs:

```python
@app.get("/marcacoes/{mid}")
def obter(mid: int, utilizador = Depends(utilizador_atual)):
    m = repo.obter(mid)
    if m is None or m.cliente_id != utilizador.id:
        raise HTTPException(404)
    return m
```

Sem a verificação `m.cliente_id != utilizador.id`, qualquer pessoa com sessão iniciada vê as marcações de todos, só mudando o número no URL. Este erro tem nome (IDOR) e está sempre no topo das listas de vulnerabilidades.

## Quando usar um serviço pronto

Para a maioria dos projetos, um serviço de autenticação (Firebase Auth, Supabase Auth, Auth0, Keycloak) é mais seguro do que fazeres tu: trata de recuperação de password, verificação de email, login com Google, proteção contra força bruta e 2FA. Já usas o Firebase Auth nos teus projetos; a lógica de **autorização** continua a ser tua (como as regras de segurança do Firebase).

## Lista rápida

- HTTPS sempre.
- Limitar tentativas de login.
- Mensagens de erro que não revelam se o email existe ("Email ou palavra-passe errados").
- Verificar permissões em **todos** os endpoints, no servidor (nunca só esconder botões no frontend).
- Segredos (chaves de assinatura) fora do código.
