Quase todos os sistemas que vais construir guardam dados de pessoas: nomes, emails, localizações, compras, registos de acesso. Na União Europeia, isso é regulado pelo **RGPD** (Regulamento Geral sobre a Proteção de Dados). Não é só um problema dos juristas: a maior parte das obrigações cumpre-se — ou falha — no desenho da base de dados e do código.

## O que é o RGPD

É o **Regulamento (UE) 2016/679**, aplicável desde 25 de maio de 2018 em todos os Estados-Membros. Em Portugal é complementado pela **Lei n.º 58/2019**, e a autoridade de controlo é a **CNPD** (Comissão Nacional de Proteção de Dados). Aplica-se a qualquer organização que trate dados de pessoas que estejam na UE, mesmo que a empresa esteja fora.

Conceitos base:

- **Dado pessoal**: qualquer informação sobre uma pessoa identificada ou identificável — nome, email, número de cliente, IP, localização, fotografia.
- **Categorias especiais** (art. 9.º): saúde, origem racial ou étnica, opiniões políticas, religião, orientação sexual, dados biométricos e genéticos. Têm proteção reforçada.
- **Tratamento**: qualquer operação sobre dados — recolher, guardar, consultar, cruzar, apagar.
- **Responsável pelo tratamento**: quem decide para quê e como (a empresa). **Subcontratante**: quem trata por conta dele (o fornecedor de cloud, a empresa de email marketing).

## Os sete princípios (art. 5.º)

1. **Licitude, lealdade e transparência**: base legal e informação clara ao titular.
2. **Limitação das finalidades**: recolhidos para um fim concreto, e não reutilizados para outro incompatível.
3. **Minimização**: só os dados necessários.
4. **Exatidão**: corrigir o que estiver errado.
5. **Limitação da conservação**: apagar quando já não forem precisos.
6. **Integridade e confidencialidade**: segurança adequada.
7. **Responsabilidade**: conseguir demonstrar que se cumpre.

## Bases legais (art. 6.º)

Todo o tratamento precisa de uma de seis bases: **consentimento**, **contrato**, **obrigação legal**, **interesses vitais**, **interesse público** ou **interesses legítimos**. O consentimento não é a única, nem muitas vezes a melhor: para entregar uma encomenda, a base é o contrato. Quando se usa consentimento, tem de ser livre, específico, informado, inequívoco — uma caixa já assinalada não conta — e tão fácil de retirar como de dar.

## Direitos dos titulares

Acesso, retificação, apagamento ("direito a ser esquecido"), limitação, **portabilidade** (receber os dados num formato estruturado e legível por máquina), oposição, e o direito a não ficar sujeito a **decisões exclusivamente automatizadas** com efeitos significativos (art. 22.º). A resposta deve ser dada, em regra, no prazo de um mês.

Para um programador, isto traduz-se em funcionalidades: exportar os dados de um utilizador em JSON, apagá-los de verdade (incluindo cópias e logs, dentro do possível), e saber onde estão.

## Privacidade desde a conceção

O art. 25.º exige **proteção de dados desde a conceção e por defeito**. Na prática:

- não recolher campos "porque pode dar jeito";
- definições por defeito mais privadas (perfil não público, sem rastreio opcional ligado);
- prazos de conservação implementados com tarefas que apagam dados antigos;
- separar identificadores dos restantes dados;
- cifrar em trânsito (HTTPS) e em repouso, controlar acessos, registar quem consulta o quê.

## Pseudonimização não é anonimização

Substituir o nome por um código é **pseudonimização**: com a chave, volta-se à pessoa, por isso os dados continuam a ser pessoais. **Anonimizar** é tornar a reidentificação razoavelmente impossível, o que é muito mais difícil do que parece — combinações de código postal, data de nascimento e sexo identificam a maioria das pessoas.

```python
import hmac, hashlib

CHAVE = b"guardada-fora-da-base-de-dados"     # num cofre de segredos, nunca no código

def pseudonimo(email: str) -> str:
    return hmac.new(CHAVE, email.lower().encode(), hashlib.sha256).hexdigest()[:16]

print(pseudonimo("ana@exemplo.pt"))   # sempre o mesmo código para o mesmo email
```

Usar HMAC com chave secreta, em vez de um hash simples, impede que alguém calcule o hash de uma lista de emails conhecidos e os encontre na tabela.

## Violações de dados

Se houver uma violação (fuga, acesso indevido, perda), o responsável tem de a notificar à CNPD **em 72 horas** após ter conhecimento, salvo se for improvável que resulte em risco, e informar os titulares se o risco for elevado. As coimas podem chegar a **20 milhões de euros ou 4% do volume de negócios anual mundial**, o que for maior.

## Erros comuns

- Achar que um IP ou um ID de cliente "não é dado pessoal".
- Pedir consentimento para tudo, incluindo o que é necessário para o contrato.
- "Apagar" marcando um campo `apagado = true` e manter tudo.
- Copiar a base de dados de produção, com dados reais, para testes.
- Escrever dados pessoais nos logs (emails, tokens, moradas).
