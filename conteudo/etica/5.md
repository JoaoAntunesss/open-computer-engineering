Cerca de uma em cada seis pessoas no mundo vive com uma deficiência significativa, segundo a Organização Mundial da Saúde. A isso somam-se as limitações temporárias (um braço partido) e situacionais (sol no ecrã, um bebé ao colo, uma ligação lenta). Software acessível funciona para todas elas — e, quase sempre, fica melhor para toda a gente.

## Quem usa o teu software de forma diferente

- **Visão**: pessoas cegas usam leitores de ecrã (NVDA, JAWS, VoiceOver, TalkBack) que leem a página em voz alta; pessoas com baixa visão usam ampliação e contraste alto; cerca de 8% dos homens têm algum tipo de daltonismo.
- **Motora**: navegam só com teclado, com interruptores, com controlo por voz ou por movimento dos olhos.
- **Audição**: precisam de legendas e transcrições.
- **Cognitiva**: beneficiam de linguagem simples, estrutura previsível e tempo suficiente.

## As WCAG

As **Web Content Accessibility Guidelines** do W3C são a referência mundial. A versão 2.2 é de outubro de 2023. Organizam-se em quatro princípios, o **POUR**:

- **Percetível**: alternativas em texto a imagens, legendas, contraste suficiente, conteúdo que se adapta ao tamanho do ecrã.
- **Operável**: tudo funciona com teclado, há tempo suficiente, nada pisca mais de três vezes por segundo, a navegação é clara.
- **Compreensível**: texto legível, comportamento previsível, ajuda a evitar e corrigir erros em formulários.
- **Robusto**: código válido e semântico, que as tecnologias de apoio conseguem interpretar.

Cada critério tem um nível: **A** (mínimo), **AA** (o que a lei normalmente exige) e **AAA**.

## A lei

- Em Portugal, o **Decreto-Lei n.º 83/2018** obriga os sítios web e aplicações móveis do setor público a cumprir as WCAG (nível AA) e a publicar uma declaração de acessibilidade.
- O **Ato Europeu de Acessibilidade** (Diretiva (UE) 2019/882), aplicável desde 28 de junho de 2025, alarga obrigações a muitos produtos e serviços privados: comércio eletrónico, bancos, transportes, livros digitais, telefones e computadores.

## O essencial, na prática

**HTML semântico primeiro.** Um `<button>` já é focável, ativa-se com Enter e Espaço e é anunciado como botão. Um `<div onclick>` não é nada disso.

```html
<!-- mal -->
<div class="btn" onclick="enviar()">Enviar</div>

<!-- bem -->
<button type="submit">Enviar</button>
```

Outras regras de ouro:

- **Imagens**: texto alternativo que diga o que a imagem transmite (`alt="Gráfico: vendas subiram 20% em março"`); imagens decorativas com `alt=""`.
- **Formulários**: cada campo com `<label>` associado; mensagens de erro em texto, perto do campo, e não só a vermelho.
- **Estrutura**: um `<h1>` por página, títulos por ordem, regiões (`<header>`, `<nav>`, `<main>`) e uma ligação "Saltar para o conteúdo".
- **Teclado**: tudo alcançável com Tab, ordem lógica, foco sempre visível, e nada que "prenda" o foco.
- **Cor**: nunca usar só a cor para transmitir informação (junta um ícone ou texto).
- **Movimento**: respeitar `prefers-reduced-motion` e permitir pausar animações.
- **ARIA** só quando o HTML não chega. A primeira regra do ARIA é: se existe um elemento nativo, usa-o.

## Contraste

As WCAG definem o **contraste** entre duas cores a partir da luminância relativa. O nível AA exige pelo menos **4.5:1** para texto normal e **3:1** para texto grande (a partir de 24 px, ou 18.66 px em negrito) e para componentes da interface.

```python
def luminancia(hexcor):
    r, g, b = (int(hexcor.lstrip("#")[i:i + 2], 16) / 255 for i in (0, 2, 4))
    lin = lambda c: c / 12.92 if c <= 0.03928 else ((c + 0.055) / 1.055) ** 2.4
    return 0.2126 * lin(r) + 0.7152 * lin(g) + 0.0722 * lin(b)

def contraste(c1, c2):
    l1, l2 = sorted([luminancia(c1), luminancia(c2)], reverse=True)
    return (l1 + 0.05) / (l2 + 0.05)

print(round(contraste("#777777", "#ffffff"), 2))   # 4.48: falha AA por pouco
print(round(contraste("#767676", "#ffffff"), 2))   # 4.54: passa
print(round(contraste("#eef2fb", "#04060d"), 2))   # texto deste site sobre o fundo
```

## Erros comuns

- Tirar o contorno de foco (`outline: none`) sem pôr outro visível.
- Botões só com ícone e sem nome acessível (`aria-label`).
- Placeholders no lugar de labels.
- Achar que acessibilidade é "um extra para o fim": corrigir no fim custa muito mais.
- Confiar só no resultado verde do Lighthouse.
