Muitas das máquinas onde o teu código vai correr não têm ecrã: servidores da faculdade, máquinas na cloud, um Raspberry Pi. O **SSH** (*Secure Shell*) dá-te um terminal nessas máquinas através da rede, com tudo cifrado.

## Ligar a uma máquina

```bash
ssh aluno@servidor.exemplo.pt
```

Na primeira ligação aparece uma pergunta sobre a **impressão digital** do servidor. O SSH guarda-a em `~/.ssh/known_hosts` e, nas ligações seguintes, confirma que estás a falar com a mesma máquina. Se um dia aparecer o aviso *"REMOTE HOST IDENTIFICATION HAS CHANGED"*, não o ignores: ou o servidor foi reinstalado, ou alguém está a tentar fazer-se passar por ele. Confirma com quem gere a máquina.

Para sair, escreve `exit` ou carrega em `Ctrl+D`.

## Chaves em vez de palavras-passe

Escrever a palavra-passe sempre é lento e menos seguro. A alternativa é um **par de chaves**:

- a **chave privada** fica só no teu computador e nunca sai de lá;
- a **chave pública** é copiada para os servidores onde queres entrar.

O servidor desafia-te com algo que só a chave privada consegue responder. A chave privada nunca passa pela rede.

```bash
ssh-keygen -t ed25519 -C "o-teu-email@exemplo.pt"
# carrega Enter para o local por omissão e escolhe uma frase-passe
```

Ficam dois ficheiros: `~/.ssh/id_ed25519` (privada, **não partilhes**) e `~/.ssh/id_ed25519.pub` (pública).

```bash
ssh-copy-id aluno@servidor.exemplo.pt     # instala a pública no servidor
ssh aluno@servidor.exemplo.pt             # já não pede a palavra-passe da conta
```

Para o GitHub: copia o conteúdo de `id_ed25519.pub` para **Settings → SSH and GPG keys → New SSH key**, e testa com `ssh -T git@github.com`.

> A frase-passe protege a chave privada se alguém te roubar o portátil. Com o `ssh-agent` só a escreves uma vez por sessão.

## O ficheiro de configuração

Em vez de decorares utilizadores e endereços, cria `~/.ssh/config`:

```text
Host lab
    HostName servidor.exemplo.pt
    User aluno
    IdentityFile ~/.ssh/id_ed25519

Host pi
    HostName 192.168.1.50
    User pi
```

Passas a escrever só `ssh lab` ou `ssh pi`. Funciona também no `scp`, no `rsync` e no Git.

## Copiar ficheiros

```bash
scp relatorio.pdf lab:~/entregas/          # local → remoto
scp lab:~/resultados.csv .                 # remoto → local
rsync -avz projeto/ lab:~/projeto/         # sincroniza pastas, só envia o que mudou
```

Para pastas grandes ou cópias repetidas, o `rsync` é muito mais rápido porque só transfere as diferenças.

## Correr coisas que demoram

Se fechares o portátil, a ligação SSH cai e o programa que estava a correr morre com ela. Para trabalhos longos, usa o `tmux`:

```bash
ssh lab
tmux new -s treino          # abre uma sessão que sobrevive à desligação
python treinar_modelo.py
# Ctrl+b e depois d  → sai da sessão, que continua a correr
exit
# mais tarde:
ssh lab
tmux attach -t treino       # voltas a ver o programa onde estava
```

## Túneis

O SSH pode reencaminhar portas. Se no servidor está a correr um Jupyter na porta 8888, que só aceita ligações locais:

```bash
ssh -L 8888:localhost:8888 lab
```

Abres `http://localhost:8888` no teu browser e o tráfego vai cifrado até ao servidor.

## Erros comuns

- Partilhar ou fazer commit da chave **privada** (o ficheiro sem `.pub`). Se acontecer, gera um par novo e remove a chave antiga de todos os servidores e do GitHub.
- *"Permissions are too open"*: a chave privada tem de ter permissões `600`. Corre `chmod 600 ~/.ssh/id_ed25519`.
- Treinos de horas mortos porque a ligação caiu. Usa `tmux`.
