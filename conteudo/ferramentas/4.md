O Git guarda a história de um projeto: cada versão, quem a fez e porquê. Deixas de ter `relatorio_final_v3_AGORA_SIM.docx`, podes voltar atrás quando estragas algo e podes trabalhar em várias coisas ao mesmo tempo sem as misturar. Em todas as cadeiras com projeto, e em qualquer emprego, vão assumir que sabes usá-lo.

## A ideia central: snapshots

Um **commit** é uma fotografia do projeto inteiro num momento, com uma mensagem a explicar o que mudou. Cada commit aponta para o anterior, e a sequência forma a história.

O Git tem três zonas:

1. **Pasta de trabalho**: os ficheiros como estão no teu disco.
2. **Área de preparação** (*staging*): o que vai entrar no próximo commit.
3. **Repositório**: a história de commits, guardada na pasta `.git`.

```text
editar ficheiros  →  git add  →  git commit
(pasta de trabalho)   (staging)    (repositório)
```

A área de preparação existe para escolheres o que entra em cada commit: podes ter mudado cinco ficheiros e fazer dois commits separados, cada um com uma ideia.

## Primeiros passos

```bash
git config --global user.name "João Antunes"
git config --global user.email "o-teu-email@exemplo.pt"
git config --global init.defaultBranch main

mkdir projeto && cd projeto
git init                       # cria o repositório (a pasta .git)
echo "# Projeto" > README.md
git status                     # o que mudou? O que está preparado?
git add README.md              # prepara
git commit -m "Adiciona README"
git log --oneline              # história resumida
```

O `git status` é o comando que vais usar mais. Corre-o antes e depois de cada operação até ganhares confiança.

```bash
git diff                # o que mudou e ainda não está preparado
git diff --staged       # o que está preparado para o próximo commit
git add -p              # prepara por partes, escolhendo bloco a bloco
git restore ficheiro    # deita fora as alterações não preparadas
```

### Boas mensagens de commit

Escreve no imperativo, em uma linha curta, o que o commit faz: `Corrige divisão por zero na média`, não `alterações` nem `wip`. Se precisares de explicar porquê, deixa uma linha em branco e escreve um parágrafo.

### O que não entra no Git

Cria um ficheiro `.gitignore` com o que não deve ser guardado: ficheiros gerados, dependências e segredos.

```text
__pycache__/
*.o
node_modules/
.env
```

Nunca faças commit de palavras-passe ou chaves. Mesmo que as apagues no commit seguinte, continuam na história.

## Ramos

Um **ramo** (*branch*) é uma linha de desenvolvimento independente. Na prática, é só um nome que aponta para um commit e avança quando fazes commits novos.

```bash
git switch -c login        # cria o ramo "login" e muda para ele
# ... editar, add, commit ...
git switch main            # volta ao main; os ficheiros mudam no disco
git branch                 # lista os ramos
```

Usa um ramo para cada funcionalidade ou correção. O `main` fica sempre num estado que funciona.

## Merge

Quando a funcionalidade está pronta, juntas o ramo ao `main`:

```bash
git switch main
git merge login
```

Se o `main` não avançou entretanto, o Git limita-se a mover o `main` para a frente (*fast-forward*). Se os dois avançaram, cria um **commit de merge** com dois pais.

### Conflitos

Se os dois ramos mudaram as mesmas linhas, o Git não adivinha qual está certa e marca o ficheiro:

```text
<<<<<<< HEAD
total = soma / len(valores)
=======
total = soma / max(len(valores), 1)
>>>>>>> login
```

Resolver é simples: edita o ficheiro até ficar como deve, apaga as marcas, e depois:

```bash
git add calculos.py
git commit            # conclui o merge
```

Os conflitos não são erros nem perigosos: são o Git a pedir-te uma decisão.

## Rebase

O `rebase` é a alternativa ao merge: em vez de juntar as duas histórias, **reaplica os teus commits por cima** do ramo de destino, como se tivesses começado a trabalhar a partir da versão mais recente.

```bash
git switch login
git rebase main       # os commits de "login" passam a vir depois dos do main
```

Fica uma história em linha reta, mais fácil de ler. A regra de ouro: **não faças rebase de commits que já partilhaste** (que já enviaste para o GitHub e outras pessoas usam). O rebase cria commits novos, e quem tinha os antigos fica com uma história diferente da tua.

## Voltar atrás

```bash
git restore ficheiro           # descarta alterações não preparadas
git restore --staged ficheiro  # tira da área de preparação
git commit --amend             # corrige o último commit (mensagem ou conteúdo)
git revert abc123              # cria um commit que desfaz o abc123 (seguro)
git reset --hard abc123        # volta o ramo ao abc123 e APAGA o que veio depois
```

Usa `revert` para desfazer algo já partilhado. O `reset --hard` reescreve a história e perde trabalho: só o uses quando sabes exatamente o que fazes. Mesmo assim, o `git reflog` mostra onde o ramo esteve nos últimos dias e permite recuperar quase tudo.

## Erros comuns

- Commits enormes com dez alterações misturadas. Faz commits pequenos, cada um com uma ideia.
- Trabalhar diretamente no `main` em projetos de grupo.
- Fazer commit de `node_modules`, ficheiros compilados ou `.env`.
- Entrar em pânico num conflito e apagar a pasta. Corre `git status`: diz-te exatamente o que fazer.
