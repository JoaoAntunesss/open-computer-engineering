Código de sistemas operativos (processos, threads, ficheiros) é dos mais difíceis de ler, porque várias coisas acontecem **ao mesmo tempo** e a ordem muda de execução para execução. A tabela de rastreio passa a ter uma coluna por processo ou thread.

## Ler e prever: fork

```c
#include <stdio.h>
#include <unistd.h>

int main(void) {
    int x = 10;
    pid_t pid = fork();
    if (pid == 0) {
        x = x + 5;
        printf("filho: %d\n", x);
    } else {
        x = x - 5;
        printf("pai: %d\n", x);
    }
    printf("fim: %d\n", x);
    return 0;
}
```

Antes de correres no teu Linux (ou WSL): quantas linhas aparecem? Que valores? A ordem é sempre a mesma?

## Encontra o erro: uma condição de corrida

Duas threads somam 1 a um contador partilhado, 100 000 vezes cada. Em Python (como em C) isto pode perder incrementos:

```python
import threading

contador = 0
def trabalho():
    global contador
    for _ in range(100000):
        valor = contador
        valor = valor + 1
        contador = valor

threads = [threading.Thread(target=trabalho) for _ in range(2)]
for t in threads: t.start()
for t in threads: t.join()
print(contador, "(esperado: 200000)")
```

Corre-o várias vezes no teu computador (as threads não funcionam nas caixas desta página). Porque é que se perdem incrementos? Faz a tabela de rastreio com duas colunas (thread A e thread B) e encontra uma ordem que perde uma soma.

## Escreve tu

Corrige o contador com um `threading.Lock` à volta das três linhas críticas. Explica porque é que o código com o lock deixa de perder somas.

**Ler e prever (fork):** aparecem 4 linhas: o filho mostra `filho: 15` e `fim: 15`; o pai mostra `pai: 5` e `fim: 5`. Cada processo tem a **sua cópia** de `x`. A ordem entre pai e filho não é garantida e pode mudar de execução para execução.

**Encontra o erro:** ler, somar e escrever são três passos. Se A lê 41, B lê 41, A escreve 42 e B escreve 42, perdeu-se uma soma. É uma condição de corrida (*race condition*).

**Escreve tu:**
```python
trinco = threading.Lock()
def trabalho():
    global contador
    for _ in range(100000):
        with trinco:
            contador += 1
```
O lock garante que só uma thread de cada vez executa a secção crítica.
