**Virtualizar** é fazer um recurso parecer outro: um computador físico parecer vários, ou um conjunto de processos parecer estar sozinho na máquina. Há duas grandes formas: **máquinas virtuais**, que simulam um computador inteiro com o seu próprio sistema operativo, e **contentores**, que isolam processos que partilham o mesmo kernel. A cloud inteira assenta nestas duas ideias.

## Máquinas virtuais

Um **hipervisor** corre vários sistemas operativos convidados, cada um convencido de que tem o hardware só para si.

- **Tipo 1** (*bare metal*): o hipervisor corre diretamente no hardware. VMware ESXi, Xen, Hyper-V, KVM (dentro do Linux). É o que os fornecedores de cloud usam.
- **Tipo 2** (*hosted*): corre como um programa dentro de um SO normal. VirtualBox, VMware Workstation, Parallels, UTM.

**Como funciona:** o SO convidado corre em modo utilizador (ou num modo especial). Quando tenta uma instrução privilegiada (mudar a tabela de páginas, desativar interrupções), o processador gera uma exceção e o hipervisor **emula** essa instrução sobre o hardware virtual. Os processadores modernos têm suporte próprio (Intel VT-x, AMD-V) e tabelas de páginas em dois níveis (convidado → "físico" do convidado → físico real), o que torna as VMs quase tão rápidas como o hardware real.

**Vantagens:** isolamento forte (cada VM tem o seu kernel), qualquer SO (Windows num Linux), *snapshots*, migração de uma VM entre máquinas sem a desligar.

**Custos:** cada VM tem um SO inteiro (gigabytes de disco, centenas de MB de RAM) e demora segundos ou minutos a arrancar.

## Contentores

Um contentor é um grupo de **processos normais** do Linux, isolados com duas funcionalidades do kernel:

- **Namespaces:** cada contentor tem a sua vista do sistema. Namespace de PID (o processo principal vê-se como PID 1), de rede (as suas próprias interfaces e portas), de montagem (o seu sistema de ficheiros), de utilizadores, de nome da máquina.
- **cgroups:** limitam e contabilizam os recursos: no máximo 512 MB de RAM, 1,5 núcleos, tantas operações de disco por segundo.

Mais um **sistema de ficheiros em camadas** (overlayfs): a imagem é um conjunto de camadas só de leitura (sistema base, dependências, a aplicação), mais uma camada de escrita por contentor.

**Vantagens:** arrancam em milissegundos, ocupam pouco (partilham o kernel e as camadas), e a imagem leva tudo o que a aplicação precisa: "funciona no meu computador" passa a funcionar em todo o lado.

**Limites:** o isolamento é mais fraco do que numa VM (uma falha de segurança no kernel afeta todos os contentores); um contentor Linux precisa de um kernel Linux (no Mac e no Windows, o Docker Desktop corre uma VM Linux escondida).

## Comparação

| | máquina virtual | contentor |
|---|---|---|
| isola | um computador inteiro | processos |
| kernel | um por VM | partilhado |
| arranque | segundos a minutos | milissegundos |
| tamanho | GB | MB |
| isolamento | forte | bom, mas menor |
| uso típico | vários SO, separar clientes na cloud | empacotar e distribuir aplicações |

Na cloud, usam-se muitas vezes os dois: contentores a correr dentro de VMs.

## Docker na prática

```dockerfile
FROM python:3.12-slim          # camada base
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "app.py"]
```

```
docker build -t minha-app .
docker run -d -p 8080:80 --memory 512m --cpus 1 minha-app
docker ps
docker exec -it <id> sh        # entrar no contentor
```

`-p 8080:80` liga a porta 8080 da máquina à 80 do contentor (namespace de rede); `--memory` e `--cpus` são cgroups.

Para ver que um contentor é só um processo, corre um e procura-o com `ps aux` na máquina: lá está, com um PID normal.

## Ler e prever

Dentro de um contentor, `ps aux` mostra o processo principal com PID 1. Na máquina, o mesmo processo tem, por exemplo, PID 48213. Que namespace explica isto? E porque é que, se o contentor tentar usar 2 GB com `--memory 512m`, o processo é terminado?

??? Soluções
1: o namespace de PID: o contentor tem a sua própria numeração. Com `--memory 512m`, o cgroup de memória não deixa passar desse limite; quando o processo tenta, o kernel ativa o OOM killer dentro do cgroup e termina-o.

2: não arranca nenhum sistema operativo: é só criar namespaces e cgroups e lançar um processo no kernel que já está a correr.

3: VMs (ou micro-VMs), pelo isolamento mais forte: cada cliente tem o seu kernel, por isso uma falha no kernel não expõe os outros. O Firecracker cria micro-VMs que arrancam em cerca de 125 ms, juntando o isolamento das VMs à rapidez dos contentores; é usado no AWS Lambda.

4: cada instrução cria uma camada, que fica em cache. Se só o código mudar, a camada do `pip install` é reaproveitada e a construção é muito mais rápida.
