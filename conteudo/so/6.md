Em Arquitetura de Computadores viste como o hardware traduz endereços virtuais (MMU, tabelas de páginas, TLB). Aqui vês o outro lado: o que o **sistema operativo** faz com esse mecanismo. É ele que cria as tabelas de páginas, decide que páginas ficam na RAM e quais vão para o disco, e trata cada falta de página.

## O espaço de endereços de um processo

```
endereços altos
┌──────────────┐
│ pilha        │  cresce para baixo
│      ↓       │
│              │
│      ↑       │
│ heap         │  cresce para cima (malloc)
├──────────────┤
│ dados (.data, .bss) │
├──────────────┤
│ código (.text) │  só de leitura e execução
└──────────────┘
endereços baixos
```

No Linux, vês o mapa de um processo em `/proc/<pid>/maps`. Por segurança, as zonas são colocadas em endereços aleatórios em cada execução (**ASLR**), para dificultar ataques.

## O que o SO faz com as páginas

- **Atribuição preguiçosa:** `malloc(1 GB)` só reserva endereços. As páginas físicas só são atribuídas na primeira escrita, numa falta de página. Por isso pedir muita memória é instantâneo e usá-la não é.
- **Copy-on-write:** depois de `fork`, pai e filho partilham as páginas marcadas como só de leitura. Quem escrever primeiro provoca uma falta de página e recebe a sua cópia.
- **Partilha:** as bibliotecas (`libc.so`) e os executáveis existem uma vez na RAM, mapeados em vários processos.
- **Ficheiros mapeados em memória** (`mmap`): o ficheiro aparece como um vetor; as páginas são lidas do disco quando são tocadas.

## Paginação para disco e substituição

Quando a RAM enche, o SO escolhe uma página para expulsar (escrevendo-a no **swap** se estiver suja). Que página escolher?

- **Ótimo (OPT/Belady):** a que vai ser usada mais tarde no futuro. Impossível na prática, mas serve de referência.
- **FIFO:** a que entrou há mais tempo. Simples, mas pode expulsar páginas muito usadas.
- **LRU:** a usada há mais tempo. Muito bom, mas caro de implementar exatamente.
- **Relógio (segunda oportunidade):** aproxima o LRU com o bit de **acesso** que o hardware marca em cada página. Percorre as páginas em círculo: se o bit é 1, põe-o a 0 e passa à frente; se é 0, expulsa. É o que os SO usam, em variantes.

Prevê o número de faltas de cada algoritmo com 3 molduras (páginas físicas):

```python run
def fifo(refs, k):
    mem, faltas = [], 0
    for p in refs:
        if p not in mem:
            faltas += 1
            if len(mem) == k:
                mem.pop(0)
            mem.append(p)
    return faltas

def lru(refs, k):
    mem, faltas = [], 0
    for p in refs:
        if p in mem:
            mem.remove(p)
        else:
            faltas += 1
            if len(mem) == k:
                mem.pop(0)                 # a menos recentemente usada está à frente
        mem.append(p)
    return faltas

def otimo(refs, k):
    mem, faltas = [], 0
    for i, p in enumerate(refs):
        if p in mem:
            continue
        faltas += 1
        if len(mem) == k:
            futuro = refs[i + 1:]
            vitima = max(mem, key=lambda q: futuro.index(q) if q in futuro else len(refs))
            mem.remove(vitima)
        mem.append(p)
    return faltas

refs = [7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 2, 1, 2, 0, 1, 7, 0, 1]
for k in (3, 4):
    print(f"{k} molduras: FIFO {fifo(refs, k)}, LRU {lru(refs, k)}, ótimo {otimo(refs, k)}")

belady = [1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5]
print("anomalia de Belady (FIFO):", fifo(belady, 3), "faltas com 3,", fifo(belady, 4), "com 4")
```

A última linha mostra a **anomalia de Belady**: com FIFO, ter mais memória pode dar **mais** faltas. O LRU não sofre disto.

## Thrashing

Se os processos ativos precisam, ao mesmo tempo, de mais páginas do que cabem na RAM, o sistema passa o tempo a trocar páginas com o disco e quase não faz trabalho útil: é o **thrashing**. O computador fica lento, o disco não para. Soluções: menos processos ao mesmo tempo, mais RAM, ou o **OOM killer** do Linux, que termina o processo que mais memória gasta.
