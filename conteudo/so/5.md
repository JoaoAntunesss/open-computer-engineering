Um **interbloqueio** (*deadlock*) acontece quando um grupo de threads fica parado para sempre, cada uma à espera de um recurso que outra do grupo tem. Não há erro nem mensagem: o programa simplesmente deixa de responder. Saber as condições que o causam permite desenhar programas onde ele não pode acontecer.

## O exemplo clássico

```c
// Thread 1                       // Thread 2
lock(&conta_a);                   lock(&conta_b);
lock(&conta_b);   // espera...    lock(&conta_a);   // espera...
transferir(a, b);                 transferir(b, a);
```

A thread 1 tem `a` e espera por `b`; a thread 2 tem `b` e espera por `a`. Nenhuma avança. Funciona quase sempre, e bloqueia quando as duas fazem o primeiro `lock` quase ao mesmo tempo.

## As quatro condições (Coffman)

O interbloqueio só acontece se as quatro forem verdadeiras ao mesmo tempo:

1. **Exclusão mútua:** os recursos não podem ser partilhados.
2. **Posse e espera:** uma thread guarda recursos enquanto espera por outros.
3. **Sem preempção:** não se pode tirar um recurso a quem o tem.
4. **Espera circular:** há um ciclo T₁ → T₂ → … → T₁, em que cada uma espera por um recurso da seguinte.

Para **prevenir**, basta quebrar uma.

## Prevenção na prática

- **Ordem global dos trincos** (quebra a espera circular): todas as threads adquirem os trincos pela mesma ordem. Para contas: primeiro a de número menor. É a técnica mais usada.
- **Pedir tudo de uma vez** (quebra posse e espera): adquire todos os recursos no início, ou nenhum.
- **Tentar e desistir** (simula preempção): `pthread_mutex_trylock`; se falhar, liberta o que tens, espera um pouco e tenta de novo. Cuidado com o *livelock* (todos desistem e tentam outra vez ao mesmo tempo, para sempre).
- **Menos trincos:** estruturas sem partilha, mensagens em vez de memória partilhada, um único trinco grosso quando o desempenho não é crítico.

## Evitar: o algoritmo do banqueiro

Cada processo declara à partida o máximo de recursos de que vai precisar. Antes de conceder um pedido, o SO verifica se o sistema continua num **estado seguro**: existe uma ordem em que todos os processos podem terminar. Se não, o pedido espera. É elegante, mas pouco usado em SO gerais (ninguém sabe os máximos à partida); aparece em sistemas embutidos e em escalonadores de recursos.

## Detetar e recuperar

Constrói-se o **grafo de espera** (T₁ → T₂ se T₁ espera por algo que T₂ tem) e procura-se um **ciclo**. Se houver, aborta-se uma das threads (ou transações). As bases de dados fazem exatamente isto: o PostgreSQL deteta o ciclo e cancela uma das transações com o erro *deadlock detected*.

```python run
def tem_ciclo(espera):
    # espera: thread -> thread de quem está à espera
    for inicio in espera:
        visto, t = [], inicio
        while t in espera and t not in visto:
            visto.append(t)
            t = espera[t]
        if t == inicio:
            return visto
    return None

print(tem_ciclo({"T1": "T2", "T2": "T3", "T3": "T1"}))
print(tem_ciclo({"T1": "T2", "T2": "T3"}))
print(tem_ciclo({"T1": "T2", "T2": "T3", "T3": "T2", "T4": "T1"}))
```

## A ordem dos trincos em código

```c
void transferir(Conta *de, Conta *para, int valor) {
    Conta *primeiro = de->id < para->id ? de : para;
    Conta *segundo  = de->id < para->id ? para : de;
    pthread_mutex_lock(&primeiro->trinco);
    pthread_mutex_lock(&segundo->trinco);
    de->saldo -= valor;
    para->saldo += valor;
    pthread_mutex_unlock(&segundo->trinco);
    pthread_mutex_unlock(&primeiro->trinco);
}
```

Agora duas transferências em sentidos opostos pedem os trincos pela mesma ordem e não podem formar um ciclo.

## O jantar dos filósofos

Cinco filósofos à volta de uma mesa, com um garfo entre cada dois. Para comer, cada um precisa dos dois garfos ao lado. Se todos pegarem no garfo da esquerda ao mesmo tempo, ficam todos à espera do da direita: interbloqueio. Solução: numerar os garfos e pegar sempre primeiro no de número menor (o último filósofo pega primeiro no da direita).
