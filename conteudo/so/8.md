Os processos têm memória separada, por isso precisam do sistema operativo para comunicar. A **comunicação entre processos** (IPC) tem várias formas: **pipes** para mandar uma sequência de bytes de um para outro, **sinais** para avisos curtos, **sockets** para comunicar na mesma máquina ou pela rede, e memória partilhada para grandes volumes.

## Pipes

Um pipe é um canal num só sentido, com um buffer no kernel: o que se escreve numa ponta lê-se na outra, pela mesma ordem. É o que a shell usa em `ls | grep .c | wc -l`.

```c
// pipe.c
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    int fd[2];
    pipe(fd);                     // fd[0]: leitura, fd[1]: escrita
    if (fork() == 0) {            // filho: escreve
        close(fd[0]);
        const char *msg[] = {"um", "dois", "três"};
        for (int i = 0; i < 3; i++) {
            if (write(fd[1], msg[i], strlen(msg[i]) + 1) < 0) return 1;
        }
        close(fd[1]);             // fechar a escrita = fim de ficheiro para o leitor
        return 0;
    }
    close(fd[1]);                 // pai: lê
    char buf[64];
    ssize_t n;
    while ((n = read(fd[0], buf, sizeof buf)) > 0) {
        for (ssize_t i = 0; i < n; i += strlen(buf + i) + 1)
            printf("pai recebeu: %s\n", buf + i);
    }
    close(fd[0]);
    wait(NULL);
    return 0;
}
```

Regras importantes:

- `read` bloqueia enquanto o pipe estiver vazio, e devolve 0 (fim) quando **todas** as pontas de escrita estiverem fechadas. Se te esqueceres de fechar uma cópia da ponta de escrita, o leitor espera para sempre.
- `write` bloqueia se o buffer (normalmente 64 KB) estiver cheio.
- Um pipe é um **fluxo de bytes**: não guarda fronteiras entre mensagens. Duas escritas podem chegar numa só leitura (por isso o pai percorre o buffer à procura dos `\0`).
- Com `dup2(fd[1], 1)` antes de um `exec`, a saída de um programa passa a ir para o pipe. É assim que a shell liga `ls` a `grep`.

## Sinais

Um sinal é uma notificação assíncrona, identificada por um número:

| Sinal | Quando | Por omissão |
|---|---|---|
| `SIGINT` | Ctrl+C | termina |
| `SIGTERM` | `kill pid` | termina (pode ser tratado) |
| `SIGKILL` | `kill -9 pid` | termina (não pode ser tratado) |
| `SIGSEGV` | acesso inválido à memória | termina com core dump |
| `SIGCHLD` | um filho terminou | ignorado |
| `SIGPIPE` | escrever num pipe sem leitores | termina |

Um programa pode instalar um **tratador** para fazer algo antes de sair (gravar o estado, fechar ligações):

```c
volatile sig_atomic_t parar = 0;
void tratador(int s) { (void)s; parar = 1; }      // só coisas simples aqui
// no main: signal(SIGINT, tratador); while (!parar) { trabalho(); }
```

O tratador pode correr a meio de qualquer instrução: dentro dele só se podem usar funções seguras (*async-signal-safe*). `printf` e `malloc` não são. O padrão seguro é pôr uma variável a 1 e tratar o resto no ciclo principal.

## Sockets

Um socket é uma ponta de comunicação **bidirecional**. Os de domínio Unix ligam processos da mesma máquina (o Docker e o PostgreSQL usam-nos); os TCP/IP ligam máquinas diferentes (vês os pormenores em Redes). A interface é a mesma: `socket`, `bind`, `listen`, `accept` no servidor; `connect` no cliente; depois `read`/`write` como num ficheiro.

## Memória partilhada

Com `mmap` (ou `shm_open`), dois processos mapeiam as mesmas páginas físicas. É a forma mais rápida (sem cópias pelo kernel), mas volta a precisar de sincronização, como com threads.

## A mesma ideia em Python

O browser não consegue lançar processos, por isso corre este no teu computador:

```python
import subprocess
r = subprocess.run("printf 'b\\na\\nc\\na\\n' | sort | uniq -c", shell=True,
                   capture_output=True, text=True)
print(r.stdout)
```

Prevê a saída: o `printf` escreve quatro linhas para um pipe; o `sort` lê-as, ordena e escreve para outro pipe; o `uniq -c` conta as repetidas seguidas.
