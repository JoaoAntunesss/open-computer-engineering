Um sistema que serve 100 utilizadores e um que serve 1 milhão são feitos das mesmas peças. O que muda é como as combinas. Três ferramentas resolvem a maioria dos problemas de escala: **cache**, **réplicas** e **filas**. Antes de qualquer uma, a regra: **mede primeiro**. A maioria dos sistemas lentos tem uma query sem índice, não um problema de arquitetura.

## Escalar na vertical e na horizontal

- **Vertical**: uma máquina maior. Simples, mas tem limite e é um ponto único de falha.
- **Horizontal**: mais máquinas iguais atrás de um balanceador de carga. Obriga a que a aplicação **não guarde estado** na memória (sessões, ficheiros): tudo vai para a base de dados, para uma cache partilhada ou para armazenamento de ficheiros.

## Cache

Guardar o resultado de algo caro para não o repetir.

```python
def horarios_livres(salao_id, dia):
    chave = f"livres:{salao_id}:{dia}"
    em_cache = redis.get(chave)
    if em_cache:
        return json.loads(em_cache)
    livres = calcular_horarios_livres(salao_id, dia)   # query pesada
    redis.setex(chave, 60, json.dumps(livres))          # válido 60 s
    return livres
```

A parte difícil é a **invalidação**: quando alguém marca, a cache desse dia tem de ser apagada, senão outro cliente vê um horário que já não existe. Pergunta sempre: "quanto tempo posso mostrar dados desatualizados?" Para a lista de serviços, uma hora; para horários livres, quase nada.

Há cache em todos os níveis: no browser, numa CDN (imagens e páginas estáticas), na aplicação (Redis) e na própria base de dados.

## Réplicas de leitura

A maioria das aplicações lê muito mais do que escreve. Uma base de dados principal recebe as escritas e copia-as para **réplicas** que respondem às leituras. Custo: as réplicas podem estar uns milissegundos (ou segundos) atrasadas. Depois de um utilizador gravar algo, lê da principal, senão pode não ver o que acabou de gravar.

## Filas

Nem tudo tem de acontecer durante o pedido. Enviar emails, gerar PDFs, processar imagens: o pedido põe uma **mensagem numa fila** e responde logo; um **trabalhador** (*worker*) vai tirando mensagens e faz o trabalho.

```text
POST /marcacoes  →  grava na BD  →  fila: "enviar_confirmacao(41)"  →  responde 201
                                         ↓
                               worker envia o email
```

Vantagens: respostas rápidas, picos absorvidos pela fila, se o serviço de email falhar a mensagem fica para tentar outra vez. Cuidado: o worker pode processar a mesma mensagem duas vezes (vê a lição sobre idempotência).

## Limites de pedidos

Proteger a API de abusos e de clientes com bugs: limitar pedidos por utilizador ou por IP (por exemplo 100 por minuto) e devolver `429` quando passa. É barato e evita muitos incidentes.
