A diferença mais clara entre um júnior e um sénior não é escrever código mais depressa: é saber que **não há soluções perfeitas, só compromissos**, e conseguir escolher e explicar o compromisso certo para aquele contexto.

## Tudo é um compromisso

| Ganhas | Pagas com |
|---|---|
| Mais rapidez (cache) | Dados que podem estar desatualizados |
| Mais escala (várias máquinas) | Mais complexidade e falhas parciais |
| Mais flexibilidade (camadas, abstrações) | Mais código para perceber |
| Entregar já | Dívida técnica para pagar depois |
| Serviço gerido (Firebase, Cloud Run) | Menos controlo e dependência de um fornecedor |

A pergunta de um sénior é sempre: **para este problema, com esta equipa, este prazo e este orçamento, qual é a opção mais simples que funciona?** E, muitas vezes, a resposta é a mais aborrecida.

## Escrever as decisões: ADR

Um **Architecture Decision Record** é um documento curto que regista uma decisão importante. Daqui a um ano, ninguém se vai lembrar porque se escolheu PostgreSQL em vez de Firebase, a não ser que esteja escrito.

```markdown
# ADR 007: Passar as marcações do Firebase para PostgreSQL

Data: 2027-03-02 · Estado: aceite

## Contexto
Os clientes pedem relatórios por período e por funcionário. No Firebase isto
obriga a ler todos os dados e agregar no browser, que já demora 8 s.

## Decisão
Guardar marcações em PostgreSQL (Neon), atrás de uma API FastAPI. O Firebase
continua para a autenticação.

## Alternativas consideradas
- Manter Firebase e pré-calcular relatórios com Cloud Functions: menos mudança,
  mas cada relatório novo obriga a código novo.
- BigQuery: excelente para relatórios, caro e complexo para o volume atual.

## Consequências
+ Relatórios com SQL, em milissegundos.
- Uma API para manter, migração de dados, custo de alojamento (zero no plano grátis).
```

## Como avaliar opções

1. **Requisitos reais**: quantos utilizadores? quantos dados? que tempo de resposta? o que acontece se falhar?
2. **Duas ou três alternativas**, incluindo "não fazer nada" ou "a solução mais simples".
3. **Critérios explícitos**: custo, complexidade, tempo para entregar, risco, quem vai manter.
4. **Decidir**, escrever e definir quando se revê a decisão.

## Reversível ou não?

Decisões fáceis de desfazer (o nome de uma função, uma biblioteca pequena) tomam-se depressa. Decisões difíceis de desfazer (a base de dados, o formato público de uma API, a linguagem do projeto) merecem tempo, protótipos e um ADR.

## Exercício

Escreve 3 ADRs para decisões reais de projetos teus (por exemplo: porque usaste Firebase, porque o site é estático, porque escolheste Electron). Para cada um, inclui pelo menos uma alternativa que rejeitaste e o que custou a escolha.
