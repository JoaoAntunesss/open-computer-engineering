Muitas empresas fazem uma entrevista de **system design** para lugares de sénior: tens 45 minutos para desenhar um sistema (um encurtador de links, um chat, um sistema de reservas) num quadro. Não há resposta certa: avaliam **como pensas**, como fazes perguntas e como justificas os compromissos.

## Um método em 6 passos

1. **Perceber o problema (5 min).** Pergunta antes de desenhar. Que funcionalidades? Quantos utilizadores? Quantos pedidos por segundo? Mais leituras ou escritas? O que é aceitável falhar?
2. **Contas por alto (5 min).** 10 milhões de links novos por mês ≈ 4 por segundo; 100 leituras por cada escrita ≈ 400 por segundo; cada registo ~500 bytes → ~5 GB por mês. Estas contas decidem se precisas de uma base de dados ou de cinquenta.
3. **API (5 min).** Os endpoints principais e os dados que entram e saem.
4. **Desenho de alto nível (10 min).** Caixas e setas: clientes, balanceador, serviços, base de dados, cache, filas. Começa simples.
5. **Aprofundar (15 min).** Escolhe as partes difíceis: o modelo de dados, como gerar identificadores curtos únicos, onde está o estrangulamento, o que acontece quando uma peça falha.
6. **Rever (5 min).** O que mudarias com 10 vezes mais tráfego? Que compromissos aceitaste?

## Exemplo resumido: encurtador de links

- **Requisitos**: criar link curto, redirecionar, estatísticas simples. 400 leituras/s, 4 escritas/s, links para sempre.
- **API**: `POST /links {url}` → `{codigo}`; `GET /{codigo}` → `301` para o URL original.
- **Dados**: tabela `links(codigo PK, url, criado_em, dono)`.
- **Código curto**: 7 carateres em base62 dão 62⁷ ≈ 3,5 biliões de combinações. Gerar a partir de um contador ou aleatório com verificação de colisão (cada opção tem compromissos: previsibilidade contra colisões).
- **Leituras**: cache (Redis) à frente da base de dados, porque os links populares são lidos muitas vezes e nunca mudam. Uma CDN pode até responder aos redirecionamentos mais populares.
- **Estatísticas**: cada clique vai para uma fila e é agregado em segundo plano, para não atrasar o redirecionamento.
- **Falhas**: se a cache cair, a base de dados aguenta 400/s com um índice na chave primária.

## O que os entrevistadores procuram

- Perguntas antes de soluções.
- Números para justificar escolhas.
- Começar simples e complicar só quando os requisitos obrigam.
- Falar dos compromissos de cada escolha, sem esconder os defeitos.
- Pensar nas falhas.
