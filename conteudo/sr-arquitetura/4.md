Quando um sistema tem várias partes (base de dados, filas, serviços externos), as coisas falham **a meio**: o pagamento foi feito mas a marcação não ficou gravada; o email foi enviado duas vezes. Três ideias protegem-te: **transações**, **idempotência** e aceitar a **consistência eventual** onde faz sentido.

## Transações: tudo ou nada

Dentro de uma só base de dados, uma transação garante que um conjunto de alterações acontece todo ou nada (as propriedades ACID). Usa-as sempre que várias escritas têm de ser coerentes.

O problema clássico sem elas: dois clientes marcam a mesma hora ao mesmo tempo. Os dois leem "livre", os dois gravam. Soluções:

- Uma restrição na base de dados: `UNIQUE (funcionario_id, inicio)`. O segundo `INSERT` falha e devolves `409`. A base de dados é o árbitro.
- Ou `SELECT ... FOR UPDATE` dentro de uma transação, para bloquear a linha enquanto decides.

Regra: **regras de integridade importantes ficam na base de dados**, não só no código.

## Idempotência: repetir sem estragar

Na rede, um pedido pode chegar duas vezes (o utilizador clica duas vezes, a app repete após um timeout, a fila entrega a mensagem duas vezes). Uma operação **idempotente** dá o mesmo resultado se for feita uma ou várias vezes.

Para pedidos que criam coisas (pagamentos, encomendas), o cliente envia uma **chave de idempotência**:

```text
POST /pagamentos
Idempotency-Key: 6f1c2a9e-4b7d-4a0e-9a51-1d2b3c4d5e6f
```

O servidor guarda a chave com o resultado. Se a mesma chave chegar outra vez, devolve o resultado guardado em vez de cobrar duas vezes. É assim que funcionam as APIs de pagamentos (Stripe, por exemplo).

Para workers de filas: antes de processar, verifica se já foi processado (por exemplo, um campo `email_enviado_em`).

## Quando há vários sistemas: consistência eventual

Entre serviços diferentes não há uma transação única. A abordagem habitual é aceitar que, durante um curto período, as partes não estão de acordo, mas garantir que **acabam por ficar**:

- Grava a mudança e um "evento a enviar" **na mesma transação** (o padrão *outbox*); um processo envia os eventos depois. Assim nunca gravas sem avisar, nem avisas sem gravar.
- Se um passo falhar, executa uma **compensação** (cancelar a reserva se o pagamento falhou), em vez de tentar desfazer tudo de uma vez.

## O que perguntar num desenho

- O que acontece se este pedido chegar duas vezes?
- O que acontece se o sistema rebentar entre estas duas linhas?
- Quem é o árbitro quando dois pedidos competem pelo mesmo recurso?
- Durante quanto tempo podem os dados estar desatualizados, e quem nota?

## Exercício

Desenha o fluxo "marcar e pagar sinal de 5 €" com a API de pagamentos de um fornecedor. Indica onde ficam as transações, a chave de idempotência, o que acontece se o pagamento for aprovado mas a tua API rebentar antes de gravar, e como o sistema recupera.
