A maior parte do trabalho de um sénior não é em projetos novos. É em sistemas que já existem, que funcionam (mais ou menos), têm utilizadores e não podem parar. Saber melhorar **código legado** sem o partir é uma competência rara e muito valorizada.

## O que é código legado

Uma definição prática (de Michael Feathers): **código sem testes**. Não importa a idade: se não tens testes, cada alteração é um risco e as pessoas têm medo de lhe mexer.

## Reescrever do zero? Quase nunca.

A tentação é deitar fora e começar de novo. Normalmente corre mal: o código antigo tem anos de correções para casos que ninguém documentou, a reescrita demora o dobro do previsto, e durante esse tempo é preciso manter os dois. Prefere melhorar aos bocados.

## Testes de caracterização

Antes de mudar, escreve testes que **registam o que o código faz hoje**, mesmo que pareça errado:

```python
def test_caracterizacao_calculo_portes():
    # Não sei se isto está certo, mas é o que o sistema faz hoje
    assert calcular_portes(peso=0, zona="ilhas") == 7.5
    assert calcular_portes(peso=2.5, zona="continente") == 4.2
```

Agora podes mudar a estrutura com uma rede de segurança. Se um teste mudar, decides conscientemente se era um bug.

## O padrão estrangulador (*strangler fig*)

Para substituir um sistema antigo por um novo sem uma "grande mudança":

1. Põe uma camada à frente (um proxy, ou uma função) por onde passa todo o tráfego.
2. Implementa **uma** funcionalidade no sistema novo e encaminha só essa para lá.
3. Repete funcionalidade a funcionalidade.
4. Quando o antigo já não recebe nada, desliga-o.

Em cada passo há um sistema a funcionar e podes voltar atrás.

## Migrar dados sem parar

O mesmo princípio da lição de migrações da fase Júnior, em grande:

1. Escrever nos dois sítios (antigo e novo).
2. Copiar os dados históricos.
3. Comparar os dois (há diferenças? porquê?).
4. Ler do novo, com a possibilidade de voltar ao antigo.
5. Deixar de escrever no antigo.

## Funcionalidades atrás de interruptores

**Feature flags** deixam pôr código novo em produção desligado e ligá-lo aos poucos (para 1% dos utilizadores, para um salão de teste). Se correr mal, desligas sem deploy.

## Exercício

Escolhe o teu projeto mais antigo. Escreve 10 testes de caracterização para a sua parte mais importante, e depois planeia (por escrito, em passos com rollback) uma migração realista, por exemplo do Firebase para PostgreSQL, sem nunca deixar o sistema parado.
