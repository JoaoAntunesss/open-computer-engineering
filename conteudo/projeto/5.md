Testes automáticos dizem se o software faz o que foi programado; só os **utilizadores reais** dizem se faz o que é preciso. No projeto final, testar com as pessoas que vão usar o sistema (a dona do salão, as funcionárias, clientes de verdade) é o que separa um trabalho académico de um produto. Em IPM viste o método; aqui é a aplicação ao teu projeto, incluindo o que acontece depois de o pores em uso.

## Antes do lançamento: testes de usabilidade

- 5 participantes do público-alvo por ronda (clientes do salão, não colegas de curso).
- Tarefas realistas, sem dar a resposta ("marque uma madeixa para a próxima sexta à tarde").
- Pensar em voz alta, sem ajudar.
- Medir: taxa de sucesso, tempo, erros, e a satisfação (SUS).
- Corrigir os problemas mais graves e repetir.

## Depois do lançamento: o uso real

Pôr o sistema a uso, mesmo em pequena escala (só o Salão Aurora, durante duas semanas), revela o que nenhum teste revela: dados estranhos, horários de uso, telemóveis antigos, a funcionária que nunca abre o painel.

- **Analítica** (respeitando a privacidade e o RGPD): quantas pessoas começam uma marcação e quantas a acabam? Em que passo desistem?
- **Registo de erros** do lado do cliente (Sentry, ou um simples endpoint que regista os erros do JavaScript).
- **Feedback direto:** um botão "algo não correu bem?", e conversas com a dona.

## Medir o funil

Prevê onde está o maior problema, olhando para os números de duas semanas de uso:

```python run
funil = [
    ("abriu a página de marcações", 640),
    ("escolheu um serviço", 512),
    ("escolheu o dia", 468),
    ("escolheu a hora", 221),
    ("preencheu os dados", 198),
    ("confirmou", 187),
]
anterior = funil[0][1]
print(f"{'passo':30} {'pessoas':>8} {'do passo anterior':>18} {'do início':>10}")
for passo, n in funil:
    print(f"{passo:30} {n:8} {n / anterior:17.0%} {n / funil[0][1]:10.0%}")
    anterior = n

pior = min(range(1, len(funil)), key=lambda i: funil[i][1] / funil[i - 1][1])
print(f"\nmaior perda: '{funil[pior - 1][0]}' → '{funil[pior][0]}'")
```

Os números dizem **onde**, não **porquê**. Para o porquê, é preciso observar pessoas nesse passo (talvez as horas livres apareçam mal no telemóvel, ou os dias sem vagas não estejam marcados e as pessoas escolham dias cheios).

## Testes A/B (se houver volume)

Com muitos utilizadores, comparam-se duas versões de um passo com grupos aleatórios (Probabilidades, lição 8). Com poucos (um salão), não há dados para conclusões estatísticas: observar e conversar dá mais informação.

## Ética e consentimento

- Pede autorização para gravar ecrãs ou voz, e explica para que serve.
- Não recolhas mais dados do que precisas; anonimiza o que fica no relatório.
- Se o projeto envolve dados pessoais reais, a política de privacidade e o tratamento de dados têm de estar resolvidos **antes** de os recolher.
- Algumas universidades exigem aprovação de uma comissão de ética para estudos com pessoas: confirma.

## O que levar para o relatório

Os testes com utilizadores são das partes mais valorizadas pelo júri: mostram que o trabalho foi validado. Regista, para cada ronda: quem participou (perfil, sem nomes), as tarefas, os resultados (números), os problemas encontrados, o que mudou por causa deles, e os resultados da ronda seguinte.
