Um projeto final não se faz em três meses de programação seguidos de uma entrega. Faz-se em **ciclos curtos**: construir um pedaço, mostrá-lo ao cliente a funcionar, ouvir, ajustar. Cada demonstração é uma oportunidade de descobrir cedo que se percebeu mal um requisito, quando corrigir ainda é barato.

## O ciclo

```
planear (o que entra neste ciclo, 1–2 semanas)
   ↓
construir (histórias pequenas, de ponta a ponta, com testes)
   ↓
integrar e pôr em produção (ou num ambiente de testes)
   ↓
demonstrar ao cliente, com dados realistas
   ↓
retrospetiva (o que melhorar na forma de trabalhar)
   ↓ (repetir)
```

## Demonstrações que funcionam

- **Software a funcionar**, não slides. Num ambiente parecido com o real (o telemóvel do cliente, os serviços dele).
- **O cliente usa**, tu observas. Dá-lhe uma tarefa ("marca uma coloração para sábado") e cala-te. Onde hesita, há trabalho.
- **Dados realistas:** os serviços e os preços verdadeiros do salão, não "Serviço 1, 10 €".
- **Curta e focada:** 20 a 30 minutos, sobre o que mudou desde a última.
- **Regista as reações:** cada comentário vira uma história no quadro, ou uma decisão de não fazer.

## Integração contínua desde o início

Pôr em produção ao fim de cada ciclo só é viável se for fácil: CI com testes e deploy automático (Engenharia de Software, lição 7). Um projeto que só é "juntado" na última semana descobre lá todos os problemas de integração.

## Ciclos e aprendizagem

O valor de iterar está em **mudar o plano** com o que se aprende. Esta simulação compara duas equipas: uma que só mostra ao cliente no fim, outra que mostra a cada 2 semanas. Em cada ciclo, há uma probabilidade de uma funcionalidade estar a ser feita "errada" (mal percebida); quanto mais tarde se descobre, mais trabalho se deita fora.

```python run
import random

def projeto(semanas=12, ciclo=2, prob_mal_percebido=0.15, repeticoes=2000):
    desperdicio_total = 0
    for _ in range(repeticoes):
        desperdicio = 0
        semanas_em_erro = 0
        for semana in range(1, semanas + 1):
            if semanas_em_erro:
                semanas_em_erro += 1                                # continua a construir em cima do erro
            elif random.random() < prob_mal_percebido:              # começou algo mal percebido
                semanas_em_erro = 1
            if semana % ciclo == 0 and semanas_em_erro:             # demonstração: o cliente repara
                desperdicio += semanas_em_erro
                semanas_em_erro = 0
        desperdicio += semanas_em_erro                              # o que só se descobre no fim
        desperdicio_total += desperdicio
    return desperdicio_total / repeticoes

random.seed(0)
for ciclo in (12, 4, 2, 1):
    print(f"demonstração a cada {ciclo:2} semana(s): em média {projeto(ciclo=ciclo):.1f} semanas de trabalho deitado fora")
```

Prevê a tendência antes de correr. O modelo é simplificado (na realidade, cada demonstração também custa tempo), mas a conclusão é robusta: descobrir cedo é mais barato.

## Retrospetivas

No fim de cada ciclo, 15–30 minutos, três perguntas: o que correu bem? O que correu mal? O que mudamos no próximo ciclo (uma ou duas ações concretas, com responsável)? Sozinho, escreve as respostas num ficheiro: daqui a um mês, vais ver padrões.

## Gerir o tempo num semestre

- Os ciclos em semanas de exames são mais leves: planeia-o.
- **Congela as funcionalidades** duas ou três semanas antes da entrega: a partir daí, só correções, testes, documentação e preparação da apresentação.
- Mantém uma lista do que ficou de fora e porquê: é material para o relatório (trabalho futuro).
