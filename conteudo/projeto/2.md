Com o problema escolhido, é preciso transformá-lo num plano: o que se entrega, por que ordem, quem faz o quê, e como se sabe se está a correr bem. O plano não serve para ser cumprido à risca (vai mudar), mas para tomar decisões quando as coisas mudarem.

## Do objetivo às entregas

1. **Visão:** uma frase. "Clientes do Salão Aurora marcam online em menos de 1 minuto, e a dona gere a agenda num ecrã."
2. **Épicos:** os grandes blocos (marcações, painel da dona, lembretes, pagamentos).
3. **Histórias de utilizador** com critérios de aceitação (Engenharia de Software, lição 2).
4. **Marcos** com algo a funcionar para mostrar ao cliente, de 2 em 2 ou de 3 em 3 semanas.

## O produto mínimo viável

O **MVP** é a versão mais pequena que já resolve o problema principal para alguém real. Para o salão: marcar um serviço numa hora livre e a dona ver a marcação. Sem pagamentos, sem lembretes, sem estatísticas. Põe-se a uso o mais cedo possível; tudo o resto prioriza-se com o que se aprende.

## Priorizar: MoSCoW

- **Must:** sem isto, não serve (marcar, ver a agenda).
- **Should:** importante, mas há forma de contornar (lembretes por SMS).
- **Could:** seria bom (estatísticas, temas).
- **Won't (desta vez):** fica explicitamente de fora (app nativa, programa de fidelização).

## Dividir o trabalho numa equipa

- Dividir por **funcionalidades** (cada pessoa faz uma história de ponta a ponta), não por camadas ("eu faço a base de dados, tu a interface"), que cria dependências e esperas.
- Um **quadro** (GitHub Projects, Trello) com as colunas A fazer / Em curso / Revisão / Feito, e limite de trabalho em curso.
- Uma pessoa responsável por cada história, mas todo o código revisto por outra (pull requests).
- Combinar desde o início: horários de reunião, como se decide, onde fica a documentação, a definição de "feito".
- Sozinho, aplica-se o mesmo em ponto pequeno (um quadro, marcos, demonstrações ao cliente).

## Acompanhar: o gráfico de *burndown*

Mostra o trabalho que falta ao longo do tempo, comparado com a linha ideal. Prevê, olhando para os dados, se a equipa vai acabar a tempo:

```python run
total = 60                                   # pontos de história no plano
semanas = 10
feito_por_semana = [4, 5, 7, 6, 3, 2]        # o que se fez nas primeiras 6 semanas
acrescentado = [0, 0, 5, 0, 8, 0]            # trabalho que apareceu entretanto (pedidos novos)

restante = total
print("semana  ideal  restante")
for s, (f, a) in enumerate(zip(feito_por_semana, acrescentado), 1):
    restante = restante - f + a
    ideal = total - total * s / semanas
    print(f"{s:6} {ideal:6.0f} {restante:8}  {'#' * (restante // 2)}")

velocidade = sum(feito_por_semana[-3:]) / 3
print(f"velocidade recente: {velocidade:.1f} pontos/semana → faltam {restante / velocidade:.1f} semanas "
      f"(o semestre tem {semanas - len(feito_por_semana)})")
```

Quando o gráfico mostra atraso, há três alavancas: **reduzir o âmbito** (passar *should* para *won't*), mudar o prazo, ou mudar a forma de trabalhar (porque é que a velocidade caiu?). Acrescentar pessoas tarde raramente ajuda (lei de Brooks).

## Quando o cliente pede mais

Acontece sempre. Não se diz "não" nem "sim" automaticamente: escreve-se a história, estima-se, e pergunta-se ao cliente **o que sai** para ela entrar. O plano fica atualizado e o cliente percebe o custo de cada pedido.
