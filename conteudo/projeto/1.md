O projeto final é a cadeira em que juntas tudo o que aprendeste num produto a sério, para um cliente a sério (ou o mais perto disso possível). A decisão mais importante acontece antes de escrever uma linha de código: **que problema** vais resolver, e **para quem**. Um projeto tecnicamente brilhante que ninguém usa conta menos do que um simples que resolve um problema real.

## O que faz um bom problema

- **Real:** alguém o tem hoje e perde tempo ou dinheiro com ele. "O salão perde 3 horas por semana ao telefone a marcar" é real; "uma rede social para cães com blockchain" quase nunca é.
- **Com um cliente acessível:** alguém com quem possas falar todas as semanas, que te dê dados reais, teste as versões e diga o que está mal. Os melhores projetos têm um cliente exigente.
- **Do tamanho certo:** algo que uma equipa (ou tu sozinho) consegue entregar a funcionar no semestre, com uma primeira versão útil a meio. É melhor um problema pequeno bem resolvido do que um grande pela metade.
- **Com espaço para engenharia:** dados, regras, utilizadores diferentes, integração com algo externo. Um site só de conteúdo é pouco; um sistema de marcações com pagamentos e lembretes tem o suficiente.
- **Que te interessa:** vais passar meses com ele.

## Onde encontrar

- Negócios locais que ainda usam papel, Excel ou WhatsApp para gerir o trabalho (salões, oficinas, ginásios, associações, clínicas).
- O teu trabalho atual: tarefas repetitivas que se podiam automatizar (no serviço público, há muitas).
- Associações de estudantes, IPSS, clubes desportivos, a própria universidade.
- Projetos open source com pedidos de funcionalidades marcados como "help wanted".

## Validar antes de escolher

Antes de te comprometeres, fala com **pelo menos três pessoas** que tenham o problema (entrevistas da lição 3 de IPM). Pergunta como resolvem hoje, quanto lhes custa, o que já experimentaram. Se ninguém se queixar, o problema não é tão grande como parecia.

## Comparar ideias

Uma matriz de decisão simples ajuda a escolher com menos paixão e mais critério. Prevê qual ganha:

```python run
criterios = {"problema real": 3, "cliente disponível": 3, "cabe no semestre": 2, "engenharia interessante": 2, "motivação": 1}
ideias = {
    "marcações para salões":        {"problema real": 5, "cliente disponível": 5, "cabe no semestre": 4, "engenharia interessante": 4, "motivação": 4},
    "app de dieta com IA":           {"problema real": 3, "cliente disponível": 1, "cabe no semestre": 2, "engenharia interessante": 5, "motivação": 5},
    "gestor de quotas da associação": {"problema real": 4, "cliente disponível": 4, "cabe no semestre": 5, "engenharia interessante": 2, "motivação": 2},
    "rede social para estudantes":   {"problema real": 2, "cliente disponível": 2, "cabe no semestre": 1, "engenharia interessante": 4, "motivação": 5},
}
pontos = {nome: sum(criterios[c] * v for c, v in notas.items()) for nome, notas in ideias.items()}
maximo = 5 * sum(criterios.values())
for nome, p in sorted(pontos.items(), key=lambda x: -x[1]):
    print(f"{nome:32} {p:3} / {maximo}  {'#' * (p // 3)}")
```

Os pesos são uma escolha tua (aqui, o problema real e o cliente pesam mais). Muda-os e vê se o vencedor muda: se mudar com pequenas alterações, as ideias estão próximas e a decisão é mais pessoal.

## A proposta

Uma página, com:

1. **O problema**, em linguagem do cliente, com números se possível.
2. **Quem é o cliente** e quem são os utilizadores.
3. **A solução proposta**, em poucas frases (não a tecnologia: o que faz).
4. **O que fica fora** (tão importante como o que fica dentro).
5. **Como se mede o sucesso:** "a dona deixa de atender marcações por telefone", "80% das marcações passam a ser online".
6. **Riscos** principais (a lição 9 de Engenharia de Software).
