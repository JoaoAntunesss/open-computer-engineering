As escolhas de arquitetura e de tecnologia de um projeto final têm de servir **o problema, a equipa e o prazo**, não o currículo de quem as faz. A pergunta não é "qual é a tecnologia mais moderna?", mas "com que tecnologia esta equipa entrega um produto fiável neste semestre, e que o cliente consegue manter depois?".

## Critérios

1. **O que o problema exige:** tempo real? Funcionar sem rede? Muitos utilizadores? Dados sensíveis (saúde, pagamentos)? Integrações (SMS, pagamentos, calendários)?
2. **O que a equipa conhece:** aprender uma tecnologia nova custa semanas. Uma coisa nova por projeto, no máximo.
3. **Custo e manutenção:** quem paga o alojamento depois? Quem atualiza as dependências daqui a um ano? Um cliente pequeno não tem uma equipa de operações.
4. **Maturidade e comunidade:** documentação, respostas no Stack Overflow, bibliotecas, estabilidade.
5. **Saída:** se for preciso mudar, quão difícil é (dependência de um fornecedor)?

## Arquiteturas típicas para um projeto final

| Opção | Exemplo de stack | Bom para |
|---|---|---|
| **Monólito clássico** | Django ou Laravel + PostgreSQL, num PaaS | a maioria dos projetos; formulários, regras, administração já feita |
| **SPA + API** | React/Vue + FastAPI/Express + PostgreSQL | interfaces muito interativas, ou uma API usada também por uma app |
| **BaaS** | HTML/JS ou React + Firebase/Supabase | equipas pequenas, tempo real, sem servidor para gerir |
| **App móvel** | Flutter ou Kotlin (Android) + backend acima | quando o telemóvel é essencial (câmara, notificações, offline) |

Regra prática: **comece pelo mais simples que resolve**. Microsserviços, Kubernetes e filas de mensagens num projeto de semestre costumam ser complexidade que não paga.

## Decidir com critério

Uma matriz pesada (como na lição 1) evita escolhas por moda. Prevê o resultado para uma equipa de 3 pessoas que só conhece JavaScript e Python, a fazer o sistema de marcações:

```python run
pesos = {"conhecimento da equipa": 3, "tempo até ao MVP": 3, "custo para o cliente": 2,
         "manutenção pelo cliente": 2, "adequação (tempo real, integrações)": 2}
opcoes = {
    "Django + PostgreSQL (PaaS)":     [4, 4, 3, 3, 3],
    "React + FastAPI + PostgreSQL":   [4, 3, 3, 2, 4],
    "HTML/JS + Firebase":             [5, 5, 5, 4, 4],
    "microsserviços em Kubernetes":   [1, 1, 1, 1, 4],
    "Flutter + Firebase":             [1, 2, 4, 3, 5],
}
nomes = list(pesos)
for opcao, notas in sorted(opcoes.items(), key=lambda o: -sum(p * n for p, n in zip(pesos.values(), o[1]))):
    total = sum(p * n for p, n in zip(pesos.values(), notas))
    fraco = nomes[min(range(len(notas)), key=lambda i: notas[i])]
    print(f"{opcao:30} {total:3}   ponto fraco: {fraco}")
```

Não há resposta universal: com outra equipa (por exemplo, que já fez apps em Flutter) ou outro problema (uma app que tem de funcionar sem rede), o resultado muda.

## Documentar as decisões

Para cada decisão importante, um **ADR** curto (Engenharia de Software, lição 4): contexto, decisão, alternativas consideradas, consequências. No relatório final, o júri vai perguntar "porque escolheram X?": a resposta está pronta e é honesta.

## Desenhar antes de programar

- **Modelo de domínio** e **modelo de dados** (BD, lições 1 e 2): as entidades e as relações.
- **Diagrama de componentes:** o que fala com o quê.
- **Fluxos críticos:** o diagrama de sequência da marcação e do pagamento.
- **Modelo de ameaças** (Segurança, lição 9), sobretudo se houver dados pessoais ou pagamentos.
- **Uma "fatia vertical"** a funcionar logo na primeira semana: uma página que lê e escreve na base de dados em produção. Descobre-se cedo o que é difícil (o deploy, a autenticação).
