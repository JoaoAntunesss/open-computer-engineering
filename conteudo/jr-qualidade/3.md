Os testes unitários dizem que cada peça funciona. Os testes de **integração** dizem que as peças funcionam **juntas**: o teu código com a base de dados, com outra API, com o sistema de ficheiros. E para testar uma peça sem as outras, usam-se **duplos** (o mais conhecido é o *mock*).

## Um teste de integração com base de dados

Em vez da base de dados de produção, usa-se uma de teste, criada e apagada em cada execução. Com SQLite em memória é instantâneo:

```python
import sqlite3
import pytest
from repositorio import criar_tabelas, guardar_cliente, procurar_por_email

@pytest.fixture
def db():
    con = sqlite3.connect(":memory:")
    criar_tabelas(con)
    yield con
    con.close()

def test_guardar_e_procurar(db):
    guardar_cliente(db, "Ana", "ana@exemplo.pt")
    c = procurar_por_email(db, "ana@exemplo.pt")
    assert c["nome"] == "Ana"

def test_email_repetido_e_recusado(db):
    guardar_cliente(db, "Ana", "ana@exemplo.pt")
    with pytest.raises(sqlite3.IntegrityError):
        guardar_cliente(db, "Outra", "ana@exemplo.pt")
```

A *fixture* `db` prepara uma base limpa para cada teste. Para PostgreSQL, faz-se o mesmo com um contentor Docker (ferramentas como o Testcontainers tratam disso).

## Duplos: quando não queres a coisa verdadeira

Não queres que os testes enviem emails reais, cobrem cartões ou dependam da internet. Substituis essa parte por um duplo:

| Tipo | O que é |
|---|---|
| **Stub** | Devolve sempre uma resposta fixa |
| **Fake** | Uma versão simples que funciona (base de dados em memória) |
| **Mock** | Regista como foi chamado, para verificares depois |

```python
from unittest.mock import Mock
from marcacoes import confirmar_marcacao

def test_confirmar_envia_email():
    email = Mock()
    confirmar_marcacao("ana@exemplo.pt", "2027-01-10 15:00", enviar_email=email)
    email.assert_called_once()
    destino, assunto, corpo = email.call_args.args
    assert destino == "ana@exemplo.pt"
    assert "10 de janeiro" in corpo
```

Repara que a função recebe `enviar_email` como parâmetro. Este desenho (passar as dependências em vez de as criar lá dentro) chama-se **injeção de dependências** e é o que torna o código fácil de testar.

## Não exagerar nos mocks

Se mockares tudo, os testes passam mas não provam nada: estás a testar os mocks. Regra prática:

- Mocka o que é **lento, caro ou externo** (email, pagamentos, APIs).
- Usa a coisa verdadeira (ou um fake) para o que é teu (base de dados de teste, as tuas funções).

## Exercício

Tens uma função `lembrar_marcacoes(hoje, repositorio, enviar_sms)` que envia SMS a quem tem marcação amanhã. Escreve: um teste com um fake do repositório e um mock do SMS que confirme que só os clientes de amanhã recebem mensagem, e um teste que confirme que nada é enviado quando não há marcações.
